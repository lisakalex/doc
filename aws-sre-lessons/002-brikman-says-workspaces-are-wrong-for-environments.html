Question 002 · terraform

Brikman says workspaces are the wrong way to separate environments. aws-sre uses workspaces to separate environments. Who is right?

#002 2026-11-16 terraform answered

The question, as asked

Nobody asked it. It fell out of pointing the library at the repo: the single most authoritative Terraform book on the shelf argues against the central design decision in terraform/cluster/env.tf.

"Due to these drawbacks, workspaces are not a suitable mechanism for isolating one environment from another: e.g., isolating staging from production."

— Brikman, Terraform: Up & Running 3e, p171

Short answer

Brikman is right, and env.tf already says so in a comment — but the repo is weaker than that comment implies. The three env/backend-*.hcl files are byte-identical apart from a comment, so the per-environment backend config is decoration: -backend-config=env/backend-prod.hcl selects nothing. The environment comes entirely from terraform workspace select, which is exactly the invisible, same-credentials mechanism Brikman warns about.

The repo's defence is that it is a teaching specimen that has to stay readable as one configuration. That is a legitimate trade, but it is a trade, and the missing half of it is that nothing enforces the choice.

The mechanism

Brikman's three objections, checked against this repo:

His objection Does it land here?
All workspaces share one backend, so one set of credentials and access controls covers every environment Yes, fully. All three backend files name the same bucket example-tfstate, the same key cluster/terraform.tfstate, and the same lock table.
Workspaces are invisible in the code and the terminal Yes. Nothing in a diff tells you which environment it will hit.
Therefore error-prone, with no second layer of defence Yes — and env.tf makes it worse in one specific way, below.

The thing worth taking away is why sharing a backend matters. State is not just a record; it is read-write credentials to everything it describes. An identity that can write env:/dev/cluster/terraform.tfstate can write env:/prod/cluster/terraform.tfstate, because they are two keys in one bucket under one bucket policy. So "dev and prod are separate" is true of the resources and false of the authority over them. Separate directories do not fix that by themselves either — separate accounts do, which is what the env.tf comment points at and what a real employer would have.

Then there is the default-workspace fallback:

env = terraform.workspace == "default" ? "dev" : terraform.workspace

The comment argues this is safe because dev is the survivable place to land. That reasoning is sound for a forgotten workspace select. It does not cover the more likely mistake: running workspace select prod once, walking away, and coming back to a shell that is still on prod. The workspace is sticky state on disk (.terraform/environment), not something you pass per command, so the dangerous case is not "no workspace" but "the wrong workspace, left over". A fallback cannot help with that. Only something that prints the target and refuses, or a separate account, can.

What I thought first

That the per-environment backend files were doing real work — that -backend-config=env/backend-prod.hcl was what made prod prod. The naming invites that reading, the Makefile passes the flag on every init, and three separate files look like three separate configurations.

They are three copies of one configuration. The flag is a no-op; the terraform workspace select on the next line of the Makefile is the whole mechanism. The files would only earn their names if they differed — a per-environment bucket, or at minimum a per-environment key.

The general shape: a file named after a distinction does not create the distinction. Same error as 001, where a remote named origin looked like it carried permission. Both times the name described intent and was mistaken for enforcement.

What would actually fix it

In rough order of strength, weakest first:

  1. A check block asserting the workspace matches the bucket or key in use — makes the mismatch visible, enforces nothing.
  2. Give each backend file a distinct key (e.g. cluster/prod/terraform.tfstate) so the three files stop being identical, and drop the workspace prefix. The files then mean what they are named.
  3. A distinct bucket per environment, with its own bucket policy — now a dev credential cannot address prod state.
  4. A distinct AWS account per environment. This is the only one that is a boundary rather than a convention, and it is what env.tf already names as the real answer.

None of this is applied; see the standing caveat in the README.
