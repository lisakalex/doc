Question 001 · safety

Does removing a git remote guarantee a push can't reach GitHub?

#001 2026-11-15 safety answered

The question, as asked

"Do you think if we remove a remote from this project repo, it will guarantee that any push doesn't reach the GitHub"

Short answer

No. git remote remove origin deletes three lines from .git/config and stops exactly one thing — a bare git push with no arguments, because the branch's upstream tracking goes with it. Pushing by URL needs no remote and no config at all, and the credential still works.

The guarantee is server-side: archiving the repository on GitHub, which makes it read-only for every method and every credential.

The mechanism

A remote is a nickname, not a permission. .git/config maps the name origin to a URL so you can type less. Git accepts a URL anywhere it accepts a remote name, so deleting the nickname leaves this working:

git push git@github.com:lisakalex/aws-sre.git HEAD:main

Authorisation is separate and untouched. This machine pushes over SSH with ~/.ssh/id_rsa, which is registered against the GitHub account; removing a config entry does not deregister a key. And the URL is recoverable from the reflog, the README and argocd/applicationset.yaml regardless.

So removing the remote is a guard against a reflex, not against an intention — the same class as a shell alias. Three rungs of strength:

Stops Bypassed by
Remove the remote bare git push naming the URL
pre-push hook every push, however addressed --no-verify; and .git/hooks is untracked, so it needs core.hooksPath to survive a clone
Archive the repo every push, period unarchiving it

Only the third is enforced by the other end of the connection, so nothing in the working copy can weaken it. That is the same reasoning as preferring an IAM policy or an SCP over prevent_destroy for production deletion: a control the actor can edit is not a control over that actor.

git remote set-url --push origin no_push is a popular variant and is the same illusion — push-by-URL walks past it identically.

Where to look

Verified after archiving, on 2026-11-15:

$ git push --dry-run origin main
ERROR: This repository was archived so it is read-only.
fatal: Could not read from remote repository.

$ git fetch origin        # reads still work
From github.com:lisakalex/aws-sre
 * [new branch]  claude/html-from-markdown-3n7ga4 -> origin/...
  • aws-sre/docs/SAFETY.md — "Layer 0 — the repository is archived"
  • GitHub: Settings → Danger Zone → Archive this repository

What I thought first

The intuition was that a push needs a remote, so removing the remote removes the ability to push. Reasonable, because that is how it behaves day to day: every push you have ever typed was git push or git push origin main, and both stop working.

What the intuition misses is that the thing which stops working is the shorthand. The underlying operation takes a URL and a credential, and both are still there. The general shape of the mistake — mistaking a convenience for a constraint — is worth more than the git detail.

Consequences worth remembering

Archiving also freezes things that are easy to forget:

  • GitHub Actions do not run on an archived repository, scheduled workflows included. drift.yml's nightly plan stopped. Harmless while nothing is applied, but it is a guard that silently stopped working — unarchive and confirm it runs before trusting it again.
  • Open pull requests cannot be merged (there were 5).
  • Most repository settings are locked; any change means unarchiving first.
  • Archiving does not retract anything. Everything already pushed is still there.
