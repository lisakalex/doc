Mule Without Keys

Reaching AWS Secrets Manager or Parameter Store from Mule without storing a long-lived AWS access key. Written for an estate with standalone hybrid runtimes on your own servers and CloudHub applications — because those two can reach very different places, and pretending otherwise produces a design that quietly fails on one of them.

standalone hybrid CloudHub 2026-09-16

The answer, before the detail

One runtime can do this. The other cannot.

RuntimeWhere it runsBest achievableMechanism
standalone hybridyour serversno stored AWS keyIAM Roles Anywhere — X.509 exchanged for temporary credentials
CloudHubMuleSoft's AWS accounta stored credential, or no AWS access at allno customer workload identity to federate from

That asymmetry is the whole design. You own the on-premises hosts, so you can give them an identity. You do not own the CloudHub workers, so you cannot — which means the useful goal is no keys where it is achievable, and tightly scoped keys where it is not, rather than one uniform approach that is weakest everywhere.

Check this first

The connector decides whether any of this is possible

Some MuleSoft AWS connectors expose only Access Key and Secret Key fields. If yours does, it will force a static credential regardless of how good your federation is, and the design is dead before it starts.

You need an authentication option equivalent to "Default AWS Credentials Provider Chain" or a role-based mode. That is what lets the underlying AWS Java SDK resolve credentials from the environment instead of from connector fields.

verify before designing

  • Open the connector in Exchange and confirm it offers the default provider chain or a role option.
  • If it does not, the fallback is calling the AWS API over HTTPS with SigV4 from a Java module — workable, but substantially more code to own.
  • Check whether an SSM / Parameter Store connector exists at all. Secrets Manager has a first-class connector; SSM may not, and that alone may decide which store you use.

Part 1 · standalone hybrid

IAM Roles Anywhere

OIDC federation is the usual answer for workloads outside AWS, but it needs a token issuer — a Kubernetes API server, SPIRE, a CI provider. A standalone Mule runtime on a VM has none of those. Roles Anywhere is the route that fits: the host proves itself with a certificate from a CA you already operate.

The wiring is one file

The signing helper implements AWS's credential_process contract, so the Java SDK inside Mule picks up credentials with no application code change:

# ~/.aws/config on the Mule host [profile mule] credential_process = /opt/aws/aws_signing_helper credential-process \ --certificate /etc/pki/mule.crt \ --private-key /etc/pki/mule.key \ --trust-anchor-arn arn:aws:rolesanywhere:eu-west-1:111122223333:trust-anchor/… \ --profile-arn arn:aws:rolesanywhere:eu-west-1:111122223333:profile/… \ --role-arn arn:aws:iam::111122223333:role/mule-secrets-reader

Then give the Mule runtime the profile. For a standalone runtime managed by the service wrapper, that is an environment entry in the wrapper configuration:

# $MULE_HOME/conf/wrapper.conf set.AWS_PROFILE=mule set.AWS_REGION=eu-west-1

verify

  • Confirm the exact directive your runtime's wrapper uses for environment variables, and that it is inherited by the JVM — set.NAME=value is the Tanuki wrapper convention but check your version.
  • Test outside Mule first: AWS_PROFILE=mule aws sts get-caller-identity on the host. If that returns an assumed-role ARN, the hard part is done.

Two things that make this genuinely strong

issue short, renew often

Certificate lifetime

Days, not years, renewed automatically by your PKI. A compromised certificate expires without anyone doing anything. This is the property an access key can never have.

PKCS#11

Key in a TPM or HSM

Roles Anywhere supports PKCS#11, so the private key never exists as a readable file. This is the step that makes "no stored secret" literally true rather than approximately true.

Scope the role to the certificate

Roles Anywhere surfaces certificate attributes as principal tags, so the trust policy can name which certificate may assume the role — the same discipline as pinning sub and aud in an OIDC trust policy:

"Condition": { "StringEquals": { "aws:PrincipalTag/x509Subject/CN": "mule-prod-01" } }

Without a condition like this, any certificate your CA has ever issued can assume the role — including the one on a developer laptop. A CA is a wide trust boundary; narrow it here.

Part 2 · CloudHub

Why the same trick does not work here

A CloudHub worker runs inside MuleSoft's AWS account, not yours. That single fact removes both federation routes:

instance rolebelongs to MuleSoft's account, and grants nothing in yours
IAM Roles Anywhererequires a certificate and private key placed on the host — you do not control the host
OIDC federationrequires a workload identity token the platform issues to your app

verify — this is the one to check yourself

  • Confirm whether your CloudHub version exposes any workload identity token usable for AssumeRoleWithWebIdentity. If it does, that changes this section entirely and you should design around it instead.
  • I would not rely on my answer here — platform capabilities move, and this is exactly the kind of thing that gains a feature between releases.

Assuming it does not, you have three options, and the first is better than it sounds:

1

Give CloudHub no AWS access at all

Ask why the CloudHub app needs to read an AWS secret. Often it needs the thing the secret unlocks, not the secret. Put that capability behind an internal API served from the on-premises tier — which already has a real AWS identity — and let CloudHub call it over your existing connectivity.

The credential never leaves the environment that can hold it safely. This is usually the right answer and it is usually dismissed too quickly.

2

Let Anypoint hold what CloudHub needs

If the value is genuinely needed in CloudHub and is not an AWS credential, keep it in Anypoint's own secure configuration rather than fetching it from AWS. One store, one owner, no synchronisation problem.

3

A stored AWS credential, scoped hard

If neither works, accept level 3 deliberately rather than by accident, and make the blast radius small.

If you land on option 3, the credential should be able to do exactly one thing:

{ "Effect": "Allow", "Action": ["secretsmanager:GetSecretValue"], "Resource": "arn:aws:secretsmanager:eu-west-1:111122223333:secret:cloudhub/orders-*" }, { "Effect": "Allow", "Action": ["kms:Decrypt"], "Resource": "arn:aws:kms:eu-west-1:111122223333:key/…" }

Four things to do alongside it

Wildcard the ARN suffix. Secrets Manager appends six random characters that change if the secret is recreated — secret:cloudhub/orders-*, not the full ARN, or the policy silently stops matching one day.

Rotate it on a calendar. There is no automation path here; put it in a schedule and treat a missed rotation as a finding.

Alarm on use from anywhere unexpected. CloudTrail records the source IP of every call. That credential should only ever be used from CloudHub's ranges — anything else is an incident, and it is the only detection you get.

Write down that it is level 3 and why. An accepted risk with a reason is an engineering decision. The same risk undocumented is an oversight, and the difference is entirely visible in a review.

Both runtimes

Fetch once, not per message

Whatever the credential path, do not call AWS on every message. It adds a network round trip to your latency, costs per request, and will eventually throttle under load.

cache with a TTLObject Store with an expiry of minutes to hours, sized to how often the value can change
re-fetch on auth failureif the downstream rejects the credential, invalidate the cache entry and retry once
never at property-resolution timesecure properties resolve at startup, so a value read that way is frozen until redeploy

That last row is the one that surprises people

If the secret arrives as a secure:: property placeholder, the application reads it once when it deploys. Rotate the value in AWS and the running app carries on with the old one until someone redeploys — and the failure appears days later, at an unrelated moment, looking like a connectivity problem.

Fetching inside the flow with a cache is what makes rotation invisible. It is a deliberate design choice, not the default.

Which store

Parameter Store unless something rotates

For your estate, rotation is largely manual anyway: nothing automated can reach a database on your own network without either exposing it or building a tunnel, and CloudHub cannot be rotated into. So Secrets Manager's headline feature is mostly unavailable to you, and Parameter Store is the honest default — provided a connector exists.

If no SSM connector exists, use Secrets Manager rather than hand-writing SigV4 to save $4.80 a year. That is the wrong trade, and it is the sort of decision that looks clever in a design document and expensive in a maintenance window.

Before you build

Verification checklist

Everything here that I could not confirm from your environment. Confirm these before committing to the design — several would change it.

confirm

  • The AWS connector offers a default credential provider chain or role option, not just key fields.
  • Whether an SSM / Parameter Store connector exists for your runtime version.
  • Whether CloudHub exposes any workload identity token usable for web-identity federation.
  • The wrapper directive that sets environment variables for your standalone runtime, and that the JVM inherits them.
  • That your CA can issue short-lived certificates automatically — if renewal is manual, you have replaced one long-lived secret with another.
  • Whether your hosts have a TPM usable through PKCS#11. Without it the private key is a readable file, and the design is "much better" rather than "no stored secret".
