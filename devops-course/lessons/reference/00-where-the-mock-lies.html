Where the Mock Lies

You can run most of this course's hands-on work with no AWS account, no credentials and no spend — the real aws CLI against a local fake, with the repo's own buckets, tables, key and role already in it. What you cannot do is trust all of it. A mock that refuses the wrong things teaches you wrong things, and this one succeeds in four places where AWS would refuse.

uv run assets/scripts/sandbox.py moto 5, server mode 23 behaviours measured $0.00

The one command

A local account, seeded to match your Terraform

# terminal 1 — boots moto in server mode and creates what terraform/ creates uv run assets/scripts/sandbox.py # terminal 2 — point the CLI at it, then run the lessons export AWS_CONFIG_FILE=assets/scripts/sandbox.aws.config aws kms describe-key --key-id alias/prima-tech-challenge-avatars --profile sandbox \ --query 'KeyMetadata.[KeyState,Origin,KeyManager]' --output text # Enabled AWS_KMS CUSTOMER

Every command in every lesson works unchanged except for one word: where the lesson says --profile admin, say --profile sandbox. No endpoint flags, no awslocal wrapper — the AWS CLI reads endpoint_url straight out of the profile.

The sandbox is seeded with the resources terraform/main.tf and terraform/state-backend/ really create, under the same names: the avatars CMK with rotation on and its alias, both buckets versioned and encrypted with that key and fully public-access-blocked, the users table keyed on email, the prima-tech-challenge-tfstate-lock table keyed on LockID, and prima-app-role carrying its three real statements.

The three that matter

Where it will mislead you, specifically

1 · Nothing is denied, ever

There is no IAM evaluation. Not a partial one — none. Create a role whose trust policy denies every principal on earth, then assume it:

# trust policy: { "Effect": "Deny", "Principal": { "AWS": "*" }, "Action": "sts:AssumeRole" } aws sts assume-role --role-arn arn:aws:iam::123456789012:role/denyrole \ --role-session-name probe --profile sandbox arn:aws:sts::123456789012:assumed-role/denyrole/probe # AWS: AccessDenied

So Module 2 is the one part of this course you cannot do hands-on for free. Lesson 2.3 (explicit deny wins), 2.4 (the missing claim) and 2.2 (how role assumption works) all turn on a refusal that never comes. The policy simulator, which Lesson 2.3 uses as its instrument, is not implemented at all.

LocalStack can enforce IAM — identity policies, resource policies, permissions boundaries and SCPs together, with an error naming the policy that denied you — behind ENFORCE_IAM=1. It is a paid feature, not in Community. moto has its own access control behind INITIAL_NO_AUTH_ACTION_COUNT, which its documentation describes as "very basic". Neither is a substitute for reading the evaluation rules and reasoning.

2 · A disabled key still decrypts

Lesson 4.2's claim is that disabling a key is the one action that is instant, total and fully reversible — the kill switch. Here it kills nothing:

aws kms disable-key --key-id $KID --profile sandbox aws kms encrypt --key-id $KID --plaintext "$(echo -n hello | base64)" --profile sandbox NjllNTQzOWItOWFhYS00MTVmLTgwMWUtOGUxOTI0MDc3YjgzaGVsbG8= # AWS: KMSInvalidStateException

And look at that blob. Base64-decode it and you get the key ID followed by the word hello. The sandbox's "ciphertext" is a concatenation, so it will faithfully demonstrate the shape of envelope encryption — which is what envelope.py uses it for — and will tell you nothing whatsoever about confidentiality.

The half that is real is the useful half

Every KMS state transition is faithful. Enabled → schedule-key-deletion → PendingDeletion with a correct seven-day deletion date → cancel-key-deletion → Disabled, which is precisely the two-step recovery in Lesson 4.3's fourth revision question, and you can now walk it on a keyboard instead of in your head. What the sandbox omits is the consequence of the state, not the state.

3 · Capacity is a constant

900-byte item ConsumedCapacity 1.0 # AWS: 1 WCU 10 KB item ConsumedCapacity 1.0 # AWS: 10 WCU

Which erases most of Lesson 5.2. The 28.9% break-even, the 3,000-read / 1,000-write per-partition ceiling, burst capacity, adaptive capacity, the four kinds of throttling — none of it has a model behind it here. This is exactly why access_patterns.py computes read units in Python from item sizes rather than reading ConsumedCapacity out of the response: the number moto returns is a placeholder, and a lesson built on it would have been a lesson built on 1.0.

The pattern across all four: anything whose lesson is a consequence rather than a configuration. The sandbox is excellent at "what did I declare" and poor at "what happens because of it".

The rule

How to use an instrument with a known bias

1

Run the fidelity table first, not the lesson

uv run assets/scripts/sandbox.py --fidelity. If the behaviour you are about to exercise is in the fake column, the sandbox cannot answer your question and a success proves nothing.

2

Treat a refusal as evidence and a success as a question

When the mock refuses, it is almost always right — refusals are the part that has to be written deliberately. When it succeeds, ask whether AWS would have.

3

Re-measure after upgrading

The table is a snapshot of moto 5. fake rows are the ones most likely to become real, because they are bugs people file. That is a good thing to notice rather than assume.

4

Keep the real account for the consequences

If an account is available at all, spend it on the four things above — a denied IAM call, a disabled key breaking a running service, a throttled table, a bill. Everything else can be done here for nothing.

A worked example of the rule, from building this page

get-key-rotation-status refused an alias and I assumed the mock was broken. The KMS API reference says the parameter takes "the key ID or key ARN" — no alias — so the refusal was correct and my command was wrong. It is the same family as cancel-key-deletion in Lesson 4.3, which also takes a key ID or ARN and never an alias. The mock taught me something true by saying no.
