The Second Lock

Permission to write an object is not permission to write an encrypted object. Your own Terraform already carries the fix, in a comment you have read but probably not needed yet. This is why it is there.

account 739489595894 us-east-1 terraform/main.tf 2026-09-13

Start with the failure

Full S3 permission, and the upload still fails

Imagine the app role held only its first statement — every S3 action it needs, on exactly the right bucket:

{ "Effect": "Allow", "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:ListBucket"], "Resource": [bucket_arn, bucket_arn + "/*"] }

A user uploads an avatar. The call fails:

AccessDenied: User: arn:aws:sts::739489595894:assumed-role/prima-app-role/… is not authorized to perform: kms:GenerateDataKey on resource: arn:aws:kms:…:key/…

Nothing is wrong with the S3 permission. The request never got far enough to be an S3 problem. Your repo already anticipates this — terraform/main.tf:

# Required because the bucket's default encryption uses the CMK # above: PutObject needs GenerateDataKey, GetObject needs Decrypt. Effect = "Allow" Action = ["kms:Decrypt", "kms:GenerateDataKey"] Resource = aws_kms_key.avatars.arn

The rule

On a bucket with KMS default encryption, every object operation needs permission on two separate resources: the object, and the key. Grant one without the other and you get a denial that names a service you were not thinking about.

To understand why a write needs a key operation called GenerateDataKey — rather than something called Encrypt — you have to know what S3 actually does with your CMK. It is not what most people assume.

The mechanism

Nothing is ever encrypted with your CMK

Your customer-managed key never touches your data. It cannot — KMS will not encrypt more than 4 KB in a single call, and your avatars are larger than that. What happens instead is envelope encryption:

On the way back out, the steps run in reverse: S3 reads the encrypted data key stored beside the object, sends that to KMS as kms:Decrypt, gets the plaintext data key back, decrypts the object, and forgets the key again. Which is exactly why your policy grants those two actions and no others.

Three consequences worth stating in an interview

Your data never travels to KMS. Only a 256-bit key does. You can encrypt petabytes through a service with a 4 KB request limit.

Revocation is instant and total. Disable the CMK and every object in the bucket becomes unreadable immediately — no re-encryption, no sweep. The data keys are still there, still wrapped, and nothing can unwrap them. This is the Module 3.1 answer to “what does versioning not save you from”, seen from the other side.

Every read and write is an auditable KMS event. CloudTrail records each Decrypt and GenerateDataKey with the caller's identity. That is the real reason to choose a CMK over the default key, and it is the next section.

The choice you already made

SSE-S3 vs SSE-KMS with a customer key

Every object in S3 is encrypted at rest — that has been the unconditional default since January 2023, and it is not something you switch on. What you choose is who controls the key:

Your repo comments the reasoning already: “a customer-managed key rather than the AWS-managed aws/s3 key gives us key rotation, CloudTrail auditing of key usage, and the ability to revoke access by disabling the key — independent of the bucket/object permissions themselves.” That last clause is the one to remember: the key is a second, independent control surface. You can cut off access to data without touching a single IAM policy.

Two more exist and are worth naming only so you are not surprised: SSE-C, where you send the key with every request and AWS stores none of it (you own the loss risk), and DSSE-KMS, which applies two independent layers for regulated workloads at roughly double the KMS cost. Neither is a sensible default.

A cost decision in a security setting's clothes

bucket_key_enabled = true

One line in your encryption block, easy to skim past, and on a busy bucket it is the difference between pennies and a genuine bill:

rule { apply_server_side_encryption_by_default { sse_algorithm = "aws:kms" kms_master_key_id = aws_kms_key.avatars.arn } bucket_key_enabled = true }

Without it, envelope encryption does what the diagram shows on every single request: one GenerateDataKey per PUT, one Decrypt per GET. KMS charges about $0.03 per 10,000 requests. With an S3 Bucket Key, S3 asks KMS for a short-lived bucket-level key and derives per-object keys from it locally — cutting KMS calls by up to 99%.

Nothing about the security posture changes — same CMK, same audit trail at the bucket level, same revocation. What changes is how many times S3 has to phone KMS. You have it on, which is correct, and the trade is worth stating precisely: per-object CloudTrail granularity is reduced, because many objects now share one key-generation event. For an avatar bucket that is the right call; for a bucket where you must prove who read which specific object, it is not.

Connect it to last week

This is a cost-reflective charge in the sense we discussed: you reduce it by doing less work. It is also the single most common surprise on KMS bills, because the line that controls it lives in an encryption block that reviewers read as a security setting and skip.

Two policies, both must say yes

Where the second lock is actually defined

Lesson 2.3 introduced resource-based policies as a diagram. Here they are holding your data. Reading an encrypted object requires both:

identity-based — on the role

May this principal use the key?

kms:Decrypt and kms:GenerateDataKey on the key ARN. This is the block in your main.tf.

resource-based — on the key

Does the key accept this principal?

The key policy. Terraform did not write one, so the key got the AWS default — and that default is what makes your IAM grant sufficient.

{ "Sid": "Enable IAM User Permissions", "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::739489595894:root" }, "Action": "kms:*", "Resource": "*" }

From 2.3: :root in a resource policy means the account as a whole, not the root user. The statement says “defer to IAM” — anyone in this account whose identity policy allows a KMS action may perform it. That is the only reason adding kms:Decrypt to a role is enough.

The failure mode that makes this worth knowing

Replace that default key policy with a narrower one that forgets to include the account or your admin role, and you have permanently lost the key — and with it every object encrypted under it. No IAM permission can repair it, because the key policy is what decides who may edit the key policy. Not even root can override it. AWS Support is the only route back, and it is not guaranteed.

This is the single most dangerous resource policy in AWS, and it is why the default always contains that :root statement. Never remove it. Add to it.

Access · the part that makes headlines

Four switches that do four different things

Everyone copies this block of four booleans and nobody can say what the individual lines do. They form a 2×2: two are about ACLs, two about bucket policies; two reject new settings, two neutralise existing ones.

ACLsBucket policies

The two columns matter because they are different mechanisms. Blocking public policies does nothing about an object made public by an ACL, and vice versa. Setting all four — which both your buckets do — is the only configuration with no gap.

Since April 2023 AWS enables all four by default on new buckets, precisely because the era of accidentally-public buckets produced a decade of breaches. Your Terraform predates nothing and sets them explicitly, which is still right: defaults change, declared intent does not.

And the ACL setting beside them

resource "aws_s3_bucket_ownership_controls" "avatars" { rule { object_ownership = "BucketOwnerPreferred" } }

ACLs are S3's original permission system, older than IAM, attached per-object, and the source of endless confusion — an object uploaded by another account could be owned by them, in your bucket, unreadable by you. BucketOwnerPreferred fixes the ownership but keeps ACLs switched on.

A real improvement you could make

AWS's current recommendation is BucketOwnerEnforced, which disables ACLs entirely and makes bucket policies the only access mechanism. One system instead of two, and one fewer way to be accidentally public. Your buckets take uploads from nobody but your own role, so nothing would break. This is a genuine, small, defensible change — the kind worth having in a portfolio diff.

The gap in your setup

Encrypted at rest is not encrypted in transit

Everything so far protects bytes sitting in S3. Nothing so far requires that they arrive over TLS. S3 accepts plain HTTP, and neither of your buckets forbids it:

$ aws s3api get-bucket-policy --bucket prima-tech-challenge-lisakalex-tfstate NoSuchBucketPolicy: The bucket policy does not exist

In practice your traffic is HTTPS — boto3 defaults to it, as does the CLI. But in practice is not a control. The control is a bucket policy that denies anything else:

{ "Sid": "DenyInsecureTransport", "Effect": "Deny", "Principal": "*", "Action": "s3:*", "Resource": ["arn:aws:s3:::BUCKET", "arn:aws:s3:::BUCKET/*"], "Condition": { "Bool": { "aws:SecureTransport": "false" } } }

Note the shape, because Lesson 2.5 taught exactly this trap: it is a Deny with a negative condition. aws:SecureTransport is always present on an S3 request — every call arrives over one protocol or the other — so plain Bool is safe here, unlike aws:MultiFactorAuthPresent, which can be absent entirely. Knowing why the two cases differ is the difference between copying a snippet and understanding it.

Hands-on · ~5 minutes · read-only, costs nothing

Inspect what is actually configured

Warm the session first: aws sts get-caller-identity --profile admin. Every command below only reads.

1

See the encryption config

aws s3api get-bucket-encryption --bucket prima-tech-challenge-lisakalex-tfstate --profile admin — the algorithm, the key ARN, and BucketKeyEnabled in one place.

2

Prove it on a real object

aws s3api head-object --bucket … --key senior-sre-tech-challenge/terraform.tfstate --profile admin — look for ServerSideEncryption, SSEKMSKeyId and BucketKeyEnabled. Per-object proof, not just bucket intent.

3

Read the key policy

aws kms get-key-policy --key-id <id> --policy-name default --profile admin — find the :root statement and say out loud what it means.

4

Confirm all four switches

aws s3api get-public-access-block --bucket … --profile admin — four trues. Then get-bucket-ownership-controls for the ACL setting.

5

Confirm the TLS gap

aws s3api get-bucket-policy --bucket … --profile admin — NoSuchBucketPolicy. That is the finding, not an error.

Check yourself

Four questions

Your own words, closed book. Given the 3.1 pattern, watch the term pairs — two of these turn on picking the right one of two similar words.
