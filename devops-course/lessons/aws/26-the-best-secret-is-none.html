The Best Secret Is None

Before learning how to store a secret, learn how not to have one. Your repository already manages secrets correctly, and the way it does that is by containing none — which is a design decision, not an absence.

taught 2026-09-15 added after Module 2 closed app/ · terraform/ · .github/

The audit

Search your own repo for a secret. There isn't one.

Where you would expect oneWhat is actually there
app/config.pyregion, bucket name, table name, size limit — configuration, not secrets
app/services/s3.pyaws_secret_access_key="test" — a LocalStack dummy, guarded by if settings.aws_endpoint_url
terraform/no secretsmanager, no ssm, nothing to store
.github/workflows/role-to-assume: over OIDC — no stored AWS keys

The single GitHub secret is AWS_ACCOUNT_ID, and that is an identifier rather than a credential — knowing it grants nobody anything. Hiding it is cheap defence in depth against reconnaissance, not secret management.

This is the whole lesson

Every secret you eliminate is one you never have to store, rotate, audit, revoke, or explain in an incident. Secret management is the fallback for when elimination fails — not the first tool you reach for.

The ranking

Three levels, in this order

1

No secret exists

The identity is proved by what the caller is, not by what it stores. IRSA for pods, OIDC for pipelines, instance roles for EC2. You already have two of these — Lessons 2.2 and 2.4 were about exactly this machinery. Nothing on disk, nothing to leak, credentials that expire in minutes.

2

A secret exists, and AWS holds it

RDS with managed rotation: the database password is generated, stored and rotated by AWS, and no human ever sees it. A secret nobody knows cannot be leaked by a person. Use this wherever the service supports it.

3

A secret exists and you own it

A third-party API key, a webhook signing secret, a legacy database that predates IAM. Now — and only now — you need a secret store, and you accept the duties that come with it: storage, rotation, access control, audit, revocation.

Most teams start at level 3 because it is the level with a product attached to it. The engineering is at levels 1 and 2.

The decision is almost entirely about rotation

If nothing rotates the value, Parameter Store SecureString does the same job for nothing. Fifty secrets in Secrets Manager is $240 a year to store strings — and teams routinely fill it with values that never change, and with configuration that was never secret at all.

Parameter Store for configuration and for secrets nobody rotates. Secrets Manager when rotation is real.

Reading one

The second lock, again

Lesson 3.2's rule reappears unchanged: a value encrypted with KMS needs permission on two resources — the secret, and the key.

{ "Effect": "Allow", "Action": ["secretsmanager:GetSecretValue"], "Resource": "arn:aws:secretsmanager:us-east-1:739489595894:secret:prod/db-AbCdEf" }, { "Effect": "Allow", "Action": ["kms:Decrypt"], "Resource": "arn:aws:kms:us-east-1:739489595894:key/…" }

Grant the first without the second and the denial names KMS — the same confusing failure that opened Lesson 3.2, from a different service.

The six random characters

That -AbCdEf suffix is generated by AWS and is not stable. Delete and recreate the secret and it changes, and every policy naming the full ARN silently stops matching. Write secret:prod/db-* instead. This is a common and confusing breakage: nothing in your policy changed, and access stopped.

Fetch once, not per request

GetSecretValue on every request costs money, adds a network round trip to your latency, and will eventually throttle. Read at startup, or cache with a TTL using the AWS caching library or the Lambda extension. A secret that rotates every 30 days does not need fetching ten thousand times an hour.

The traps

Four ways to leak a secret you stored correctly

1. Reading it into Terraform

data "aws_secretsmanager_secret_version" writes the plaintext into your state file. Now apply everything you learned in Module 3: your state lives in a versioned bucket, so the plaintext is preserved in every historical version, and nothing in that bucket expires noncurrent versions. One careless data block and the secret is permanently archived, in multiple copies, in a place you cannot fully clean without deleting versions by id.

Create the secret in Terraform with a placeholder; set the real value out of band; let the application read it at runtime. Terraform should know the secret's name, never its value.

2. Putting it in an environment variable at deploy time. ECS task definitions and Lambda both support secret references resolved at runtime. Embedding the literal value means it appears in the console, in CloudTrail, and in every describe-task-definition any reader can run.

3. Syncing it into a Kubernetes Secret without thinking. Two options on EKS, and they differ in posture:

External Secrets Operatorsyncs into a Kubernetes Secret — convenient, but those are base64 in etcd and readable by anything with RBAC on that namespace
Secrets Store CSI drivermounts values as files in the pod; no Kubernetes Secret object exists. Stronger, slightly more setup

4. Assuming deletion is immediate. Secrets Manager holds a deleted secret for a recovery window of 7 to 30 days — the same design as KMS key deletion, for the same reason. --force-delete-without-recovery skips it, and there is no undo.

Rotation

Why rotating does not cause an outage

Rotation does not overwrite a value. It uses staging labels — pointers that move between versions:

AWSCURRENT the version applications get today AWSPENDING the new value, created and tested but not yet promoted AWSPREVIOUS the one before — still valid, briefly

The rotation function creates the new credential as AWSPENDING, tests that it actually works, and only then moves AWSCURRENT to point at it. The old value becomes AWSPREVIOUS and keeps working for a window.

That third label is the whole trick

Without it, every in-flight connection holding the old credential fails the instant the value changes. With it, both are briefly valid, so a caller that cached the old value keeps working until it next refreshes — and an application that re-reads the secret on an auth failure recovers on its own.

Same principle as attaching KnockOnly before detaching AdministratorAccess in Lesson 2.5, and copy-before-delete in Lesson 3.1: never create a window where the old thing is gone and the new thing is unproven. Fourth appearance in this course.

Rotation, mechanically

AWS changes the database too — not just the stored string

The common misunderstanding is that Secrets Manager generates a new value and leaves you to apply it wherever the old one was. It does not. The rotation function changes the password in the database itself and then records it. Both sides, one sequence.

1

createSecret

Generate a new password and store it as AWSPENDING. The database is untouched at this point — nothing has changed for anyone.

2

setSecret — the step people miss

Connect to the database and actually change the password. This requires a credential permitted to do so, which is why there are usually two secrets: the one being rotated, and a master secret holding an admin user that does the rotating.

3

testSecret

Connect using the AWSPENDING value and prove it works.

4

finishSecret

Move AWSCURRENT to the new version. The old value becomes AWSPREVIOUS and keeps working briefly.

A failed rotation is a non-event

If step 3 fails, step 4 never runs. AWSCURRENT still points at the old value, the old password still works, and nothing broke. The test step is what makes rotation safe to run unattended — and it is the same shape as every other version of this principle in the course: prove the new thing before retiring the old one.

What your application has to do

Read the secret at runtime. Then rotation is invisible — the next refresh picks up the new value. What breaks is reading it once at deploy time into an environment variable: rotation changes the database out from under a process that will never look again.

cache with a TTL // do not call GetSecretValue per request re-read on auth failure // if the DB rejects you, refresh once and retry one source of truth // no copies in env vars, config files, other services

That last line is the real answer to "then I update it wherever I have it?" — if the password exists in four places, rotation breaks four things. The purpose of a secret store is that it exists in one, and everything reads from there.

Two strategies

single user

Password changed in place

One database user. There is a brief window where a connection opened with the old password is rejected. AWSPREVIOUS plus a retry covers it, but the window is real.

alternating users — production

Two users, swapped

Two users with identical permissions, say app and app_clone. While one serves traffic, the other's password is rotated, then AWSCURRENT switches. The credential in active use is never mid-change, so the window disappears.

Where it actually goes wrong

The Lambda cannot reach the database. The single most common rotation failure. Your database sits in a private subnet; the rotation function runs in Lambda's own network unless you attach it to your VPC, give it a security group, and let the database accept it. Rotation then fails on a schedule while everything still looks configured.

The credential cannot be changed by an API call. AWS ships rotation functions for RDS, Aurora, Redshift and DocumentDB because those expose a password-change API. A partner's API key that requires emailing their support desk cannot be rotated on a schedule by any software. This is why "we rotate every 90 days" is so often a policy nobody implements — and why eliminating a secret is worth more than rotating one.

The common real case

What if the database is not in AWS?

A VPS at another provider, a legacy server, a partner's system. Secrets Manager does not know or care where your database lives — it stores a string. Rotation is a separate, optional feature, and it is just a Lambda function. AWS ships ready-made rotation functions for RDS, Aurora, Redshift and DocumentDB because it knows those APIs. For anything else, you write it.

OptionWho changes the database passwordEffort
no rotationyou, by handnone — Secrets Manager is purely a store
custom rotation Lambdathe function you wrotereal, and the networking is the hard part
Parameter Store insteadyou, by handnone, and free

So the direct answer: if you do not enable rotation, yes — you change the password on the server yourself and then update the secret yourself. Secrets Manager still earns its place as the one source of truth your application reads from. It simply is not automating the change.

Why automating it is usually the wrong call here

For RDS, the rotation Lambda and the database share a VPC. For a server elsewhere, the Lambda has to reach it, and both routes are unpleasant:

Expose the database port to the internet and restrict by source address — except Lambda's egress addresses are dynamic unless you place the function in a VPC and route it through a NAT Gateway for a fixed IP. That NAT Gateway costs roughly $32 a month, to rotate a secret that costs $0.40 a month.

Or build a tunnel — a VPN between AWS and the provider. More robust, more setup, and now you are operating network infrastructure in order to rotate one password.

Eighty times the cost of the thing it automates, plus a component that fails silently. For a single external database, do not build it.

Manual rotation, done properly

You still get the safety of staging labels without any Lambda — they are only API calls. Combined with two database users, this is zero-downtime rotation on a calendar reminder:

# 1. change the password on the server yourself — ideally for the IDLE user of a pair # 2. store it as pending, not current aws secretsmanager put-secret-value --secret-id prod/db \ --secret-string '{"username":"app_clone","password":"…"}' \ --version-stages AWSPENDING # 3. test it from the application's point of view # 4. promote it aws secretsmanager update-secret-version-stage --secret-id prod/db \ --version-stage AWSCURRENT \ --move-to-version-id <new> --remove-from-version-id <old>

The architectural consequence, which is the real lesson

A database outside AWS removes levels 1 and 2 from the ranking entirely. No IRSA, no IAM database authentication, no AWS-managed rotation where nobody ever sees the password. You are forced to level 3 and inherit every duty that comes with it.

Where you run something determines which secret-management options exist at all. The VPS looked cheaper than RDS, and part of that difference has just become your operational problem. That second-order effect is worth naming out loud in an interview.

What to actually choose, for one external database

not rotating

Parameter Store SecureString

Same encryption, same runtime read, free. Does not start a meter for a feature you are not using.

careful manual rotation

Secrets Manager

For the version history and staging labels above. $4.80 a year is noise if you will genuinely use them.

rotation genuinely matters

HashiCorp Vault

Its database engine issues short-lived users on demand rather than rotating a long-lived password — closer to level 1 than anything AWS offers for a non-AWS database. The standard answer when the estate is not all in one cloud.

Hands-on · ~5 minutes · costs nothing

Prove the second lock, for free

Deliberately using Parameter Store, not Secrets Manager — it teaches the identical permission model and is free, where a Secrets Manager secret would start billing $0.40/month. Warm the session first: aws sts get-caller-identity --profile admin.

1

Confirm you have none

aws secretsmanager list-secrets --profile admin and aws ssm describe-parameters --profile admin — both empty. That empty output is the good result, not a missing step.

2

Create an encrypted parameter

aws ssm put-parameter --name /course/demo --value "not-a-real-secret" --type SecureString --profile admin — SecureString means KMS encrypts it, using the AWS-managed aws/ssm key by default.

3

Read it without decrypting

aws ssm get-parameter --name /course/demo --profile admin — you get ciphertext. Permission on the parameter alone gets you the envelope, not the contents.

4

Now decrypt it

aws ssm get-parameter --name /course/demo --with-decryption --profile admin — this call additionally needs kms:Decrypt. As role/admin you have it, so it works; a role holding only ssm:GetParameter would fail here and the error would name KMS. That is the second lock, demonstrated.

5

Clean up

aws ssm delete-parameter --name /course/demo --profile admin — immediate, no recovery window. Unlike Secrets Manager, and worth noticing the difference.

Check yourself

Four questions

From memory, without opening the lesson.

Your team wants to move 40 configuration values — feature flags, timeouts, a region name — into Secrets Manager "so they're all in one place". What do you say?

Two objections. One is arithmetic. The other is about what the word "secret" is supposed to mean, and what you lose when everything is one.

A policy grants secretsmanager:GetSecretValue on the exact secret ARN. It worked for months, then stopped — with no policy change. What happened?

Something about the ARN is not stable. Ask what would have had to happen to the secret itself.

Why does rotation need three staging labels rather than two?

Picture the moment the pointer moves, and ask what is happening to connections opened five seconds earlier.

A colleague adds a data "aws_secretsmanager_secret_version" block to read a database password in Terraform. Why is this worse on your state bucket specifically than on a bucket without versioning?

Work out where the plaintext ends up, then apply Lesson 3.3's finding about what your state backend does and does not expire.
