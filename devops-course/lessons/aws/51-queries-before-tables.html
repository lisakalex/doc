Queries Before Tables

In a relational database you model the data, then ask it anything. In DynamoDB you enumerate the questions first and derive the keys from them — because the keys decide which questions are cheap, every other question is a full table read, and you cannot change the keys afterwards.

terraform/main.tf:112 hash_key = email no sort key, no index dynamodb:Scan

Start with the failure

Your GET /users reads the whole table, every time

# app/services/dynamodb.py def list_users(self) -> list[dict]: items: list[dict] = [] response = self._table.scan() items.extend(response.get("Items", [])) while "LastEvaluatedKey" in response: response = self._table.scan(ExclusiveStartKey=response["LastEvaluatedKey"]) items.extend(response.get("Items", [])) return items

That while loop is the tell. It exists because a single read returns at most 1 MB, so the code walks the table a megabyte at a time and glues the pages together. With twelve users it is instant and free. With a hundred thousand it reads roughly 13 MB and makes thirteen round trips — on every request, for every visitor, to render one page.

And the permission was already granted, back in Module 2:

# terraform/main.tf — the app role Action = ["dynamodb:PutItem", "dynamodb:Scan", "dynamodb:GetItem"]

That Scan in an IAM policy is a fossil. Somebody needed a question the key schema could not answer, and the cheapest fix in the moment was a permission rather than a redesign.

The rule

A DynamoDB table answers the questions its keys were designed for. Every other question is a full table read — and no amount of filtering makes it cheaper.

What you actually declared

The key schema is a physical layout, not a constraint

Eight lines of Terraform, and most of them are types:

resource "aws_dynamodb_table" "users" { name = local.dynamodb_table billing_mode = "PAY_PER_REQUEST" hash_key = "email" attribute { name = "email" type = "S" } }

hash_key is Terraform's name for the partition key, and it does something a relational primary key does not: DynamoDB hashes the value and the result decides which physical partition the item is stored on. It is a placement decision, made per item, at write time.

A key can have a second part. The sort key does not affect placement — items sharing a partition key live together, ordered by sort key. That ordering is the entire reason ranges are cheap: “everything for this customer between March and June” is a contiguous read of one partition.

Three verbs, and only three

What you may ask, and what it costs

OperationRequiresReadsUse it for
GetItemthe exact partition key (and sort key, if there is one)one item“this user, by email”
Queryan exact partition key, plus an optional condition on the sort keyonly the matching items in one partition“this customer's orders since March”
Scannothingevery item, 1 MB at a timemigrations, exports, and admin jobs nobody waits on

The shape of the constraint is in the second row: Query cannot search for a partition key, only match one. There is no “find the partitions where…”. You must already know the value. Designing the key is therefore the same act as designing the question.

The fact that surprises everyone

A FilterExpression does not save you a single read unit. DynamoDB reads the items first and applies the filter afterwards, discarding what does not match. A filtered scan that returns three items out of a million costs exactly the same as reading the million. The response even tells you: ScannedCount is what you paid for, Count is what you got.

The same is true of ProjectionExpression — asking for two attributes instead of twenty reduces the bytes on the wire, not the bytes read. Capacity is computed from what was read from disk, never from what was returned to you.

Run it yourself · ~30 seconds · no AWS account

What the gap looks like with numbers on it

assets/scripts/access_patterns.py builds your own users table in memory, fills it with 5,000 users signed up across a year, and answers one product question twice.

uv run assets/scripts/access_patterns.py question: which of 5,000 users signed up since 2026-09-23? Scan + FilterExpression items read 5,000 <- every item in the table items returned 108 read units 80 Query on a GSI keyed (signup_month, created_at) items read 108 items returned 108 read units 2.0 same answer, 40x the reads

Forty times, on a table small enough to fit in one page. The ratio is not the point though — the slope is. The scan grows with the table; the query grows with the answer. At 5,000 users it is 40×; at 100,000 users, with the same 108 results, it is 800×, and the scan has also become thirteen sequential round trips because of the 1 MB page limit.

Read units here are calculated the way DynamoDB calculates them: total bytes read, rounded up to 4 KB, halved because scans and queries are eventually consistent unless you ask otherwise. The script prints its working.

Your table, honestly

The questions you can and cannot afford

Product asks for…On your table today
a user by email addressGetItem one read, single-digit milliseconds
every user, for the admin listScan the whole table, paged
users who signed up this weekScan + filter — same cost as the whole table
the 20 most recent sign-upsScan everything, then sort in Python — there is no order to exploit
a user by their internal idScan + filter, because the id is not a key
a count of usersScan — DynamoDB has no cheap COUNT(*)

One row out of six is what the table was designed for. That is not a bug in the table — it is an accurate reflection of one decision made on one line, months ago: hash_key = "email". Everything else was never asked for, so it was never paid for.

The part with no undo

You cannot change a key schema

There is no ALTER TABLE. The partition key and sort key are fixed at creation, for the life of the table. Changing them means creating a new table, migrating every item, repointing the application, and deleting the old one — with the writes still arriving throughout.

Add later?LimitNotes
Partition / sort keynever—new table and a migration
Global secondary indexyes20 per tableown partition and sort key, own capacity, eventually consistent
Local secondary indexcreation only5 per tablesame partition key, different sort key
Non-key attributesanytime—the table is schemaless below the key

So the GSI is the escape hatch, and it is the reason a wrong key is survivable. It is not free: a GSI is a second copy of the projected attributes, written on every write to the base table, billed for its own storage and its own write units. Twenty indexes on a hot table is twenty multiples of your write bill.

Terraform will do this silently

Change hash_key in main.tf and terraform plan will show you forces replacement — which means destroy and create. On a DynamoDB table that is every item you have. This is the one place in your repo where reading the plan output carefully is not a nicety.

The method

Write the questions down first

The discipline is mechanical, and it happens before any Terraform. List every question the application will ask, with how often and how selective it is. Then, and only then, derive keys.

1

Enumerate the access patterns

“Get a user by email”, “list users newest first, 20 at a time”, “find a user by id”. Write them as sentences, not as tables. If you cannot name the question, you cannot design for it.

2

For each, name the one value you will always have

That value is a candidate partition key. For “get a user by email” it is the email. For “newest first” there is no such value — which is the signal that you need a bucket.

3

Give ranges a sort key

“Between these dates”, “the most recent N”, “starting with” — all of these are sort key conditions, and all of them require the partition key to be pinned first.

4

Check the spread before you commit

A partition key with few distinct values concentrates traffic on few partitions. The fix is usually a finer bucket — month rather than year — or a suffix that spreads writes across several partitions at the cost of querying each.

What that produces for this repo

# terraform/main.tf — same table, one index added resource "aws_dynamodb_table" "users" { name = local.dynamodb_table billing_mode = "PAY_PER_REQUEST" hash_key = "email" # unchanged — do not touch this line attribute { name = "email" type = "S" } attribute { name = "signup_month" type = "S" } attribute { name = "created_at" type = "S" } global_secondary_index { name = "by-signup-month" hash_key = "signup_month" # "2026-09" range_key = "created_at" # ISO 8601, so lexical order is chronological projection_type = "ALL" } }

Two points hide in that block. signup_month is a derived attribute — the application writes it, computed from the timestamp, purely so that something exists to partition on. That is normal and it is the trick: in DynamoDB you invent attributes whose only job is to be a key.

And created_at must be ISO 8601, because sort keys are compared as strings. 2026-09-30 sorts correctly; 30/09/2026 does not. Choosing the format is choosing whether ranges work.

The application side is then a three-line change — the pagination the API is missing comes along for free, because LastEvaluatedKey becomes the cursor:

# app/services/dynamodb.py def recent_users(self, month: str, limit: int = 20, start=None) -> dict: kwargs = { "IndexName": "by-signup-month", "KeyConditionExpression": Key("signup_month").eq(month), "ScanIndexForward": False, # newest first: descending sort key "Limit": limit, } if start: kwargs["ExclusiveStartKey"] = start return self._table.query(**kwargs)

Module 2, returning

Delete the permission and the mistake becomes impossible

Once the query exists, the last step is the one people skip:

# terraform/main.tf — the app role Action = ["dynamodb:PutItem", "dynamodb:GetItem", "dynamodb:Query"] # dynamodb:Scan removed Resource = [ aws_dynamodb_table.users.arn, "${aws_dynamodb_table.users.arn}/index/*", # a GSI is a separate resource ]

With Scan gone, the expensive mistake stops being a judgement call and becomes an AccessDeniedException in a pull request. This is the Module 2 idea used constructively: permissions are not only about attackers, they are about making the wrong thing fail loudly and early.

Note the second ARN. Queries against an index are authorised against table/users/index/by-signup-month, not against the table — a policy that names only the table denies every index read, with an error that mentions neither.

Hands-on · ~10 minutes · nothing costs money

Watch the counters yourself

Your AWS stack is torn down, so this runs against LocalStack, which the repo already has wired up.

1. Start it

docker compose --profile localstack up -d export AWS_ENDPOINT_URL=http://localhost:4566 AWS_DEFAULT_REGION=us-east-1 export AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test

2. Create the table you already have

aws dynamodb create-table --table-name users \ --attribute-definitions AttributeName=email,AttributeType=S \ --key-schema AttributeName=email,KeyType=HASH \ --billing-mode PAY_PER_REQUEST

3. Put a few users in, then ask for one

aws dynamodb put-item --table-name users --item \ '{"email":{"S":"a@example.com"},"created_at":{"S":"2026-09-30"}}' aws dynamodb get-item --table-name users \ --key '{"email":{"S":"a@example.com"}}' \ --return-consumed-capacity TOTAL

ConsumedCapacity of 0.5 — one eventually consistent read of an item under 4 KB. This is the only shape of request your table is designed for.

4. Now ask a question it was not designed for

aws dynamodb scan --table-name users \ --filter-expression "created_at >= :d" \ --expression-attribute-values '{":d":{"S":"2026-09-01"}}' \ --return-consumed-capacity TOTAL \ --query '{Scanned:ScannedCount,Returned:Count,Paid:ConsumedCapacity.CapacityUnits}'

Compare Scanned with Returned. On three items the difference is academic; the point is that Paid tracks the first number and not the second, and it will keep doing that for the next four years of sign-ups.

Check yourself

Four questions

A colleague says “the scan is fine, I added a filter expression so it only returns the ten rows we need.” What do you tell them, and what evidence do you show?

The filter runs after the read, not during it. DynamoDB reads every item, then discards the ones that do not match, and bills for everything it read. Ten returned rows out of a million cost the same as reading the million.

The evidence is in the response they already have: run it with --return-consumed-capacity TOTAL and compare ScannedCount, Count and CapacityUnits. The capacity tracks ScannedCount. A high scanned count with a low count is the definition of an inefficient scan.

Which means the filter improved the payload and changed nothing about the cost or the latency, both of which grow with the table for as long as the code survives.

You need “the 20 most recent sign-ups”. Someone proposes a GSI with partition key "USER" — a literal constant on every item — and sort key created_at. It works perfectly in staging. What happens in production, and what would you do instead?

Every item in the table lands in one partition, because the partition key has exactly one value. That single partition now absorbs every write to the index and every read of it, and a partition has a hard throughput ceiling regardless of what the table is provisioned for. In staging, with three writes a minute, nothing shows. In production it throttles — and the throttling is invisible in the table's own metrics, because it is the index that is hot.

Instead, bucket the partition key so it has many values but few enough to query: the month (2026-09) for a “recent” view, which is one query for this month and a second for last month when the window straddles a boundary. If a month is still too much traffic, go finer — day — or add a shard suffix and query the shards in parallel.

Which means the design question is never only “what do I need to look up”, it is “how many distinct values will this key have, and how evenly will traffic land on them”.

The product owner asks for user search by name, with partial matching. What do you say?

That DynamoDB cannot do it, at any price. Sort keys support begins_with, so prefix matching on a known partition is possible, but “contains”, fuzzy matching and relevance ranking are not operations the engine has. A scan with contains() would work at demo scale and is a full table read per keystroke.

The honest answers are: put the searchable copy somewhere built for it — OpenSearch, or a relational database — fed from DynamoDB Streams; or accept prefix-only search on a key you design for it. What you do not do is add the scan and revisit it later, because “later” is after the table has grown.

Which means this is the moment to say the quiet part: DynamoDB is the wrong database for search, and choosing it for the user table does not oblige you to use it for everything.

Terraform plan on the users table shows forces replacement. Walk through what you do, in order.

Stop. Do not apply. On a DynamoDB table, replacement means destroy and create: every item is gone, and Terraform will report success.

Then, in order: read the plan to find which attribute forced it — changing hash_key or range_key does, adding a global_secondary_index does not. Decide whether you actually need a new key schema or whether a GSI answers the question. If you genuinely need it, treat it as a migration, not an apply: create the new table alongside, backfill it, dual-write, cut the application over, then remove the old one. And add lifecycle { prevent_destroy = true } to the table so the next person gets an error instead of an outage.

Which means the safeguard belongs in the code before you need it, not in the care of whoever happens to read the plan that day.
