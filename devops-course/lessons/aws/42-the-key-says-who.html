The Key Says Who

Nearly every other resource in AWS can be governed by IAM alone. A KMS key cannot. The key carries its own policy, that policy is mandatory, and it is the only reason your IAM permissions on the key mean anything at all.

terraform/main.tf:29 no explicit policy → default policy kms:ViaService aws:s3:arn

Start with the failure

You granted kms:Decrypt in IAM and the call still fails

# the IAM policy is unambiguous { "Effect": "Allow", "Action": ["kms:Decrypt"], "Resource": "arn:aws:kms:us-east-1:1111:key/8b1f…" } # and the call is still refused An error occurred (AccessDeniedException) when calling the Decrypt operation: The ciphertext refers to a customer master key that does not exist, does not exist in this region, or you are not allowed to access.

In Lesson 3.2 you met the shape of this: two locks, the bucket and the key. This lesson is about the second lock's own policy — where it lives, why it is unlike every bucket policy you have written, and how to write one that is tighter than the default your repo is using today.

The rule

IAM never grants access to a KMS key on its own. The key policy decides — and a key policy that says nothing about IAM means IAM says nothing about the key.

The difference that catches everyone

Optional on a bucket, mandatory on a key

S3 bucket policyKMS key policy
Exists by default?noalways — every key has one
If it is absent or silentIAM alone decides; access still worksnobody has access, including account admins
Can IAM grant access alone?yes, same accountno — only if the key policy delegates to IAM
Can you lock yourself out?awkwardly, and the bucket owner can recoveryes, permanently — it becomes a support case

That last row is not a rhetorical flourish. A key whose policy grants nothing to anyone cannot be edited, used or rescued by you, because editing the policy is itself an action the policy must allow. This is why AWS puts a delegation statement in the default policy and why you should think hard before removing it.

What your repo actually has

The most misread line in AWS

aws_kms_key.avatars has no policy argument, so the key was created with the AWS default key policy. It is one statement:

{ "Sid": "Enable IAM User Permissions", "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:root" }, "Action": "kms:*", "Resource": "*" }

Read the principal correctly

:root here does not mean the root user. It names the account, and it means: “IAM policies in this account are allowed to govern this key.” It grants no access by itself. Every principal still needs an IAM policy saying kms:Decrypt — which is exactly what your app role has.

So access to your avatars key is currently decided in two places, and both must say yes:

On the key

The default policy: this account's IAM may govern the key. Broad, and identical on every key anyone creates without thinking about it.

In IAM

Your app role's inline policy: kms:Decrypt and kms:GenerateDataKey on this key's ARN. Specific, and the only thing narrowing access today.

This is the standard, supported arrangement — not a bug. But it means anyone who can attach an IAM policy in this account can grant themselves use of the key. On a key that mattered, you would say more on the key itself.

Writing a real one

Four conditions that do most of the work

ConditionWhat it pins down
kms:ViaServicethe key may only be used through a named service in a named region, e.g. s3.us-east-1.amazonaws.com — a stolen credential cannot call Decrypt directly
kms:EncryptionContext:kthe key may only be used for a particular payload — S3 sets aws:s3:arn on every call
kms:CallerAccountwhich account the caller belongs to — the cross-account boundary
kms:GrantIsForAWSResourceallows CreateGrant only when an AWS service is doing it on your behalf

The hardening this repo could take today

# terraform/main.tf — an explicit policy on aws_kms_key.avatars { "Sid": "App role may use the key, but only through S3, only for this bucket", "Effect": "Allow", "Principal": { "AWS": aws_iam_role.app_role.arn }, "Action": ["kms:Decrypt", "kms:GenerateDataKey"], "Resource": "*", "Condition": { "StringEquals": { "kms:ViaService": "s3.us-east-1.amazonaws.com", "kms:EncryptionContext:aws:s3:arn": "arn:aws:s3:::your-bucket" } } }

With both conditions in place, the app role's credentials are worth strictly less to an attacker: they can decrypt avatars by reading them from this bucket, and they cannot use the key for anything else — no direct Decrypt of a blob they brought with them, no other bucket, no other region.

The trap in that second condition

S3 sets the encryption context to the bucket ARN when bucket_key_enabled = true, and to the object ARN when it is false. Your repo has bucket keys on, so the value above is right today — and the day someone turns bucket keys off to debug something, every upload and download fails with an access-denied error that mentions neither S3 nor the setting they changed.

Which is the Module 3 pattern again: two things that look like one. “The encryption context” is really two different values depending on a cost setting three lines away in the same file.

The third way in

Grants, and why AWS services use them

A grant is a small, revocable permission attached to a key, created programmatically rather than written into the policy. AWS services create them constantly on your behalf: attach an encrypted EBS volume and the service takes a grant on your key for the life of that volume.

Key policyGrant
Shapeone JSON document on the keymany small objects, one per delegation
Created bya human, in Terraformusually a service, via CreateGrant
Scopewhatever you writespecific operations, optionally pinned to an encryption context
Removed byediting the documentRevokeGrant by an admin, or RetireGrant by the grantee
Consistencyimmediateeventually consistent — use the returned grant token to act immediately

For your repo, no grants exist and none are needed: S3 works through the key policy and IAM. Know them because list-grants on an unfamiliar key is where you discover who else can really use it — a question the policy alone does not answer.

Where the bits came from

Origin: AWS's 32 bytes, or yours

The runbook below turns on one attribute you have not met yet. Every key has an Origin, fixed when the key is created and never changeable afterwards, recording where its key material came from:

# the key in this repo aws kms describe-key --key-id alias/avatars \ --query 'KeyMetadata.[Origin,KeyState]' --output text AWS_KMS Enabled

Four values exist: AWS_KMS, EXTERNAL, AWS_CLOUDHSM and EXTERNAL_KEY_STORE. The last two are custom key stores, where the material lives in a CloudHSM cluster of yours or in an external HSM reached through a proxy. They are rare, this course does not use them, and everything below is about the other two.

AWS_KMS — the default, and what you have

AWS generated the material inside its HSM fleet. No API returns it in plaintext: not to you, not to AWS staff, not through a support case. That is the entire reason the first row of the table below says no — there is no export path for the material to leak through, so a leak of it is not a thing that can happen. When somebody says “our KMS key has leaked”, this is almost never what occurred, and establishing that in the first five minutes saves you from cutting a new key for nothing.

EXTERNAL — bring your own key

You generate the 256 bits yourself and hand AWS a copy. Creating the key gives you a key with no material at all, in state PendingImport and unusable, until you fill it:

# 1. a key with no material yet aws kms create-key --origin EXTERNAL # 2. AWS hands back a public wrapping key and a single-use import token aws kms get-parameters-for-import --key-id "$KEY" \ --wrapping-algorithm RSAES_OAEP_SHA_256 --wrapping-key-spec RSA_4096 # 3. wrap your own 32 bytes with that public key, then hand them over aws kms import-key-material --key-id "$KEY" \ --encrypted-key-material fileb://wrapped.bin \ --import-token fileb://token.bin \ --expiration-model KEY_MATERIAL_DOES_NOT_EXPIRE

People do this to prove the entropy came from a source they control, to carry an already-established key into AWS, or to keep an escrow copy outside AWS for disaster recovery. All three reasons are the same fact: you hold the original. That copy — on a laptop, in a vault, on paper in a safe — can be stolen, and if it is, every data key it ever wrapped can be unwrapped offline, with no account, no credentials and no KMS involved. Which is why row two of the table is the one row where both answers are yes.

The one thing imported material buys you

An instant, reversible off switch. Deleting the material drops the key to PendingImport in seconds and every decrypt stops, yet importing the identical bytes later brings all of it back. Nothing with AWS_KMS origin behaves like that: scheduled deletion is neither instant nor undoable once the window closes. Lesson 4.1's warning about PendingDeletion being an outage nobody can buy their way out of is about your keys, not about these.

Rotation is not the same operation across the two either, which matters for the promise you make an auditor. Automatic rotation exists only for symmetric encryption keys with AWS_KMS origin. Imported material rotates on demand only, and “on demand” means you generate the next 32 bytes, import them as new material, and then call RotateKeyOnDemand to make them current. Asymmetric keys, HMAC keys and anything in a custom key store get neither, and must be rotated the manual way from Lesson 4.1 — a new key and a pointer change.

In Terraform these are two different resources. aws_kms_key always means AWS_KMS origin; there is no argument to change it. Imported material is aws_kms_external_key with key_material_base64, and that argument lands your key material in state, so it comes from a variable at apply time or it does not get committed at all.

Runbook

“The key has been compromised”

Someone says this to you in an incident channel. Before you create a new key, establish which of four different things actually happened. Only two of them are cryptographic compromises, and only those two mean any data has to be re-encrypted.

What leakedPossible?Is stored ciphertext compromised?
CMK material, AWS_KMS originno no export path exists; it is generated in an HSM and never leaves in plaintextno
Imported material, EXTERNAL originyes you hold the source copyyes
A data key — memory, logs, a heap dumpyes the realistic caseyes, for what it wrapped
Credentials of a principal with kms:Decryptyes the most common of allno — but it can be used

What each one actually calls for

1

Credentials: it was never a key problem

Nothing about the key changed; someone can call Decrypt as you. Every one of those calls is correctly authorised and appears in CloudTrail under that principal's identity, so nothing looks wrong on the key side — which is why this one is usually found from the credential end, not the KMS end. Revoke the session, remove the access, rotate the credential, and tighten the key policy: ViaService above would have made those credentials far less useful, since they would work only through S3. A new key achieves nothing, because the compromised principal has to be granted the new one for your application to keep working, and the attacker is that principal.

2

A data key: re-encrypt the objects, not the key

The wrapped copy beside the object is unchanged, so the leaked key opens that object forever. Rotating or replacing the CMK does nothing for it. Copy the affected objects onto themselves so they get fresh data keys, and remember the blast radius from Lesson 4.1: with bucket keys on, one leaked key can cover everything written in a time window.

3

Imported material: one move nobody else has

DeleteImportedKeyMaterial makes the key unusable immediately without deleting the key, and you can re-import later. Do that first, then plan the migration.

4

Only then, the new key

Create it, point new writes at it — the ARN in the bucket config, not just the alias — re-encrypt everything you intend to keep including old object versions, then watch CloudTrail for Decrypt calls on the old key until it goes quiet. Disable it as a dress rehearsal. Schedule deletion last, with the full 30-day window.

The sentence that reframes the incident

Deleting the old key does not un-leak anything. If material really escaped, every copy of the ciphertext the attacker already holds stays readable without your account, your permissions or KMS. Deletion protects the copies you still hold. The exposure already happened — so the real work is what was in those objects, who has it now, and what must be rotated downstream.

Hands-on · ~5 minutes · read-only

Read your own key's policy

1. The policy as it stands

BUCKET=$(terraform -chdir=terraform output -raw s3_bucket_name) ALIAS="alias/${BUCKET}-avatars" aws kms get-key-policy --key-id $ALIAS --policy-name default \ --query Policy --output text | python3 -m json.tool

One statement, principal …:root, action kms:*. You are looking at the default policy, and now you can say precisely what it does and does not grant.

2. Who is actually allowed, then?

aws iam get-role-policy --role-name prima-app-role --policy-name prima-app-policy \ --query 'PolicyDocument.Statement[?contains(to_string(Action), `kms`)]'

The narrowing lives here, in IAM — not on the key. That asymmetry is the lesson.

3. Does anyone hold a grant?

aws kms list-grants --key-id $ALIAS --query 'Grants[].{Grantee:GranteePrincipal,Ops:Operations}'

Expect an empty list. On a key you inherit from someone else, this is the first command to run, because grants are invisible in the policy document.

4. Who has been using the key?

aws cloudtrail lookup-events \ --lookup-attributes AttributeKey=EventName,AttributeValue=GenerateDataKey \ --max-results 5 \ --query 'Events[].{Time:EventTime,Who:Username,Src:EventSource}'

This is the audit trail you bought by choosing a customer-managed key in Lesson 3.2, and it is the evidence you would use before deleting a key in the runbook above.

Check yourself

Four questions

An engineer removes the “Enable IAM User Permissions” statement from a key policy, leaving only a statement for one deleted role. What is the state of that key?

Unusable and unmanageable. No principal can encrypt, decrypt, or edit the policy — and editing the policy is itself governed by the policy, so there is no way back from inside the account. Account administrators cannot override it: unlike an S3 bucket, there is no owner fallback.

The data is not gone, but it is unreadable until AWS Support intervenes. This is the one AWS mistake that turns into a support ticket rather than a fix.

Your key policy grants kms:* to arn:aws:iam::111122223333:root. A colleague says “that means only the root user can use the key”. Correct them.

It names the account, not the root user, and it grants no access to anyone by itself. It delegates: IAM policies in that account are now allowed to decide who may use the key. Without an IAM policy naming the key, a principal still gets nothing.

The practical consequence is the opposite of what they fear: not “only root”, but “anyone who can write IAM policy in this account”.

You pin the key policy with kms:EncryptionContext:aws:s3:arn set to the bucket ARN. Months later someone sets bucket_key_enabled = false. What happens?

Every upload and download starts failing with access denied from KMS. Without bucket keys, S3 sends the object ARN as the encryption context, so the condition no longer matches, and the key refuses every call.

Nothing in the error mentions bucket keys, and the change that caused it was made for cost or debugging reasons in a different part of the file. If you use this condition, it belongs in a comment next to bucket_key_enabled, tying the two lines together.

An incident channel says “our KMS key leaked”. What do you ask, and what do you do first?

Ask what leaked, because the phrase covers four different incidents. If it is a CMK with AWS_KMS origin, the material cannot have leaked — there is no export path, so the real event is something else. If it is credentials, the key is fine and the fix is revoking access. If it is a data key, the affected objects need re-encrypting. Only imported material is a genuine key-material leak, and it has its own instant containment in DeleteImportedKeyMaterial.

First action either way: contain access — revoke the credential, or disable the key if the outage is acceptable. New key, re-encryption, then deletion, in that order, and deletion only once CloudTrail shows the old key has gone quiet. And say the uncomfortable part out loud: deleting the key does not un-leak data anyone already copied.
