Rotation Rotates Nothing

Your repo has enable_key_rotation = true on the CMK that protects every avatar in the bucket. This lesson is about what that line does, what it very deliberately does not do, and why both halves are worth knowing before an auditor asks.

terraform/main.tf:29 aws_kms_key.avatars rotation period 365 days deletion window 7 days

Start with two sentences people say

Both of these are wrong, and wrong in the same way

Heard in a security review

“We rotate the KMS key every year, so if last year's key material leaked, last year's objects are safe now.”

Heard in a change review

“Don't turn rotation on. We'd have to re-encrypt two million objects and update everything that references the key.”

One person thinks rotation does more than it does. The other thinks it costs more than it costs. They have made the same mistake: treating the key and the key material as one thing. They are two things, and almost everything surprising about KMS rotation follows from separating them.

The rule

Rotation creates new key material. It does not create a new key, and it does not touch a single byte of your data.

The mechanism

One key, a growing stack of materials

A customer-managed key is a logical resource: an ARN, a key policy, a state, an alias or two — and, hanging off it, a list of cryptographic materials. Rotation appends to that list. Everything else about the key stays exactly as it was.

This is why aws kms decrypt takes no --key-id for a symmetric key: the ciphertext blob names its own key and its own material version. Self-describing ciphertext is what makes rotation invisible.

What rotation changes, exhaustively

ThingAfter rotation
Key ARN / key IDidentical — nothing in Terraform, IAM or the bucket config refers to a material version
Key policy, alias, tags, stateidentical
Existing objectsuntouched; not re-encrypted, not rewritten, not even read
Existing wrapped data keysuntouched; still unwrappable by the retained older material
New writeswrapped with the new material from the moment it is live
Your application codeno change — this is the entire design goal

So the change-review objection collapses: enabling rotation on a bucket holding two million objects is a metadata flag. There is no sweep, no migration, no downtime, no code change.

The uncomfortable half

Old material is kept forever, by design

AWS KMS retains every version of the material for a key with AWS_KMS origin, and deletes it only when you delete the key itself. That is what makes 2024's objects readable in 2030 without a migration — and it is also what the security review sentence gets wrong.

Say this out loud once

Rotation does not retire old material. It adds new material. Nothing about rotation makes older ciphertext harder to read than it was yesterday.

So when someone asks “what does annual rotation protect us from?”, the honest answer is narrow:

ThreatDoes rotation help?
Key exhaustion — too much ciphertext under one keyyes but a CMK only ever wraps 256-bit data keys; exhaustion is already a non-issue
A compliance rule that says “rotate annually”yes this is the real reason most keys have it on
A leaked data key from your app's memoryno the wrapped key beside the object never changes; the leaked copy decrypts that object forever
A key policy that grants too muchno policy is a separate control surface
A compromised IAM principalno it is still allowed to call Decrypt
“Make last year's data unreadable”no only key deletion does that, and it is all-or-nothing

The AWS documentation states the sharp version of this in one line: “Key rotation will not mitigate the effect of a compromised data key.” Rotation is hygiene and paperwork. It is not a containment tool.

The containment tool you already met

In Lesson 3.2 you worked out that disabling the CMK makes every object in the bucket unreadable instantly, with no sweep. That is still the fastest blast-radius control you have, and it is reversible — which is exactly what rotation is not, and what deletion is not either.

Four states, one of them final

Enabled, disabled, pending deletion, gone

StateCan decrypt?Rotates?Reversible?
Enabledyeson schedule—
Disabledno, everything fails closedno; a missed rotation runs as soon as you re-enableyes, instantly
PendingDeletionnono; rotation status reads false and cannot be changedyes — cancel-key-deletion restores the key and its rotation setting
Deletedno, permanently—never

Deleting a KMS key destroys every material version at once, and every object wrapped under any of them becomes permanently unreadable. It is the only truly irreversible action you have met in this course — worse than an S3 delete, which versioning can undo, and worse than a bucket delete, which at least requires the objects to be gone first.

A design critique of your own repo

deletion_window_in_days = 7 is commented as minimising the billing tail on terraform destroy, which is a sound choice for a teaching account you tear down often. For anything holding real data, take the 30-day maximum: the window is your entire margin for noticing the mistake, and it costs the same either way.

When automatic rotation is not enough

Manual rotation, and the alias trap

Automatic rotation only works on symmetric KMS-generated keys. For asymmetric keys, HMAC keys, keys in a custom key store — or when a rule genuinely requires the old material to stop existing — you rotate manually: create a new key, point new writes at it, re-encrypt what matters, and only then schedule the old key for deletion.

1

Create the new key and move the alias

The alias is a pointer. Moving alias/<bucket>-avatars to the new key changes what future alias-based calls resolve to.

2

Check what actually references the key

Your bucket's default-encryption config is written with kms_master_key_id = aws_kms_key.avatars.arn — the ARN, not the alias. Moving the alias changes nothing for this bucket until that line changes too.

3

Re-encrypt deliberately

Nothing re-encrypts itself. A server-side copy of each object onto itself rewraps it under the new key — and you pay the request charges from Lesson 3.3 to do it.

4

Keep the old key alive until nothing needs it

Any object still wrapped under the old key dies with it. Old versions in a versioned bucket count.

Manual rotation is the expensive one: it is the only variant that actually re-encrypts data, and the only one that can make old ciphertext unreadable. That is the trade you are making, not “better rotation”.

Cost, since Module 3 trained you to ask

Rotation's bill is bounded; requests are not

KMS charges a monthly fee per key, and a further monthly fee for the first and second rotation of the material. After the second rotation the storage charge stops growing — a key rotated ten times costs the same as one rotated twice. Set against that, per-request charges scale with traffic forever, which is why bucket_key_enabled = true from Lesson 3.2 saves far more than rotation ever costs.

Connect it to 3.3

The Module 3.3 rule was that the surprising money is in requests and floors, not in stored bytes. KMS is the same shape: the key fee is a rounding error, the GenerateDataKey calls are the bill.

Hands-on · ~6 minutes · read-only apart from two cheap API calls

Ask your own key what it has been doing

1. What kind of key is it, and what state is it in?

# the alias is built from the bucket name in terraform/main.tf:36 BUCKET=$(terraform -chdir=terraform output -raw s3_bucket_name) ALIAS="alias/${BUCKET}-avatars" aws kms describe-key --key-id $ALIAS \ --query 'KeyMetadata.{State:KeyState,Spec:KeySpec,Origin:Origin,MultiRegion:MultiRegion,Manager:KeyManager}'

Expect Enabled, SYMMETRIC_DEFAULT, AWS_KMS, false, CUSTOMER. The last two matter: KMS-generated symmetric material is exactly the case where automatic rotation is available.

2. Is rotation on, and when does it next fire?

aws kms get-key-rotation-status --key-id $ALIAS

KeyRotationEnabled: true comes from your Terraform. RotationPeriodInDays is 365 because you did not set one, and NextRotationDate is measured from the day rotation was enabled, not from the day the key was created.

3. How many materials exist so far?

aws kms list-key-rotations --key-id $ALIAS

Almost certainly an empty list: the key is younger than a year, so it still has only its original material. Worth seeing empty now, so the shape is familiar when it is not.

4. Prove the bucket stores the ARN, not the alias

aws s3api head-object --bucket $BUCKET --key <some-object> \ --query '{Enc:ServerSideEncryption,Key:SSEKMSKeyId,BucketKey:BucketKeyEnabled}'

You get aws:kms, a full arn:aws:kms:…:key/… and true. No alias, and no material version — the version lives inside the wrapped data key, which S3 never shows you.

5. Watch a ciphertext name its own key

# two API calls, well under a thousandth of a cent aws kms encrypt --key-id $ALIAS --plaintext "$(echo -n hello | base64)" \ --query CiphertextBlob --output text | base64 -d > /tmp/blob.bin # note what is missing from this command: --key-id aws kms decrypt --ciphertext-blob fileb:///tmp/blob.bin \ --query '{Key:KeyId,Plaintext:Plaintext}' --output json

KMS returns the key ARN it used, because the blob told it. That single property is what lets rotation happen behind your back without breaking a single reader.

6. Confirm the source of truth

grep -n 'enable_key_rotation\|deletion_window\|kms_master_key_id' terraform/main.tf

Three lines, three decisions: rotate annually, keep a 7-day escape hatch, and bind the bucket to this key by ARN.

Run it yourself · no AWS account needed

Envelope encryption, by hand

If “the same key twice” still feels like words rather than a mechanism, run this. The CMK is a local key standing in for one inside KMS; every other step is what S3 and KMS actually do. It needs no account, which matters when the stack is torn down.

uv run assets/scripts/envelope.py
── PutObject ───────────────────────────────────────────── data key (Plaintext) 5a2d0edb55a67edc483a4c436a220878… (32 bytes) data key (CiphertextBlob) f804d1a633f5bfdf13696dae05283eb9… (60 bytes) ^ the SAME 32 bytes: usable, and sealed under the CMK object, encrypted 8e719b8fb5e1072a5b525d11bbb5f260… (94 bytes) stored in the bucket: the ciphertext + the sealed key never stored anywhere: the plaintext data key ── GetObject ───────────────────────────────────────────── data key, recovered by KMS 5a2d0edb55a67edc483a4c436a220878… (32 bytes) object, decrypted b'a 5 MB avatar, pretend…'

The two highlighted values are identical. That is what GenerateDataKey returning “the same key twice” means, made literal: 32 random bytes, handed back once usable and once sealed under the CMK. The sealed form is 60 bytes rather than 32 because sealing adds a nonce and an authentication tag — an envelope is bigger than the letter inside it.

1

Mint 32 random bytes

That is all a data key is. Enough for AES-256, and nothing more magic than that.

2

Seal a copy under the CMK

“Wrapped” means encrypted with another key. This copy can travel and be stored; only KMS can open it.

3

Encrypt the object with the usable copy

Your bytes never go near KMS. This is why a 4 KB request limit can protect petabytes.

4

Destroy the usable copy

The single line that makes the whole design work. Keep it and the CMK is decoration.

5

Store ciphertext and sealed key together

To read it back, S3 hands the sealed copy to KMS, gets the usable one, decrypts, and forgets it again.

Every rule in this lesson falls out of those five steps

RuleWhy, from the steps above
Disabling the CMK is instant and totalstep 5 becomes impossible. The sealed copies are still there and nothing can open them — no sweep, no re-encryption
Rotation changes nothing already writteneach object's sealed copy was sealed under the old material, which KMS retains, so it still opens
A leaked data key cannot be fixed at the CMKthe holder has the output of step 1. They skip steps 2 and 5 entirely — no KMS, no account, no permissions. Only giving the object a different data key helps

The script ends with an experiment: comment out the line that discards the plaintext data key and watch that nothing breaks — which is exactly why S3 discarding it is a decision rather than a side effect.

Check yourself

Four questions

Answer out loud before opening each one. As in Module 3, say the mechanism and the consequence — a half answer is the pattern that has cost you marks all course.

An auditor asks you to prove that objects written in 2024 can no longer be decrypted with 2024's key material. Rotation has been on since day one. What do you tell them?

That you cannot prove it, because it is not true. KMS retains every material version for the life of the key, and 2024's objects are still wrapped under 2024's material; KMS selects that version automatically on every read.

The only way to make that material stop existing is to delete the key, which would destroy every object under every version. If the requirement is real, it needs manual rotation: a new key, a re-encryption pass over everything you intend to keep, then scheduled deletion of the old key once nothing references it — old object versions included.

You are asked to enable rotation on a CMK protecting two million objects. What breaks, what must change, and what does it cost?

Nothing breaks and nothing must change. The key ARN, key policy, aliases and every reference in Terraform, IAM and the bucket configuration are unaffected, and no object is re-encrypted — new writes use the new material, old objects keep theirs.

The cost is one extra monthly key-storage fee after the first rotation and one more after the second, capped there. No request charges, because nothing re-reads the data.

A data key leaks in a heap dump from the app. You rotate the CMK immediately. What have you actually achieved, and what is the blast radius?

Close to nothing. The leaked key is plaintext and already outside KMS; the wrapped copy stored beside the object is unchanged, and the object it protects can be decrypted forever by anyone holding that leaked key. Rotation only changes what future data keys are wrapped with.

The real answer is to re-encrypt the affected objects so they get fresh data keys, and to treat the compromised principal as the incident.

The sting is the blast radius. With bucket_key_enabled = true, S3 takes a time-limited bucket-level key from KMS and derives object keys from it instead of calling GenerateDataKey per object. That is the 99% request saving from Lesson 3.2 — and it means a single leaked key covers every object written in that window, not one. The cost optimisation widened the blast radius. Both things are true, and you should be able to say both in the same breath.

On a Friday, someone runs schedule-key-deletion on the avatars key by mistake. Walk through what is happening right now, and what you do.

The key is in PendingDeletion and already unusable: every upload and download fails closed immediately, exactly as if it had been disabled. Rotation status reads false and cannot be changed while it is pending. The data is still intact — nothing has been destroyed yet.

Run aws kms cancel-key-deletion, then enable-key, because cancelling returns the key to Disabled, not Enabled. Service resumes with no data loss.

Then look at the window: this repo's deletion_window_in_days = 7 is the whole margin for catching it, and a mistake made on a Friday before a week off is a mistake you find too late. And the right follow-up is not just the window — it is a key policy that denies kms:ScheduleKeyDeletion to everyone who does not need it.

Carry these forward

Three sentences to memorise

Mechanism

Rotation adds material; it never removes any, and it never touches data.

Containment

Disabling is instant, total and reversible. Deleting is instant, total and final.

Trade

Bucket keys buy cheap requests with a wider data-key blast radius.
