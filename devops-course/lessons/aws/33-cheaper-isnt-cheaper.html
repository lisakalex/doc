Cheaper Isn't Cheaper

Every storage class below Standard advertises a lower price per gigabyte and attaches conditions that can make your bill go up. Your repo already avoids the worst of them — probably without you knowing why.

Durability is eleven nines for every class except One Zone-IA, which keeps one copy in a single Availability Zone. Losing that AZ loses the data. The name says so; people read it as "cheap Standard-IA" and do not notice.

The traps

Four charges that are not in the headline price

1

Minimum storage duration

Delete a Standard-IA object after 5 days and you are billed for 30. Deep Archive bills 180. Archiving anything short-lived costs more than leaving it in Standard, and the cheaper the class the longer the sentence.

2

Minimum billable object size — 128 KB

IA and Glacier bill every object as if it were at least 128 KB. A 10 KB file in Standard-IA is charged as 128 KB. This is the one that reverses the maths, and it is the trap your avatars would have walked into.

3

Retrieval fees

$0.01/GB for IA, $0.03/GB for Glacier Instant. Read the data twice a month and the cheaper class is no longer cheaper. Cold storage assumes the data is genuinely cold.

4

Transition requests

Each lifecycle transition is a billable request — roughly $0.01 per 1,000 into IA, $0.05 per 1,000 into Glacier. Moving two million small objects costs $20–$100 in requests alone, paid up front, before any saving begins.

Worked example · your bucket

Where "cheaper" goes backwards

Say the avatars bucket holds 100,000 avatars averaging 60 KB — about 6 GB. Your app caps uploads at 5 MB, but real profile pictures are small. Three options, one month:

Read the middle row again

The class advertised at half the price of Standard produces a higher bill. Nothing is wrong with the arithmetic — 100,000 objects of 60 KB are billed as 100,000 objects of 128 KB. The saving per gigabyte is real; you simply get charged for more than twice the gigabytes you have.

This is the most common S3 cost mistake after forgetting about egress, and it is made by people doing the responsible thing: moving old data to cheaper storage.

Your rule, examined

Why Intelligent-Tiering was the right call

rule { id = "transition-avatars-to-intelligent-tiering" status = "Enabled" filter { prefix = "avatars/" } transition { days = 90 storage_class = "INTELLIGENT_TIERING" } }

Intelligent-Tiering is the one class with no retrieval fee and no minimum storage duration. You pay a small monitoring charge — about $0.0025 per 1,000 objects per month — and S3 moves each object between tiers based on whether it is actually being read. Frequent → Infrequent after 30 days untouched, Archive Instant after 90, and straight back to Frequent the moment someone reads it, at no charge.

That matches your access pattern exactly, and your Terraform comment already reasoned it out: avatars are never overwritten, each upload gets a fresh UUID, so age alone does not mean an object is unused. An active user's avatar can be two years old and fetched daily. Any rule based on age would be guessing. Intelligent-Tiering does not guess — it measures.

And the 128 KB rule protects you here too

Objects under 128 KB are never auto-tiered by Intelligent-Tiering. They stay at the Frequent Access rate — the same price as Standard — and carry no monitoring charge. So for typical small avatars the rule does nothing at all: no saving, no penalty, just the one-off transition request.

Which means your rule earns its keep only on the larger uploads, the ones approaching your 5 MB cap. That is the honest assessment, and it is still the right rule, because the alternative — a Standard-IA transition — would have cost you money on every small object. You avoided the trap by choosing the class that has no trap.

The cheapest line in your Terraform

Aborting what never finished

rule { id = "abort-incomplete-multipart-uploads" status = "Enabled" filter {} abort_incomplete_multipart_upload { days_after_initiation = 7 } }

A multipart upload that fails halfway leaves its uploaded parts in the bucket. Those parts:

are billedas ordinary storage, every month, forever
are invisibleto aws s3 ls and to the console object list
have no ownerno key exists to delete, because the object was never completed

They can only be found with list-multipart-uploads and removed with abort-multipart-upload — or automatically, by the rule above. Accounts have discovered terabytes of them years later. Seven days is a sensible window: long enough for a legitimate retry, short enough that nothing accumulates.

The gap

Nothing expires on the versioned bucket

You proved this on Thursday. You uploaded one 20-byte file twice and deleted it twice, and the bucket kept four entries:

object demo/a/b/c.txt size=20 latest=False object demo/a/b/c.txt size=20 latest=False DELETE MARKER demo/a/b/c.txt latest=True DELETE MARKER demo/a/b/c.txt latest=False

Only an explicit delete-object --version-id on each removed them. Nothing in the state backend's Terraform would ever have cleaned them up, because it has no lifecycle configuration at all.

The rule that is missing

On a versioned bucket, aws s3 rm never frees storage — it adds a tombstone and keeps paying for the object underneath. The fix is a lifecycle rule, and it is two clauses:

rule { id = "expire-old-state-versions" status = "Enabled" filter {} noncurrent_version_expiration { noncurrent_days = 90 # delete superseded versions after 90 days newer_noncurrent_versions = 10 # …but always keep the 10 most recent } expiration { expired_object_delete_marker = true # tidy markers with nothing left under them } }

The second clause is the one people miss. When every version under a delete marker has expired, the marker itself remains — a tombstone for a grave with nothing in it. It costs almost nothing but it slows every listing and clutters every audit.

At 28,459 bytes across three versions, none of this matters on your bucket today. It matters on a bucket where Terraform state is written fifty times a day by CI, which is what the same backend looks like in a real team.

Why 90 days and 10 versions, rather than one or the other

noncurrent_days alone would delete every old version on a quiet bucket that has not been applied in three months — removing exactly the history you would want after a long gap. newer_noncurrent_versions alone would keep ten versions forever, even if the last nine were written in one bad afternoon. Together they mean: keep at least the last ten, and anything older than 90 days beyond that goes.

How to decide, generally

Three questions, in this order

first

How big are the objects?

Under 128 KB, every class below Standard bills you for 128 KB. Stop here — the answer is Standard or Intelligent-Tiering. Most "we should archive this" proposals die on this question.

second

How long do they live?

Shorter than the minimum duration and the cheaper class costs more. 30 days for IA, 90 for Glacier, 180 for Deep Archive.

third

Do you know the access pattern?

If yes, pick the class directly. If no — and you usually do not — Intelligent-Tiering measures it for you instead of making you guess.

Only after all three does the price per gigabyte matter. Starting from the price list and working backwards is how people end up with the middle row of the table above.

Hands-on · ~5 minutes · read-only, costs nothing

Check your own bucket

Warm the session first: aws sts get-caller-identity --profile admin. Everything below only reads. B=prima-tech-challenge-lisakalex-tfstate

1

Confirm the gap

aws s3api get-bucket-lifecycle-configuration --bucket $B --profile admin — expect NoSuchLifecycleConfiguration. That error is the finding.

2

Check for orphaned multipart uploads

aws s3api list-multipart-uploads --bucket $B --profile admin — empty output means none. On an old bucket with no abort rule, this is where the surprise lives.

3

See an object's storage class

aws s3api head-object --bucket $B --key senior-sre-tech-challenge/terraform.tfstate --profile admin — note that StorageClass is absent. Absent means STANDARD; S3 only names the class when it is something else.

4

Add up what versioning is actually storing

aws s3api list-object-versions --bucket $B --profile admin --query 'sum(Versions[].Size)' — you are billed for this number, not for the 181 bytes that aws s3 ls shows.

5

Price it

Multiply that total by $0.023 per GB per month. Then note that the KMS key beside it costs $1/month — the key protecting your state costs orders of magnitude more than the state. Which is the right lesson about optimising storage classes on small data.

Check yourself

Four questions

From memory, without opening the lesson. Two of these are arithmetic — do the arithmetic rather than guessing the direction.

A colleague proposes moving 5 million log files, average 8 KB, from Standard to Glacier Instant Retrieval to "save 80%". What happens to the bill?

Work out the billable size first, then the transition cost, then the minimum duration. Three separate charges, and only one of them is the price per GB.

Why does Intelligent-Tiering have no retrieval fee, when Standard-IA does? What is it charging for instead?

Both classes have to make money on data that is read more than expected. They chose different mechanisms — one charges for being wrong, the other charges a flat fee for watching.

Your CI runs terraform apply 50 times a day on a versioned state bucket with no lifecycle rules. What is the shape of the bill after a year, and what does aws s3 ls show?

Count the objects created, then ask which of them are visible. The gap between what you are billed for and what you can see is the whole point.

One Zone-IA is cheaper than Standard-IA and has the same eleven nines of durability. Why is it not the obvious default?

Eleven nines is a statement about a failure mode. Ask which failure mode, and what is different about where the copies live.
