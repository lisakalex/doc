Nothing Breaks Until It Restarts

In S3, the key is on the request path: make it unusable and the next download fails. Everywhere else in AWS it is on the lifecycle path — the volume keeps writing, the database keeps serving, and the failure waits for the next attach, restart or scale-out. That delay is the most dangerous property KMS has.

one key, many services grants request quotas multi-Region keys

Start with the failure

03:12, and the Auto Scaling group cannot launch anything

# capacity has been draining for an hour; every launch attempt fails aws autoscaling describe-scaling-activities --max-items 1 StatusCode: Failed Description: Launching a new EC2 instance. Status Reason: Client.InternalError StatusMessage: Client.InternalError: Client error on launch

Client.InternalError is the least helpful error message in AWS, and this is its most common cause: the instances have encrypted EBS volumes, and somebody disabled the KMS key at four o'clock the previous afternoon while tidying up unused resources. Nothing broke at four. Nothing broke at midnight. It broke when the group tried to launch an instance.

The rule

Outside S3, making a key unusable does not break anything that is already running. It breaks the next lifecycle event — and you do not choose when that happens.

Two places the key can sit

The request path and the lifecycle path

Everything in Module 4 so far has been S3, where the pattern is simple: every upload calls GenerateDataKey and every download calls Decrypt, so the key is being exercised constantly and any problem with it surfaces within seconds. That is the exception, not the rule.

ServiceWhen it calls KMSWhen you find out the key is gone

DynamoDBrefreshes the table key every 5 minutes per caller~5 minutes then the table goes Inaccessible

Read the last column as a list of how long you get to make a mistake before it is visible. For an EBS volume the answer is indefinitely, and that is why the Friday-afternoon tidy-up becomes a Tuesday-morning incident with no obvious cause.

Why the delay exists

The data key is in the hardware, not in KMS

Envelope encryption from Lesson 4.1, one layer down. When you create an encrypted EBS volume, EBS asks KMS for a data key and stores the wrapped copy in the volume's metadata. When you attach that volume to an instance, EC2 unwraps the data key once and hands the plaintext to the Nitro card, which encrypts and decrypts every block of disk I/O from then on.

1

The volume is attached and running

The plaintext data key is resident in Nitro hardware. Every read and write uses it. KMS is not involved at all — not once per I/O, not once per hour, not at all.

2

Somebody disables the key

Nothing happens. The instance does not notice, the volume does not notice, CloudWatch does not notice. There is no alarm to fire because no call failed.

3

The volume is detached

Nitro discards the data key. This is the moment the incident is created, and it still looks like nothing has gone wrong. Detaching happens on stop, on terminate, on host replacement, and on any instance refresh.

4

Something tries to attach it again

EBS asks KMS to unwrap the data key, KMS refuses because the key is unusable, and the attach fails. In an Auto Scaling group this reads as Client.InternalError and capacity quietly stops replacing itself.

What this means for your monitoring

You cannot alarm on “the key is broken” by watching for KMS errors, because there are none until the lifecycle event. The alarm you actually need is on the configuration: an EventBridge rule on DisableKey and ScheduleKeyDeletion, or an AWS Config rule. Detect the change, not the consequence — the consequence is late by design.

Clocks you do not control

Seven days, twice, with different endings

Two services put a countdown on the incident. Both give you seven days, and both do something irreversible at the end of it — but the endings differ and so does the recovery.

RDSDynamoDB

What you get backa final snapshot named rds-final:<instance>-<resource-id>, which you restore into a new instancea restore into a new table — and the last key on the table must be enabled first

Two things worth carrying out of that table. First, the identifier changes on recovery in both cases — you restore into a new instance or a new table, so anything holding the old endpoint needs updating, which is the same lesson as the Secrets Manager ARN suffix in 2.6. Second, the read replica exception is the one that catches people: the architecture you built for availability is the one with no recoverable state.

The asymmetry to remember

Re-enabling a key is instant and free. Every deadline above exists because AWS is waiting for you to do exactly that. If you are in this incident, the first action is always enable-key — arguing about who disabled it, and why, costs you hours off a seven-day clock.

Where grants stop being trivia

The permission that outlives the person who had it

In Lesson 4.2 grants were something to know about. Here they are load-bearing, because this is how the services above actually hold their access.

When you create an encrypted RDS instance, RDS checks that you can use the key and then creates a grant on the key that it holds for the entire life of that instance. The consequence is one of the most counter-intuitive facts in KMS:

Revoking someone's key access does not stop the database they created

Take away that engineer's IAM permissions, delete their role, offboard them entirely — the RDS instance keeps running, because it is not using their access. It is using its own grant. Disabling the key stops it. Removing the person does not.

That is a feature, not a hole: you do not want a database to fail because someone left the company. But it means an access review that only reads IAM policies will tell you nobody can use the key, while five services quietly use it all day.

# the inventory question IAM cannot answer aws kms list-grants --key-id $KEY \ --query 'Grants[].{Name:Name,Who:GranteePrincipal,Ops:Operations}' # service grants look like this — the name tells you who is holding on [{ "Name": "rds-abc123...", "Who": "rds.us-east-1.amazonaws.com", ...}]

Two practical rules follow. Never revoke a grant you did not create without finding out which resource depends on it — RevokeGrant on a live volume or instance is the same outage as disabling the key, scoped to one resource, and there is no undo. And when you write a key policy that must support AWS services, allow kms:CreateGrant with the kms:GrantIsForAWSResource condition set to true, so a service can take a grant on your behalf but a human cannot hand one out.

The condition that breaks integrations

The kms:ViaService hardening from Lesson 4.2 is excellent on a single-service key and dangerous on a shared one. Pin the avatars key to s3.us-east-1.amazonaws.com and the day someone encrypts an RDS instance or a secret with the same key, it fails — correctly, and confusingly. One key per service is not a purity argument; it is what makes tight conditions possible.

The shared resource nobody drew

One account, one region, one quota

KMS request quotas are per account, per region, across every key and every service — including calls AWS services make on your behalf. Your S3 uploads, DynamoDB's five-minute refresh, every Lambda reading a secret and someone else's batch job all draw on the same number.

QuotaDefault, per second
Symmetric cryptographic operations
Encrypt, Decrypt, GenerateDataKey, ReEncrypt…		100,000 in us-east-1, us-west-2, eu-west-1 · 20,000 in several others · 10,000 everywhere else — all shared

DescribeKey2,000

The gap between the first row and the second is the operational point. A hundred thousand decrypts per second and fifty grants per second — so a large scale-out event, where every new instance with an encrypted volume needs a grant, hits a wall that has nothing to do with how much cryptography you are doing. When a launch storm fails and the key is enabled and the policy is fine, CreateGrant throttling is the thing to check.

Management operations are cheap to forget too: DisableKey at 5 per second means a script that loops over a thousand keys to disable them will throttle, and half-finished is the worst possible state to leave that in.

# what your region actually allows, rather than what a blog said aws service-quotas list-service-quotas --service-code kms \ --query "Quotas[?contains(QuotaName,'symmetric')].[QuotaName,Value]" \ --output table

Every quota here is adjustable except the custom key store one. Ask before you need it — a quota increase during an incident is a support case, not a command.

Three ways to use fewer requests, in the order you should reach for them: S3 bucket keys (Lesson 4.1 — up to 99% fewer calls, and you already have them on), data key caching in the AWS Encryption SDK for client-side encryption, and separate keys per workload, which does not reduce the total but does stop one workload's throttling from taking out the others.

Crossing a region boundary

Multi-Region keys, and why they are not the default

A KMS key is regional. Ciphertext produced in us-east-1 cannot be decrypted in eu-west-1, because the key does not exist there — which is why copying an encrypted snapshot across regions makes you name a key in the destination region, and why S3 cross-region replication decrypts and re-encrypts every data key on the way.

Multi-Region keys are the escape hatch: a set of keys in different regions with the same key ID and the same key material, so any of them can decrypt what another encrypted.

Shared, synchronised by AWSIndependent, yours to keep in step
key material and key ID (the region differs in the ARN)key policy
key spec, key usage, origingrants

That right-hand column is the whole risk. A replica key is a fully independent key that happens to share material: its policy is not synchronised, so tightening the policy in one region protects nothing in the other, and drift between the two is invisible until someone tries to decrypt somewhere unexpected.

What you give up

Regional isolation is a blast-radius boundary you get for free. A multi-Region key deletes it on purpose: the same material now protects data in several regions, so one leaked copy or one bad policy reaches all of them. AWS's own guidance is that single-Region keys are the best fit for most needs — use multi-Region keys when you have a concrete reason (client-side encryption across regions, a DR plan that must decrypt in the backup region, active-active), not as a default.

Three facts that decide real designs. You cannot convert an existing key to multi-Region or back — moving an existing workload means re-encrypting everything under a new key. Most AWS services treat a multi-Region key as though it were single-Region anyway, so S3 replication still re-encrypts even when both regions hold related keys. And a primary key cannot finish being deleted until every replica is deleted, which is a safety net and an obstacle in equal measure.

Runbook

“Can we disable this key?”

The question arrives as cost tidying, or as a leaver's access review, or as an auditor asking why an unused key exists. Answer it in this order, and never from the console's “last used” column alone.

1

Find every grant

list-grants first, because it names services that IAM will never mention. An RDS grant here means a database depends on this key whether or not anyone has touched it in months.

2

Find every caller in CloudTrail

Ninety days of Decrypt and GenerateDataKey events, grouped by invokedBy and by the encryption context. The context tells you which bucket, secret or table, not merely which service.

3

Search the estate for the key ARN

Encrypted resources reference the key in their own configuration — bucket encryption, RDS KmsKeyId, EBS volumes, secrets, snapshots. AWS Config or a scripted sweep finds the ones that are attached but idle, which is exactly the set CloudTrail cannot show you.

4

Classify what you found by path

Request-path users fail immediately and loudly; lifecycle-path users fail at some unknown future restart. If the list contains a single EBS volume or RDS instance, the honest answer to “can we disable it” is no.

5

Disable, do not delete — and watch

Disabling is the dress rehearsal: reversible in one command, with none of the seven-day clocks running. Leave it disabled through at least one full deployment and one scale-out before anyone says the word deletion.

6

Only then schedule deletion, with the long window

Thirty days, not seven. The cost of the extra days is a few cents of key storage; the cost of being wrong is a restore from backup, or nothing at all.

Hands-on · ~5 minutes · read-only

Take an inventory of a key you did not create

These run against any account. On a key you inherit, they are the first five minutes of work — and on your own torn-down stack, read them as the shape of the answer.

1. Who holds a grant?

aws kms list-grants --key-id $KEY \ --query 'Grants[].{Name:Name,Who:GranteePrincipal,Ops:Operations}' --output table

2. Who has actually called it, and on behalf of what?

aws cloudtrail lookup-events \ --lookup-attributes AttributeKey=EventSource,AttributeValue=kms.amazonaws.com \ --max-results 50 --query 'Events[].CloudTrailEvent' --output text \ | jq -r '[.eventName, (.userIdentity.invokedBy // .userIdentity.arn)] | @tsv' \ | sort | uniq -c | sort -rn

invokedBy is the field that matters: rds.amazonaws.com in that column means a database is using this key, no matter what IAM says.

3. What is the key's own state and origin?

aws kms describe-key --key-id $KEY \ --query 'KeyMetadata.{State:KeyState,Origin:Origin,MR:MultiRegion,Mgr:KeyManager}'

MultiRegion: true changes every conclusion in this lesson, and KeyManager: AWS means it is an AWS managed key you cannot set a policy on at all.

4. How much of the region's quota are you using?

aws service-quotas list-service-quotas --service-code kms \ --query "Quotas[?contains(QuotaName,'symmetric')].[QuotaName,Value]" --output table

Check yourself

Four questions

At 16:00 on Friday someone disables a CMK used by an S3 bucket, a DynamoDB table, an RDS instance with a read replica, and forty EBS volumes. Nothing alerts. Walk the next seven days: what fails, when, and what is unrecoverable?

16:00, seconds: S3 uploads and downloads fail. If anything reads a secret with that key, it fails too. This is the only part that pages anyone.

16:05: the DynamoDB table goes Inaccessible and AWS emails the account. A seven-day clock starts.

~18:00: RDS — but the instance has a read replica, so it cannot be stopped and skips the recoverable state entirely, going straight to terminal inaccessible-encryption-credentials. RDS takes a final snapshot. Restoring into a new instance is now the only path, and the endpoint changes.

Whenever an instance next stops or is replaced: that EBS volume will not re-attach. Forty volumes means forty independent time bombs with no common trigger; an Auto Scaling group finds it within hours, a long-lived instance might not for months.

Day 7: the DynamoDB table is archived to a backup you are billed for, and must be restored into a new table.

Which means the true answer to “what is unrecoverable” is: nothing, if you enable the key in the first two hours. After that, the RDS instance and the table survive only as new resources with new identifiers, and everything that referenced the old ones has to be changed.

An access review says “this engineer left; revoke their KMS permissions.” You do. The next morning someone asks why the encrypted RDS instance they built is still running. Answer them.

Because the instance is not using their access. When RDS created it, RDS verified that the calling principal could use the key and then created its own grant on the key, which it holds for the lifetime of the instance. The grant belongs to the service, not the person.

Which means an access review that reads only IAM is incomplete: list-grants is the other half, and it is where you discover that offboarding somebody has not reduced anything's access to the key. It also means the reverse — do not “clean up” that grant to finish the review, because revoking it stops the database.

A deployment scales an Auto Scaling group from 10 to 400 instances, all with encrypted EBS volumes. Launches start failing, but the key is enabled, the policy allows the role, and your KMS decrypt rate is nowhere near the quota. What do you check, and why?

CreateGrant throttling. Every new encrypted volume needs a grant on the key, and the CreateGrant quota is 50 per second — while the symmetric cryptographic operations quota next to it is 10,000 to 100,000. The two numbers are three orders of magnitude apart, and the small one is the one a launch storm consumes.

Confirm it in CloudTrail by looking for ThrottlingException on CreateGrant, then either slow the scale-out or request a quota increase — in advance, because an increase during an incident is a support case.

Which means capacity planning for KMS is not about how much data you encrypt; it is about how many resources you create per second.

The DR plan says “replicate the avatars bucket to eu-west-1 and we are covered.” What does KMS do to that plan, and what are your two options?

The key is regional and does not exist in eu-west-1, so replication cannot simply copy the ciphertext. S3 replication decrypts each object's data key with the source key and re-encrypts it with a key in the destination region — which you must create and name, and which the replication role must be allowed to use. Miss that and replication silently fails for every encrypted object.

Option one, two independent keys: the default, and it keeps the region as a blast-radius boundary. Two key policies to maintain, and the destination has its own key with its own rotation.

Option two, a multi-Region key: same material in both regions, so ciphertext is interoperable — but you cannot convert the existing key, so you would re-encrypt everything under a new one; the key policy, grants and enabled state do not synchronise; and S3 replication re-encrypts anyway, so for this particular workload you gain very little.

Which means option one for this bucket, and multi-Region keys reserved for client-side encryption or a DR plan that has to decrypt the same ciphertext in the backup region.
