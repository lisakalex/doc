Three Seconds or Twenty-Three

You change one line of Java and push. The Docker build downloads every Maven dependency again, as it did on the last commit and the one before. The finished image has Maven, a full JDK and 73 MB of ~/.m2 in it, none of which the running service needs. Both problems come from the same place: the order of the Dockerfile and what ends up in its last stage. On the reference service, the same one-line change rebuilds in 22.8 seconds or in 3.7, and the image is 632 MB or 359 MB, depending only on how the Dockerfile is written.

A Dockerfile copies settings.xml with a repository password in, runs mvn package, and deletes it in the next step. Is the password safe?

No. It's in the layer the COPY made, and anyone who can pull the image can read it. The delete only adds a whiteout. docker save and tar get it back in two commands, and so does anything that reads the registry. Use RUN --mount=type=secret, which makes the file available to that one step without writing it into any layer. Then rotate the password, because it's already in every copy of the old image.

A build agent's docker images adds up to 24 GB, but /var/lib/docker uses 9 GB. Which number is right, and how do you see the real one?

9 GB is right; the 24 GB counts shared layers many times. Each image's SIZE includes every layer it stands on, and most images on one agent share their base layers, which are stored once, named by their SHA-256. docker system df counts each layer once; docker system df -v splits every image into SHARED SIZE and UNIQUE SIZE.

"Connection refused" against "connection timed out": what does each tell you, and where do you look for each?

Refused means the machine answered and nobody was listening. Timed out means nothing answered at all. Refused comes back in a millisecond, as a reset (RST) from the target's kernel, so the network path is fine. Look at the server: is the program running, and is it listening on that port and that address (ss -ltnp)? Timed out takes the full timeout, because the packets were dropped on the way. Look at firewalls, security groups, routing, and whether the IP is right at all.

The mechanism

The build cache is the layers from lesson 2.1

Every step in a Dockerfile makes a layer, and BuildKit keeps each one with a cache key: the layer it was built on, plus the instruction text, plus, for COPY and ADD, a checksum of the files being copied. On the next build, each step asks one question: is there a layer with exactly this key? If there is, it's reused and the step prints CACHED. If there isn't, the step runs.

The key includes the layer underneath, so the first step that misses makes every step after it miss too. A cache miss falls through the rest of the Dockerfile. RUN is never checked against the outside world: RUN apt-get update with the same text on the same layer is reused for months, whatever the mirror has since.

In the library: the bindery assembles a reference volume in a fixed order, section by section, and keeps every half-bound stage on a shelf. Change chapter 9 and the binder takes the stage that ends at chapter 8 off the shelf and binds from there. Change chapter 1 and every stage after it is useless, so the whole book is bound again. Put the chapters that change most often at the back.

Order

What changes most often goes last

Two Dockerfiles that build the same jar from the same source. The first copies everything, then builds:

# naive FROM maven:3.9-eclipse-temurin-21 WORKDIR /src COPY . . RUN mvn -q -pl services/reference -am \ package -DskipTests
# build files first FROM maven:3.9-eclipse-temurin-21 WORKDIR /src COPY pom.xml . COPY services/reference/pom.xml services/reference/ COPY services/status-api/pom.xml services/status-api/ COPY services/ingest/pom.xml services/ingest/ COPY services/enrich/pom.xml services/enrich/ RUN mvn -q -pl services/reference -am \ dependency:go-offline COPY services/reference/src services/reference/src RUN mvn -q -pl services/reference -am \ package -DskipTests

All four module POMs are copied because the parent pom.xml lists all four as modules, and Maven refuses to start if one is missing. Then one line of Java changes, and each is built again:

COPY . . first

WORKDIR /srccached
COPY . .runs
RUN mvn package22.4 s

build files first

RUN mvn go-offlinecached

3.7 s, nothing downloaded

$ docker build --progress=plain -f Dockerfile.ordered -t ref:ordered ctx #10 [ 3/10] COPY pom.xml . #10 CACHED … #12 [ 8/10] RUN mvn -q -pl services/reference -am dependency:go-offline #12 CACHED #13 [ 9/10] COPY services/reference/src services/reference/src #13 DONE 0.0s # the checksum changed: the first miss #14 [10/10] RUN mvn -q -pl services/reference -am package -DskipTests #14 DONE 3.4s

In the naive file, COPY . . checksums the whole context, so any change to any file misses there, and the RUN below it starts in a fresh layer with an empty ~/.m2. The ordered file only misses at COPY src; the layer holding the downloaded dependencies sits above it and is reused. The dependencies change when a POM changes, which is rarely.

The first build of each, with nothing cached, went the other way: 24.4 s for the naive file and 60 s for the ordered one, because dependency:go-offline downloads more than package needs (every plugin the POMs mention). You pay once to save on every build after it.

The gap

go-offline doesn't fetch everything

The obvious next step is to add -o (offline) to the package step, to prove the dependencies are all there. On 22 Nov that failed:

Could not resolve dependencies for project uk.interchange:reference:jar:0.1.0-SNAPSHOT dependency: net.bytebuddy:byte-buddy:jar:1.17.6 (test) Cannot access central … in offline mode and the artifact … has not been downloaded from it before.

dependency:go-offline resolves what the POMs declare, but some artifacts are only resolved when a plugin runs (here a test-scope dependency that Mockito pulls in). Two fixes. Drop -o and let the package step download the few it missed: it still saves almost everything. Or keep Maven's repository in a BuildKit cache mount:

RUN --mount=type=cache,target=/root/.m2 mvn -q -pl services/reference -am package -DskipTests

A cache mount is a directory BuildKit keeps between builds and mounts into the step. It's never written into the image. Measured with the naive order, COPY . . and all: the first build took 24.6 s, and after a one-line change 2.3 s, because the step reran but found ~/.m2 already full. The layer it made was 23.6 MB, just target/, against 93.2 MB without the mount. The cache lives on the build machine, so a fresh CI agent starts empty. On a long-lived Jenkins agent it's the fastest option.

Multi-stage

Build with Maven, ship only the jar

The naive image is the build environment with a jar in it:

$ docker history ref:naive --format '{{.Size}}\t{{.CreatedBy}}' | head -3 0B CMD ["java" "-jar" "services/reference/targe… 93.2MB RUN /bin/sh -c mvn -q -pl services/reference… # ~/.m2 and target/ 14.1kB COPY . . # buildkit $ docker run --rm ref:naive sh -c 'which mvn javac; du -sh /root/.m2 /src' /usr/bin/mvn /opt/java/openjdk/bin/javac 73M /root/.m2 23M /src

A multi-stage Dockerfile has more than one FROM. Each starts a new stage with its own layers. Only the last stage becomes the image; earlier stages are used during the build and then left in the build cache. COPY --from=build reaches back into an earlier stage for one file:

FROM maven:3.9-eclipse-temurin-21 AS build WORKDIR /src COPY pom.xml . COPY services/reference/pom.xml services/reference/ # … the other three POMs, go-offline, src, package, as above FROM eclipse-temurin:21-jre WORKDIR /app COPY --from=build /src/services/reference/target/reference-0.1.0-SNAPSHOT.jar app.jar CMD ["java", "-jar", "app.jar"]

The ordered image is the biggest of the four: faster to rebuild, but it keeps go-offline's 104 MB layer. The order fixes the build time and the stages fix the size; you want both. The runtime stage has no compiler and no build tool, so an attacker who gets a shell in it has less to work with, and a scanner has fewer packages to flag.

In the library: the print shop has presses, plates, ink and offcuts. Only the bound book goes on the shelf.

The context

What docker build . sends, and why it busts the cache

The last argument to docker build is the build context: the directory sent to the builder, and the only files COPY can see. Built from the real Interchange repository with no .dockerignore, COPY . . sent 23.87 MB: 22.7 MB of it the old services/reference/target, 1.4 MB of .git, and logs/. Each of those changes without any source changing, and each change misses the COPY . . checksum and rebuilds everything after it.

A .dockerignore at the root of the context leaves files out. Build 6 used an allow-list: * to exclude everything, then ! lines for the one file it needs. Build 7 does the same with the POMs and services/reference/src.

Base images

JDK, JRE, Alpine

Alpine saves 122 MB here, but it isn't free. musl isn't glibc, so a JNI library built for glibc won't load, and DNS and locale behaviour differ in small ways. BusyBox's tools are thinner when you debug inside the container. Test the service on it, not just the build. The step after that is a distroless image: no shell and no package manager at all.

A tag like 21-jre moves when a new patch is released. That's how you get security fixes, and it's also how two builds a week apart differ. The measurements on this page were taken with eclipse-temurin@sha256:d77e090a… for 21-jre. Pinning by digest freezes the base until you choose to move it (lesson 2.5).

On disk, again

The build cache has a size too

$ docker system df TYPE TOTAL ACTIVE SIZE RECLAIMABLE … Build Cache 418 0 10.82GB 8.76GB

That's this laptop on 26 Nov. Every intermediate layer, every earlier stage and every cache mount stays until something removes it. On a build agent this is the third way Docker fills a disk, after images and containers. docker builder prune removes the cache that nothing is using; --filter until=72h keeps the recent part, which is the part that makes builds fast.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

A Java service's Docker build downloads every Maven dependency on every commit, even when only one line of Java changed. Why, and what's the fix?

The source is copied before the dependencies are fetched, so every source change misses the cache at that COPY, and every step after it runs again. BuildKit's key for a COPY includes a checksum of the files, and a miss falls through the rest of the file. Copy the POMs first, fetch dependencies in their own RUN, then copy the source and package. The dependency layer is then reused until a POM changes. Or keep ~/.m2 in a RUN --mount=type=cache.

A production image contains Maven, a JDK and the whole ~/.m2 repository. What's wrong with that, and how do you fix it?

The image is the build environment, so production ships tools it never uses. It's bigger (632 MB against 359 MB here), so every pull and every node is slower, and a compiler and a build tool are there for an attacker and for the scanner's report. Use a multi-stage build: Maven in a build stage, then a second FROM on a JRE and COPY --from=build of the jar alone. Only the last stage becomes the image.

You add RUN mvn dependency:go-offline, then RUN mvn -o package. It fails: a test-scope dependency "has not been downloaded". Why, and what are two fixes?

go-offline resolves what the POMs declare, not everything plugins pull in while they run. Here, byte-buddy, a test dependency that came in through Mockito. Drop -o and let the package step fetch the few it missed; the big download is still cached. Or put the Maven repository in a BuildKit cache mount, --mount=type=cache,target=/root/.m2, so whatever any build downloads is kept for the next one without going into a layer.

Every build of a service sends a 24 MB context and never reuses the COPY . . layer, even when the source hasn't changed. Why, and what's the fix?

The context includes files that change on their own: the old target/, .git, logs. COPY . . checksums all of them, so any change there is a cache miss for that step and everything after it. Add a .dockerignore, ideally an allow-list (*, then ! for the POMs and the source), and copy only what the build needs.

Someone wants to move the runtime image from 21-jre to 21-jre-alpine to save 120 MB. What do you check before agreeing?

That the service really runs on musl, not just that the image builds. Alpine uses musl libc instead of glibc, so any native library built for glibc fails to load, and DNS and locale handling differ slightly. BusyBox makes debugging inside the container harder. Run the service's tests and a real request on the Alpine image, check for native libraries in the jar, and remember that the 120 MB is pulled once per node and shared by every container from that base, so the saving is smaller than it looks.

Interview answer · 60 seconds, spoken

"Our Java service's Docker build is slow on every commit and the image is over 600 MB. How would you fix both?"

Mechanism first: each step is cached by its parent layer, its instruction and the checksum of the files it copies, and the first miss rebuilds everything after it. So order by how often things change: POMs, then the dependency download, then the source. A .dockerignore keeps target/ and .git from busting the cache. Then size: a multi-stage build, Maven in the first stage and only the jar copied onto a JRE, so the build tools never reach production. End with your numbers: 22.8 seconds to 3.7, and 632 MB to 359. Say it with a timer, then type what you said.
