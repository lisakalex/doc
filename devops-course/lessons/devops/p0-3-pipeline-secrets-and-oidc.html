Pipeline Secrets and OIDC

Every pipeline you have run held a key: a JFrog token, an AWS access key, a password in the Jenkins credentials store. This lesson asks what each place you can keep a secret actually guarantees, finds the one problem none of them solves, and then removes the key altogether. Interchange ends the week able to reach AWS while storing nothing.

~4 hours week 2 uses your AWS account, costs nothing

The questions to ask of any secret store

Encrypted is not the same as safe

Every secret store says "encrypted at rest", and it is always true and rarely the point. Encryption at rest protects against someone stealing the disk. The secret's real risks are elsewhere, so ask these five instead:

  1. Who can read it? Not who is supposed to, but who can.
  2. How long does it live? A key that works for two years is a two-year risk.
  3. Can you tell who used it? Is there an audit log of each read?
  4. How is it rotated? By a person remembering, or by the system?
  5. What does a leak cost? What can it do, and for how long?

Four places to keep a secret

Cost: Parameter Store standard parameters have no storage charge. Secrets Manager charges per secret per month plus per API call. That is why teams keep plain config in Parameter Store and real secrets in Secrets Manager.

Log masking is cosmetic

Jenkins and GitHub both replace a secret's value with **** when it appears in the log. That is a string search on the output, nothing more. echo "$TOKEN" | base64 prints it in a form the mask does not recognise, and curl -d "$TOKEN" https://… sends it somewhere the log never sees. Masking stops accidents. It does nothing against someone who can edit the pipeline, and in both tools that is anyone who can push to the repository.

The problem none of them solves

Secret zero

Suppose you do the responsible thing and move the database password out of Jenkins into Secrets Manager. Now the pipeline has to read Secrets Manager, and to call AWS it needs AWS credentials. Where do those live? Back in the Jenkins credentials store, as an access key.

That first credential, the one that unlocks all the others, is called secret zero. Moving secrets into a better vault does not remove it. It just concentrates all the risk on it. And an AWS access key is the worst kind of secret zero: it never expires on its own, it works from anywhere on the internet, and leaked keys are found by automated scanners within minutes of reaching a public repository.

The only real fix is for the pipeline to prove who it is without holding a secret at all. That is what OIDC federation does.

The mechanism

OIDC: the pipeline proves who it is

The idea in one sentence: GitHub vouches for the job, and AWS trusts GitHub's signature. Like a passport. You do not carry a password to the border. You carry a document signed by an authority the border already trusts, which says who you are, and it expires.

1

The job asks GitHubA job with permissions: id-token: write requests a token from GitHub's OIDC provider at https://token.actions.githubusercontent.com.

2

GitHub signs a statementIt issues a JWT: a small JSON document, signed with GitHub's private key, that lists facts about this exact run. These facts are called claims. The important one is sub, the subject: repo:lisakalex/interchange:ref:refs/heads/main. The token expires within minutes.

3

The job hands it to AWSThe aws-actions/configure-aws-credentials action sends the JWT to AWS STS with AssumeRoleWithWebIdentity, naming the IAM role it wants.

4

AWS checks the signatureSTS fetches GitHub's public keys from GitHub's published key set and verifies the signature. Only GitHub holds the private key, so only GitHub could have signed it.

5

AWS checks the role's trust policyDoes this role trust GitHub as an identity provider? Does the aud claim say sts.amazonaws.com? Does the sub claim match what the role allows? Every condition must pass.

6

AWS hands back temporary keysSTS returns an access key, secret key and session token that expire, by default after one hour. The action puts them in the job's environment, and every aws command in later steps uses them.

What got stored, and where? Nothing, anywhere. GitHub holds its own signing key, AWS holds a trust policy, and the only credentials that ever exist are minted per run and dead within the hour. Go back to the five questions: who can read it (nobody, there is nothing to read), lifetime (an hour), audit (every AssumeRoleWithWebIdentity is in CloudTrail, with the repo and branch), rotation (every run), cost of a leak (an hour, limited to that role's permissions).

Where it goes wrong

The trust policy is the whole security model

The role's trust policy decides which GitHub runs may become this role. This one allows exactly one repository, on exactly one branch:

{ "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": { "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com" }, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com", "token.actions.githubusercontent.com:sub": "repo:lisakalex/interchange:ref:refs/heads/main" } } }] }

Forget the sub line and you have trusted all of GitHub

Every GitHub Actions run, in every repository on the planet, can get a token from the same issuer with aud: sts.amazonaws.com. If your condition checks only aud, then a stranger's workflow in their own repository can assume your role, and all they need is your role's ARN, which is not a secret. Security researchers have repeatedly found roles in real AWS accounts configured exactly like this. The sub condition is what says "only my repository, only this branch".

The common sub values, from GitHub's documentation:

The run is…sub claim
A push to a branchrepo:OWNER/REPO:ref:refs/heads/BRANCH
A pull requestrepo:OWNER/REPO:pull_request
A job with an environment:repo:OWNER/REPO:environment:NAME

Wildcards with StringLike, such as repo:lisakalex/interchange:*, are allowed and sometimes right, but every * widens who can become the role. A pull request runs code nobody has reviewed yet, so a role that can deploy should never trust pull_request.

Build it

Interchange reaches AWS, holding no key

A role with no permissions at all, and a workflow that assumes it and asks AWS "who am I?". sts:GetCallerIdentity needs no permission, so this proves the federation works while the role can do nothing. IAM is free, so this costs nothing.

Part 1: AWS console

  1. IAM → Identity providers → Add provider. Type OpenID Connect. Provider URL https://token.actions.githubusercontent.com, audience sts.amazonaws.com. You do this once per AWS account.
  2. IAM → Roles → Create role → Custom trust policy. Paste the policy above, with your 12-digit account ID in place of ACCOUNT_ID.
  3. Permissions: add none. Skip that page.
  4. Name it gha-interchange-whoami. Copy its ARN from the role's summary page.

Part 2: the workflow

A new file, .github/workflows/aws-whoami.yml, separate from ci.yml so that the build never gets AWS access it does not need:

name: aws-whoami on: push: branches: [main] pull_request: workflow_dispatch: permissions: contents: read id-token: write # may ask GitHub for an OIDC token; nothing else jobs: whoami: runs-on: ubuntu-24.04 steps: - uses: aws-actions/configure-aws-credentials@SHA # v6.3.0 with: role-to-assume: arn:aws:iam::ACCOUNT_ID:role/gha-interchange-whoami aws-region: eu-west-2 - run: aws sts get-caller-identity
  • Look up the SHA the same way as last week: gh api repos/aws-actions/configure-aws-credentials/commits/v6.3.0 --jq .sha
  • The role ARN is not a secret, so it can sit in the file. It is useless without a token that matches the trust policy.
  • There is no actions/checkout: this job needs no code. The AWS CLI is already on the runner image.

Push to main. In the log, get-caller-identity should print an Arn like arn:aws:sts::ACCOUNT_ID:assumed-role/gha-interchange-whoami/GitHubActions. That is the job, as the role, holding nothing.

Then break it on purpose

Open a pull request that changes anything, a line in the README will do. The workflow runs again, now with sub = repo:lisakalex/interchange:pull_request, which does not match the trust policy. The configure step should fail with an error saying it is not authorized to perform sts:AssumeRoleWithWebIdentity. That red is the trust policy working: unreviewed code does not get into your account. Then close the PR.

Last step: open CloudTrail in the AWS console, Event history, and filter on event name AssumeRoleWithWebIdentity. Both attempts are there, the success and the refusal. That is your audit trail.

The other half of the week's build

Path filters: rebuild what changed

Interchange is a monorepo: four services in one repository. Today ci.yml rebuilds all four on every push, even when you only edited a README. While the services are empty that costs 16 seconds. Once each one has code, tests and an image, it costs minutes per push, multiplied by every push.

Start with the cheap half: don't run CI at all when nothing that affects the build changed.

on: push: branches: [main] paths-ignore: - '**.md' - 'docs/**' pull_request: paths-ignore: - '**.md' - 'docs/**'

The trap with skipped workflows

A workflow that path filters skip does not report "passed". It reports nothing. If a branch rule later says the ci check must pass before merging, a docs-only pull request waits forever for a check that will never run. The standard way round it is to always run the workflow, and decide inside it what to build, which is the next step.

Per service, later. Rebuilding one service out of four is the same idea one level down: a first job works out which services/* folders changed (the common tool is the dorny/paths-filter action), and later jobs build only those, with ./mvnw -pl services/enrich -am verify. -pl picks the module and -am also builds anything it depends on. A change to the parent pom.xml, mvnw or the workflow itself must still rebuild everything, because all four depend on them. This lands in Phase 2, when each service builds an image and the minutes are real.

What this does not cover yet

The JFrog token, and other keys

OIDC works wherever the receiving side can verify GitHub's signature. AWS, Azure and GCP all can, and so can JFrog Artifactory, which means even the Maven deploy token in last week's example can be replaced. Where a system cannot, the fallback order is: a secret in Secrets Manager, read at run time by a role assumed through OIDC. That way the only thing stored anywhere is in a vault with an audit log, and secret zero is gone.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

A teammate says GitHub secrets are safe because they are masked in the logs. Why is that not enough?

Masking is a text search on the log output. echo "$TOKEN" | base64 prints it in a form the mask does not recognise, and curl can send it somewhere that never touches the log.

And anyone with write access can push a branch with a workflow that does either, because repository secrets are available to runs from any branch. Masking protects against accidents, not against anyone who can edit the pipeline.

You move the database password from Jenkins credentials into Secrets Manager. Which problem have you not solved?

Secret zero. To read Secrets Manager the pipeline needs AWS credentials, and those are now an access key stored in Jenkins: long-lived, usable from anywhere, and the key to every secret in the vault.

You improved the database password, which now has an audit log and can rotate, but concentrated the risk in one credential. OIDC removes that last key, because the pipeline proves its identity with a signed, short-lived token instead.

A role's trust policy checks aud = sts.amazonaws.com but has no condition on sub. What can happen?

Any GitHub Actions run in any repository can assume it. Every run on GitHub can get a token from the same issuer with that audience, and the role ARN is not secret. A stranger's workflow in their own repository becomes your role.

Because AWS only checks what the policy tells it to check: the signature proves the token came from GitHub, and only sub says which repository and branch it came from.

aws-whoami succeeds on a push to main and fails on a pull request. Why, and is that what you want?

The two runs carry different sub claims. The push says repo:lisakalex/interchange:ref:refs/heads/main, which the trust policy allows. The pull request says repo:lisakalex/interchange:pull_request, which it does not.

Yes, it is what you want. A pull request runs code nobody has reviewed yet, so it should not get credentials that reach your AWS account. Code gets AWS access after it is merged to main.

The temporary credentials from an OIDC run leak into a log. Compare the damage with a leaked access key.

The OIDC credentials expire, by default within an hour, and can only do what that one role allows. A leaked access key works until a person notices and revokes it, which can be months, and often belongs to a user with far wider permissions.

Because short-lived credentials limit a leak in time and the role limits it in scope. OIDC does not make leaks impossible; it makes them small.
