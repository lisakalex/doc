How to use it

Remember the card, not the words

Shape

Problem, then what I did, then because (the mechanism), then one failure I know how to find. Interviewers probe the because.

Card

Each lesson has a small table: a point, its because, its tool. Learn the rows; the sentences come by themselves when you speak.

Practise

Row 1 out loud, then rows 1–2, then 1–3. Cover the card and say it all with a 60-second timer. Look only at the row you got stuck on.

Cold first

Where the interview stage is still open, the model answer is folded. Try it cold, then open it. A green lesson number means the stage is done.

Say "our production servers", not product names. Keep only the work examples that really happened.

0.1

Build Once, Deploy Many

open

"Your team lead wants the deploy pipeline to rebuild from the tag, because it's the same code. What do you say?"

PointBecauseTool / proof
Same code ≠ same artifactA rebuild re-resolves dependencies (SNAPSHOT), uses that week's JDK and plugins, and stamps new timestampscompare SHA-256 of two builds
Promote the bytes you testedOnly the promoted jar went through test and UATArtifactory promotion
Config lives outsideIdentical bytes in every environment, so every difference must be injected at deployenv vars, config server
A tag isn't a versionTags can be moved; a digest can'tdeploy image@sha256:…
Rollback has a limitThe artifact rolls back; the database schema doesn'texpand, then contract
Model answer · try it cold first

"Same code isn't the same artifact. A rebuild re-resolves dependencies, runs on whatever JDK and plugins the agent has that week, and produces bytes nobody has tested. So we'd be shipping to production the one build that skipped test and UAT. Promoting the artifact costs us a repository we already have, and production gets exactly what we verified. That also means the configuration has to live outside the artifact, because the bytes are identical everywhere. With containers it's the same idea, but I'd deploy by digest, not by tag, because a tag can be moved. And I'd keep one caveat in mind: rolling back the jar is easy, but a database migration doesn't roll back with it, so schema changes go in as expand, then contract."

  • Two builds of one commit differ. Does it matter? (0.1a) Four causes: a dependency resolved differently, a different JDK patch on the agent, a plugin that pulled a newer version, a generated timestamp. Only the last is bytes-only. The Maven enforcer catches the first and third; a pinned build image and project.build.outputTimestamp close the other two. To find out, diff the unpacked jars and the dependency trees.

Jenkins to GitHub Actions

open

"Have you used GitHub Actions? What changes when you move a Jenkins pipeline to it?"

PointBecauseFix
Every job is a fresh machineWithout needs:, jobs run in parallel and share nothingneeds:, upload/download artifact
A new job can rebuildA separate publish job that runs mvn deploy ships untested bytespublish the artifact the test job built
Hosted runners are outsideThey can't reach servers inside our networkself-hosted runner
An action is someone else's codeIt runs with your token, and @v2 can change under youpin to a commit SHA, least permissions:
Approval gateJenkins input becomes an environment with required reviewersenvironments
Model answer · try it cold first

"Not in production. I run Jenkins in production, and I use Actions in my own project, so I know what changes when you move. First, every job is a fresh machine, so jobs share nothing and run in parallel unless you chain them with needs. Second, if you split publishing into its own job and it runs mvn deploy again, you've rebuilt the artifact, so it has to pass along the jar that was tested. Third, GitHub's runners are outside our network, so anything that deploys to internal servers needs a self-hosted runner. And fourth, an action is someone else's code running with your token, so I pin it to a commit SHA and give the workflow the least permissions. In my project the workflow reaches AWS with OIDC and holds no stored keys."

Pipeline Secrets and OIDC

open

"How do you handle secrets in a CI/CD pipeline?"

PointBecauseTool / proof
Masked isn't safeAnyone who can edit the pipeline can print it transformed, or send it out with curlbranch protection, review
Secret zeroA secrets manager still needs a credential to open it; the risk is concentrated, not goneSecrets Manager + its key
Best secret is noneOIDC: GitHub signs a token, AWS trusts the issuer and hands out credentials for one hourAssumeRoleWithWebIdentity
The trust policy is the securityCheck aud and sub; without sub, any repo on GitHub can assume the rolerepo:owner/name:ref:…
Leaked anywayShort-lived, but an hour is enoughrevoke sessions, CloudTrail
Model answer · try it cold first

"Masking in the logs isn't real protection, because anyone who can edit the pipeline can print the secret transformed or send it somewhere. Moving it into a secrets manager helps, but you still need a credential to read the manager, so the risk is concentrated, not removed. The better answer is to have no long-lived secret at all. With OIDC, GitHub signs a token for each run, AWS trusts GitHub as an identity provider and gives back credentials that expire within an hour. The whole security model is the role's trust policy: it has to check the audience and the subject, meaning which repository and which branch, otherwise any repository on GitHub could assume the role. In my project the pipeline reaches AWS that way with no stored keys. If those temporary credentials did leak, I'd still revoke the role's sessions, check CloudTrail for what they did, and fix whatever printed them."

Ansible Idempotency, Named

open

"What does idempotent mean in Ansible, and how do you make sure a playbook is?"

PointBecauseTool / proof
Two meaningsSame end state, and a second run reports changed=0run it twice
Why the report matters"changed" fires handlers: a restart on every deploy, and real drift hides in the noisehandlers
Shell always says changedAnsible can't know what a command diduse a module
Four fixesmodule; creates/removes (only checks a file exists); changed_when/failed_when; check, then actregister
--check can lieShell tasks are skipped in check modeidempotence test in CI
Model answer · try it cold first

"Idempotent means two things. Running the playbook again leaves the server in the same state, and, the part people forget, the second run reports nothing changed. That report matters because 'changed' triggers handlers, so a dishonest task restarts the service on every deploy, and a real change gets lost in the noise. Most of it comes from shell and command tasks, which always report changed, because Ansible can't know what the command did. There are four fixes: use a module, use creates or removes, which only check that a file exists, so they miss a version bump, set changed_when from the command's output, or check first and act only if needed. I also don't trust --check on a shell-heavy playbook, because shell tasks are skipped in check mode. So I test it like any behaviour: run it twice in CI and fail if the second run changes anything."

Python That Survives Leaving Your Laptop

open

"A Python script works on your laptop but fails on the build agent with 'No module named requests'. Why, and how do you make it reliable?"

PointBecauseTool / proof
Two Pythonspip installed into one Python, the script runs with anotherpython3 -m pip, which -a
A venv is a directoryIts own site-packages and a python link; no activate needed.venv/bin/python
A venv can't moveAbsolute paths in its scripts: "bad interpreter"rebuild it in place
== pins only the topTransitive dependencies drift; pip freeze has no hasheslock file, uv sync --locked
The wheel is the artifactBuild once, install the same wheel; it doesn't carry the lockwheel + constraints
Model answer · try it cold first

"Usually there are two Pythons on the agent: someone ran pip install for one, and the job runs with another. So I always use python3 -m pip, and better, a virtual environment per job. A venv is just a directory with its own packages and its own python, so the job calls .venv/bin/python directly and doesn't need activate. It can't be copied somewhere else, though, because its scripts contain absolute paths: that's the 'bad interpreter' error. The second problem is drift: pinning requests==2.28.1 pins only the top, and its dependencies can change from one year to the next. So I use a lock file with hashes and install with --locked in CI, so a different resolution fails the build. For something we deploy, I build a wheel once and install that same wheel, with the locked versions, on every server: the same build-once rule as for a jar."

Where the Disk Space Went

open

"The disk is 100% full, but du adds up to far less. What's going on, and how do you fix it?"

PointBecauseTool / proof
Deleted but openrm removes the name; the inode stays until the last process closes itlsof +L1, /proc/PID/fd
df vs dudf counts used blocks; du walks names, and the file has noneboth, side by side
Get it backRestart or signal the process, or truncate through its descriptor: > /proc/PID/fd/N
Rotate properlyA rename keeps the app writing to the old file; copytruncate can lose linescreate + reload, or app rolling
Open-file limitIt's per process; your shell's ulimit isn't the service's/proc/PID/limits
Model answer · try it cold first

"That's almost always a file that was deleted while a process still had it open. rm only removes the name. The data stays on disk until the last process closes the file. df counts used blocks, so it still sees it, but du walks the names, and the file no longer has one. I find it with lsof +L1, or by listing /proc/*/fd for 'deleted'. To get the space back, I restart or signal the process, or truncate the file through its descriptor in /proc if I can't restart. Then I fix the cause, which is usually log rotation: if logrotate just renames the file, the app keeps writing to the old one, so it needs create and a reload, or the app does its own rolling. A related trap: 'too many open files' is a per-process limit, so I check /proc/PID/limits for the service, not ulimit in my own shell."

Where the Memory Went

open

"Monitoring says a server has 3% free memory. Do you need more RAM? And a Java container keeps restarting with exit code 137. What's happening?"

PointBecauseTool / proof
Free ≠ availableSpare RAM is used as page cache, and the kernel gives it back on demandfree -m: available
Real pressureThe kernel drops cache, then swaps, then OOM-killsvmstat si/so, journalctl -k
137 = 128 + 9SIGKILL from the kernel: the cgroup limit was hit. No stack trace, the log stops mid-linedocker inspect OOMKilled
Heap OOM is differentJava throws OutOfMemoryError with a stack tracethe app log
Size the heap below the limitDefault heap is 25% of the limit; heap isn't all of Java's memory-XX:MaxRAMPercentage=75
Model answer · try it cold first

"Not necessarily. Linux uses spare memory as page cache, and it gives it back as soon as a program needs it, so 'free' is always low on a healthy server. The number to look at is 'available' in free -m. Real pressure shows as swapping in vmstat, or OOM kills in the kernel log, because under pressure the kernel drops cache first, then swaps, then kills the process with the highest OOM score. Exit code 137 is 128 plus 9, SIGKILL: the container went over its memory limit and the kernel killed it, which is why the log stops mid-line with no exception. That's different from Java's own OutOfMemoryError, which leaves a stack trace. The fix is sizing: by default Java takes a quarter of the limit for the heap, and setting -Xmx equal to the limit gets you killed, because Java needs memory outside the heap too. In my project I run it with the heap at 75% of a 512 MB limit, and I tested that a 64 MB limit gets killed with 137."

The Job Nobody Saw Fail

open

"A nightly job runs fine by hand but fails from cron, and nobody notices. Why, and how would you run it instead?"

PointBecauseTool / proof
A different environmentcron doesn't read .bashrc: minimal PATH, different directoryfull paths, set PATH
SilentOutput goes to local mail that nobody readsjournald
Timer + serviceOutput in the journal; Persistent=true runs a missed job after boot; OnFailure= alertssystemctl list-timers
Restart loop"Start request repeated too quickly": the start limit was hit; the real error is earlierjournalctl -u, reset-failed
Never edit the vendor unitAn upgrade overwrites it; a drop-in survivessystemctl edit, systemctl show
Model answer · try it cold first

"Two reasons. Cron runs the script with a minimal environment: it doesn't read .bashrc, so the PATH is short and the working directory is different, and a command that works in my terminal isn't found. And it's silent, because cron mails the output to a local mailbox nobody reads. I'd move it to a systemd timer with a service. Then the output goes to the journal, so journalctl -u shows exactly what failed, Persistent=true runs a missed job after the server comes back from patching, where cron would just skip it, and OnFailure= starts an alert unit when it fails. The same goes for long-running services started with nohup: under systemd they get restarts, limits like LimitNOFILE and MemoryMax, and logs, and I change vendor units only with a drop-in, so an upgrade doesn't overwrite it. In my project the service is restarted within five seconds after a kill -9."

Running but Unreachable

done · ¾ cold, 22 Nov

"A service is running, but users can't reach it. Walk me through how you'd debug it."

The user seesIt means, becauseI run
Slow, 5 s, then worksDNS: the first nameserver is dead; the resolver waits 5 s, then tries the nextgetent hosts, /etc/resolv.conf
Refused, at onceThe machine answered, but nothing listens on that address and port (often bound to 127.0.0.1)ss -ltnp on the server
Timed outNothing answered: the packets were dropped on the waysecurity group, firewall, ip route get
PKIX path building failedJava trusts its own cacerts, not the system'skeytool -importcert, restart
Model answer

"I start from the error message, because it tells me which step failed: the name, the route, the connection or TLS. If every call takes just over five seconds and then works, that's DNS: the first nameserver is dead, so the resolver waits five seconds for it, then asks the next one. I prove it with getent hosts, not dig, because getent reads /etc/hosts first, the same way the app does. If I get 'connection refused' straight away, the machine answered, so the network is fine, but nothing is listening on that address and port. I run ss -ltnp on the server; often the app is bound to 127.0.0.1, so curl on the server works and everyone else is refused. If it times out, nothing answered at all: the packets were dropped, so I check the security group, the firewall and whether the IP is right. And if curl works but Java fails with PKIX, Java trusts its own cacerts file, not the system's, so I import the CA with keytool and restart the app. On our production servers I found that every server used one upstream DNS server, so that's the first thing I'd check there."

  • dig shows the new IP, the app uses the old one. Two reasons? An old line in /etc/hosts wins, because nsswitch checks files before dns, and dig skips it. And the JVM caches lookups (30 s by default, forever with networkaddress.cache.ttl=-1), while connection pools keep old TCP connections. A restart clears both.

The File Root Left Behind

done · ¾ cold, 22 Nov

"How would you run a service on Linux so that a bug in it can't damage the box?"

PointBecauseWhere
Its own system user, no shellWhatever its user can do, a bug can douseradd --system
Code owned by root, 644The kernel checks owner, then group, then other; the service is other: read, no write/opt/…/app.jar
One writable placeOnly its log directory, created by systemdLogsDirectory=
Private logsNew files lose all bits for otherUMask=0027
No root for the portPorts above 1024 need no privilege8081
Failure I can findA log recreated by root: the app runs, health is green, nothing is loggedjournal: "Permission denied"
Model answer

"If a service runs as root or a normal user, any bug in it can do whatever that user can, so I give it the least it needs. In my project I created a system user for the service, with no login shell, so nobody can log in as it. The code is owned by root, in /opt, with mode 644, so the service can read its jar but can't change it. The only place it can write is its log directory, which systemd creates for it, and I set UMask=0027, so its log files aren't readable by everyone. It listens on port 8081, above 1024, so it never needs root. This works because the kernel checks owner, then group, then other, and the first match decides; for its own code, the service is other, which has read but no write. One failure I tested: if someone recreates the log as root, the app keeps running and health checks stay green, but nothing gets logged. The journal shows 'Permission denied'. I remove the file and restart."

Ten Containers, One Image

½ cold, 26 Nov · retake Sat 28

"What's actually in a Docker image, and what happens on disk when you start ten containers from it?"

PointBecauseTool / proof
Read-only layersOne per build step that changes the filesystem, named by hash, shared between imagesdocker history
One writable layer eachOverlayFS merges lower (image) and upper (container) into the container's /docker ps -s
Copy-upThe first write to an image file copies the whole file upown size vs virtual
RUN rm doesn't shrinkA later layer only adds a whiteout; the file, or a secret, still ships&& in one RUN, --mount=type=secret
Container files die with itThe writable layer goes on docker rmvolumes, logs to stdout
Model answer · try it cold first

"An image is a stack of read-only layers, one for each build step that changes the filesystem. Each layer is named by its hash, so images built on the same base share those layers on disk. When a container starts, Docker adds one thin writable layer on top, and OverlayFS merges them into the container's root filesystem. Reads come from the top-most layer that has the file; the first write to a file from the image copies the whole file up into the writable layer. So ten containers from one image cost one copy of the image plus ten small writable layers. Two things follow that people get wrong. A RUN rm in a later line only adds a whiteout, so the file, or a secret, still ships and can be read back with docker save; you clean up in the same RUN, or pass secrets with a secret mount. And anything a container writes, logs included, lives in its writable layer and is deleted with the container, unless it goes to a volume or to stdout. In my project I put our Java service into an image on Temurin 21, running as a system user, UID 999, logging to stdout, with the heap at 75% of the container's memory limit."

  • Why does RUN rm /big not make the image smaller? Each RUN line becomes a read-only layer when it finishes. A delete in a later layer only adds a whiteout, so the file still ships. To keep it out, create and remove it in the same RUN with &&; that's why you clean up apt caches in the same RUN as the install.
  • Why a container instead of a systemd service? A systemd service needs the server prepared: the runtime, the user, the paths. An image carries all of that, so the same artifact runs identically on a laptop, in CI and in production, rollback is just the previous tag, and it's what Kubernetes needs. It's not a VM, though: it shares the kernel, so I still run it as non-root.
  • Why UID 999? useradd --system picks from the system range in /etc/login.defs, counting down from 999. The kernel only cares whether the UID is 0; names come from each machine's own /etc/passwd, so on the host the same 999 can show as a different user.
  • Two services on port 8081, no clash? The container's port is in its own network namespace; only the host side of -p can clash. I'd check with ss -ltn on the host, and publish on 127.0.0.1 unless it really must be reachable, because Docker's rules bypass ufw.
