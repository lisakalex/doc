Same Commit, Different Bytes

Lesson 0.1 named four ways a rebuild of an identical commit produces a different artifact, in one sentence. This page takes that sentence apart: what each one looks like in a Jenkins, Maven and JFrog shop, the mechanism underneath, and the fix.

Recorded from a question asked on 11 October 2026. Companion to Lesson 0.1, Build Once, Deploy Many.

Two kinds of difference

Behaviour, or only bytes

The first three causes can change what the code does. The fourth changes the bytes but not the behaviour. The fourth still matters: when two checksums disagree, the checksum cannot tell you which kind of difference you are looking at.

The four causes

Each one: what happens, why, the fix

1

A dependency resolved differently

behaviour

The commit contains your pom.xml, not the jars it names. Maven fetches those at build time, so the answer can change between builds:

  • SNAPSHOT versions. acme-common:1.4-SNAPSHOT is a moving target. JFrog stores each snapshot deploy as a timestamped jar (acme-common-1.4-20261009.143012-7.jar) and Maven reads maven-metadata.xml to pick the newest. Monday's build gets build 7. Someone deploys on Tuesday, so Tuesday's build gets build 8. Same commit, different code inside.
  • Version ranges. [2.0,3.0) means "the highest version in that range that exists today". When 2.7 is published, your next build quietly takes it.
  • Transitive mediation. You depend on A and B, and each pulls in Jackson at a different version. Maven does not pick the highest. It picks the nearest in the tree and, on a tie, whichever is declared first. Reorder two dependencies, or let A drop its Jackson declaration in a patch release, and a different Jackson ships in your fat jar. Your own code did not change at all.
  • The repository itself. A JFrog virtual repository searches its members in order. Reorder them, or purge and refetch a remote proxy cache, and the same coordinates can resolve to a different file.

BecauseMaven has no lockfile, unlike npm's package-lock.json. The POM records what you asked for, not what you got, and resolution runs again on every build against a repository whose contents change.

FixBan SNAPSHOTs and ranges in release builds: Interchange's release profile already runs requireReleaseDeps, and banDynamicVersions is the matching enforcer rule for ranges. Pin transitive versions with dependencyManagement or a BOM (the Spring Boot and Camel BOMs do most of it). Add dependencyConvergence so a conflict fails the build instead of being settled silently.

2

A build agent with a different JDK patch

behaviour

Jenkins agent 1 has Temurin 21.0.4. Agent 2 was patched to 21.0.6. Whichever agent picks up the job is the one that compiles your code.

  • maven.compiler.release=21 does not protect you. It limits which APIs you may call. The compiler doing the work is still whatever JDK runs Maven.
  • javac changes between patches. Bug fixes can produce different bytecode: how lambdas and string concatenation are compiled, constant-folding fixes. Some plugins also write the JDK version into the manifest (Build-Jdk: 21.0.4), so the bytes differ even when the bytecode does not.
  • The patch case is the harmless end. The dangerous end is an agent still on JDK 17, or one whose default java was changed by an Ansible run nobody connected to the builds.

Becausethe toolchain is not part of the commit. It is part of the agent, and agents drift. Same lesson as Ansible: two servers configured "the same way" six months apart are not the same.

FixPin the JDK with Maven toolchains. Add the enforcer rule requireJavaVersion so a build on the wrong JDK fails loudly. Better still, build inside a container image pinned by digest (eclipse-temurin:21.0.5_11-jdk@sha256:…), so every agent compiles with exactly the same JDK. That is where Phase 2 takes you.

3

A plugin that pulled a newer version

behaviour

Every Maven build runs plugins: compiler, resources, jar, surefire, shade. If the POM names no version for one, Maven fills it in from its own defaults, and those defaults depend on which Maven is installed.

  • An agent on Maven 3.8 and an agent on 3.9 can package the same jar with different maven-jar-plugin versions, or run different surefire versions.
  • A new plugin version can change entry ordering, manifest contents, shading rules, or which tests get picked up. Nobody touched the POM.
  • Maven itself is the same problem: mvn on an agent is whatever someone installed there.

Becausean unpinned plugin is a dependency like any other, resolved at build time. Most people never think of it that way.

FixPin every plugin in pluginManagement (the Spring Boot parent pins most of them). Add the enforcer rule requirePluginVersions to catch the rest. Use the Maven wrapper: Interchange has ./mvnw, which pins the Maven version inside the repo, so the agent's installed Maven does not matter.

4

A generated file with a different timestamp

bytes only

The harmless kind, and the most common. Build the same code twice, one minute apart, on the same machine, and the jars still hash differently:

  • A jar is a zip, and every zip entry stores a modification time. Same .class contents with different mtimes gives different bytes and a different SHA-256.
  • Generated files carry build-time facts. Spring Boot's build-info.properties contains build.time. Older builds wrote pom.properties with a date comment. The manifest may say Built-By: jenkins on one agent and Built-By: al on your laptop. git.properties records the build host.
  • Entry order can follow the filesystem listing, which can differ between machines.

Becausethe build records when and where it ran, not just what it built. Those facts change every time, so the output changes every time.

Fixproject.build.outputTimestamp, already pinned in Interchange. Modern Maven plugins read it, set every zip entry to that fixed time and sort the entries; Spring Boot's build-info uses it too. To check: build twice and compare with sha256sum, or run mvn verify artifact:compare. When they still differ, diffoscope shows exactly which file inside differs and how.

Why it matters

Promotion ships what you tested. Reproducibility proves it

Staging tested artifact X. If production rebuilds from the same tag it gets artifact Y, and any of the four causes can make Y differ from X. Nobody tested Y.

Behaviour cannot drift

Pinning closes causes 1 to 3. The code that runs is the code that was resolved and compiled once.

You can verify

With cause 4 gone, matching hashes really do mean an identical artifact, and a mismatch means something real changed.

You still promote the built artifact rather than rebuilding. Reproducibility is what lets you prove the artifact you promoted is the one that came from that commit.

The same four, again, in Phase 2

FROM eclipse-temurin:21 is a moving tag. apt-get install curl installs whatever version is current that day. Each layer records timestamps. It is the same problem in a new tool.

Check

Two questions

Answer out loud and end with "because…" before opening.

Which two of the four causes will the Maven enforcer catch, and which two need something else?

Enforcer catches 1 and 3, and partly 2. requireReleaseDeps, banDynamicVersions and dependencyConvergence fail the build on moving or conflicting dependencies. requirePluginVersions fails on unpinned plugins. requireJavaVersion can reject the wrong JDK, though only within the range you set, so a patch difference inside it passes.

Cause 4 is not an enforcer rule at all. It is fixed by a property, project.build.outputTimestamp, which the packaging plugins read. Cause 2 is fully closed only by pinning the environment itself: toolchains, or a build image pinned by digest. Because the enforcer checks what the POM declares, and neither timestamps nor the agent's exact JDK are declared there.

Two builds of one commit have different SHA-256s. What do you run to find out whether it matters?

diffoscope on the two jars, or mvn verify artifact:compare against the reference build. If the only differences are entry times or build.time, it is cause 4: bytes, not behaviour, and outputTimestamp is missing or not honoured by some plugin. If a .class file or a dependency jar inside BOOT-INF/lib/ differs, it is one of causes 1 to 3, and something that runs has changed. Because a hash only says "different", never "how different".
