Python That Survives Leaving Your Laptop

Your Python scripts run unattended in Jenkins, and other engineers depend on them. Every "it worked on my laptop" failure in Python comes down to one of three things: the wrong interpreter, a missing package, or a different version of a package. This lesson shows the mechanism behind each one, and the files that stop it happening: a virtualenv, a lock file, and a wheel.

~3 hours week 2 laptop only, no AWS uv 0.9.10 · Python 3.14

The mechanism

What import requests actually does

Python does not "know" which packages are installed. When it meets an import, it searches a list of directories, in order, and loads the first match. That list is sys.path, and it belongs to one interpreter. This is the whole mechanism:

1

Which pythonThe shell finds python3 on PATH, or a shebang line names an interpreter directly. That choice fixes everything after it.

2

Its sys.pathThat interpreter builds its search list: the standard library first, then its own site-packages (Debian and Ubuntu call it dist-packages).

3

First match winsIt walks the list and loads the first requests it finds. If none of the directories has one, you get ModuleNotFoundError.

Here is the list on the laptop this lesson was written on, Ubuntu 26.04:

$ python3 -c 'import sys; print(sys.executable); print(*sys.path, sep="\n")' /usr/bin/python3 /usr/lib/python314.zip /usr/lib/python3.14 /usr/lib/python3.14/lib-dynload /usr/local/lib/python3.14/dist-packages /usr/lib/python3/dist-packages /usr/lib/python3.14/dist-packages $ python3 -c 'import requests; print(requests.__file__)' /usr/lib/python3/dist-packages/requests/__init__.py

requests works on this laptop because Ubuntu installed it, as the apt package python3-requests, for its own tools. Nobody on the project asked for it. A script that imports it works here by accident, and nothing written down says it needs it.

pip and python3 can be two different Pythons

pip install installs into the interpreter that pip itself belongs to. On a server with several Pythons, that is often not the one Jenkins runs. Always install with python -m pip, using the same python that will run the script. Then the install and the run use the same sys.path.

The fix for "which packages"

A virtualenv is just a directory

A virtual environment is a folder with three things in it: a link to a real interpreter, an empty site-packages, and a small config file that tells the interpreter to use that folder instead of the system one:

$ python3 -m venv .venv $ cat .venv/pyvenv.cfg home = /usr/bin include-system-site-packages = false version = 3.14.4 executable = /usr/bin/python3.14 $ ls -l .venv/bin/python .venv/bin/python -> python3 $ .venv/bin/python -c 'import requests' ModuleNotFoundError: No module named 'requests'

Same laptop, same Python 3.14, and requests is gone, because include-system-site-packages = false takes Ubuntu's dist-packages off the list. That is the point. Inside the venv, only what you install exists, so anything missing from your project's dependency list fails here, on your laptop, and not on the server.

You don't need activate

source .venv/bin/activate does three small things: it puts .venv/bin at the front of PATH, sets VIRTUAL_ENV, and changes your prompt. It is a convenience for typing. In a Jenkins job, call the interpreter by its path instead: .venv/bin/python script.py. It's shorter, and you can see in the log which Python ran.

A venv cannot be moved

When pip installs a command into a venv, it writes the venv's full path into the command's first line. Copy the venv somewhere else, and every command in it points at a Python that is no longer there:

$ head -1 server/app/bin/check-release #!/…/labs/p0-5/server/app/bin/python $ mv server/app server/moved $ server/moved/bin/check-release release.toml bash: server/moved/bin/check-release: /…/server/app/bin/python: bad interpreter: No such file or directory # exit 126

So a venv is not something you build in Jenkins and copy to a server. You build it on the machine that runs it, from files that pin exactly what goes in. The rest of this lesson is those files.

Seen on a real run

Why it failed on the server

A script you might really write: before a deploy, check that every artifact the release needs is in the repository. It reads a list from release.toml and asks Maven Central for each one. The second artifact is a version that doesn't exist, so the script exits 1 on purpose:

"""Check that every artifact a release needs exists before the deploy starts.""" import sys import tomllib import requests with open(sys.argv[1], "rb") as f: release = tomllib.load(f) missing = 0 for artifact in release["artifact"]: status = requests.head(artifact["url"], timeout=10).status_code print(status, artifact["url"].rsplit("/", 1)[-1]) missing += status != 200 sys.exit(1 if missing else 0)

Run it on three Pythons:

# the laptop: works $ python3 check_release.py release.toml 200 camel-spring-boot-bom-4.20.0.pom 404 camel-spring-boot-bom-9.9.9.pom # a server whose python3 is 3.9 (RHEL 9 and Amazon Linux 2023 both ship 3.9) $ uv run --no-project --python 3.9 check_release.py release.toml File "check_release.py", line 3, in <module> import tomllib ModuleNotFoundError: No module named 'tomllib' # a clean server with a new enough Python, and nothing installed $ uv run --no-project --python 3.12 check_release.py release.toml File "check_release.py", line 5, in <module> import requests ModuleNotFoundError: No module named 'requests'

The obvious fix on a modern Debian or Ubuntu server doesn't work any more, and that is deliberate:

$ python3 -m pip install requests error: externally-managed-environment × This environment is externally managed ╰─> To install Python packages system-wide, try apt install python3-xyz, where xyz is the package you are trying to install. If you wish to install a non-Debian-packaged Python package, create a virtual environment using python3 -m venv path/to/venv.

Don't reach for --break-system-packages

This guard (PEP 668) exists because the system Python belongs to the operating system. apt, cloud-init and other system tools import from it. Upgrade requests there for your script, and you can break a tool the OS needs. The error message already names the right fix: a venv.

Pinning

Same commit, different bytes, again

Lesson 0.1a showed a jar changing between two builds of one commit. Python dependencies do the same thing, and the reason is a real difference from Maven.

A Maven pom names exact versions, and Maven Central never changes a published file. So the same pom.xml resolves the same tree next year, unless you use ranges or SNAPSHOTs. A Python package declares ranges. requests 2.34.2 says urllib3>=1.26,<3, and pip picks the newest version in the range on the day you install. Here is a one-line requirements file, requests, resolved as of 1 January 2023 and as of today:

$ uv pip compile --exclude-newer 2023-01-01 requirements.in -o lock-2023.txt $ uv pip compile requirements.in -o lock-today.txt $ diff lock-2023.txt lock-today.txt < certifi==2022.12.7 > certifi==2026.10.23 < charset-normalizer==2.1.1 > charset-normalizer==3.5.2 < idna==3.4 > idna==3.20 < requests==2.28.1 > requests==2.34.2 < urllib3==1.26.13 > urllib3==2.8.0 # a new major version

--exclude-newer tells uv to ignore anything published after that date. It replays the resolve someone would have got on 1 January 2023, so you can see drift without waiting for it. The output above is set side by side to fit; diff prints the two columns one above the other.

Five packages, five different versions. Now pin the one you asked for, requests==2.28.1, and resolve again:

$ diff p-2023.txt p-today.txt < certifi==2022.12.7 > certifi==2026.10.23 < idna==3.4 > idna==3.20 < urllib3==1.26.13 > urllib3==1.26.20

The package you pinned stayed put, and three of the four you didn't name still changed. Those are transitive dependencies, the dependencies of your dependencies. A requirements file that pins only what you import pins less than half of what runs.

What the file saysWhat it pinsSame install next year?

pip freeze also loses the difference between "we need this" and "this came along with something we need". Six months later nobody knows which lines are safe to delete, so upgrades stop happening.

The project shape

Two files: what works, and what ships

A modern Python project has the same split as a Maven build. pyproject.toml says which versions work. The lock file records exactly which versions you tested, so CI and every server install exactly those. uv init --package creates the layout, and uv add fills in both files:

pyproject.toml: what works

[project] name = "check-release" version = "0.1.0" requires-python = ">=3.11" dependencies = [ "requests>=2.34.2", ] [project.scripts] check-release = "check_release:main" [build-system] requires = ["uv_build>=0.9.10,<0.10.0"] build-backend = "uv_build"

uv.lock: what ships (one entry of six)

[[package]] name = "requests" version = "2.34.2" dependencies = [ { name = "certifi" }, { name = "charset-normalizer" }, { name = "idna" }, { name = "urllib3" }, ] sdist = { url = "…/requests-2.34.2.tar.gz", hash = "sha256:f288924c…60b9ed" }

[project.scripts] makes check-release a real command when the package is installed, so nobody needs to know where the .py file lives. Three things now fail early, with a clear message, on the laptop or in CI:

# the old server's Python is refused before anything runs $ uv run --python 3.9 check-release release.toml error: The requested interpreter resolved to Python 3.9.25, which is incompatible with the project's Python requirement: `>=3.11` (from `project.requires-python`) # exit 2 # someone added a dependency to pyproject.toml and didn't re-lock $ uv sync --locked The lockfile at `uv.lock` needs to be updated, but `--locked` was provided. To update the lockfile, run `uv lock`. # exit 1 # a downloaded file whose hash doesn't match (certifi's hashes altered by hand) $ .venv/bin/python -m pip install --require-hashes -r bad.txt ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE. certifi==2026.10.23 from https://files.pythonhosted.org/…/certifi-2026.10.23-py3-none-any.whl Expected sha256 09895e6e…aaf36cd Got e9b54de7…ba2f61d1

uv sync --locked belongs in CI

It is the Python equivalent of failing the build when the pom and the resolved tree disagree. Without --locked, uv quietly updates the lock to match, and CI tests a set of versions nobody reviewed.

Build once, deploy many

The wheel is the artifact

A wheel (.whl) is Python's jar: a zip file with your code and a metadata file, ready to install without building anything. uv build makes one:

$ uv build Successfully built dist/check_release-0.1.0.tar.gz Successfully built dist/check_release-0.1.0-py3-none-any.whl $ unzip -l dist/check_release-0.1.0-py3-none-any.whl 475 1980-01-01 00:00 check_release/__init__.py 54 1980-01-01 00:00 check_release-0.1.0.dist-info/entry_points.txt 278 1980-01-01 00:00 check_release-0.1.0.dist-info/METADATA … $ sha256sum dist/*.whl; rm -rf dist; uv build -q; sha256sum dist/*.whl 34dfa967a51cd5b4…9a22830d dist/check_release-0.1.0-py3-none-any.whl 34dfa967a51cd5b4…9a22830d dist/check_release-0.1.0-py3-none-any.whl

Every timestamp is 1980, so two builds of one commit give the same bytes. That is the property you had to switch on for the jar in Lesson 0.1a. The build backend gives it to you here.

The wheel does not carry your lock

Look inside its METADATA: Requires-Dist: requests>=2.34.2. That is the range from pyproject.toml, not the lock. Run pip install check_release-0.1.0-py3-none-any.whl on a server next year, and pip resolves fresh versions on the day: the drift from the previous section, back again. So ship two things: the wheel, and the lock exported with hashes.

On the server, that is four commands, and none of them resolves anything:

# in CI, once: export the lock as a hashed requirements file $ uv export --format requirements-txt --no-dev --no-emit-project -o requirements.lock.txt # on the server: a venv, the locked dependencies, then the wheel without its own resolve $ python3.12 -m venv /opt/check-release $ /opt/check-release/bin/python -m pip install --require-hashes -r requirements.lock.txt $ /opt/check-release/bin/python -m pip install --no-deps check_release-0.1.0-py3-none-any.whl $ /opt/check-release/bin/check-release release.toml 200 camel-spring-boot-bom-4.20.0.pom 404 camel-spring-boot-bom-9.9.9.pom

The wheel and the requirements file are the artifacts. Publish them to JFrog the same way you publish jars today: Artifactory has PyPI repositories, and pip installs from them with --index-url. Build once, promote the same files, install them everywhere.

Phase 2 makes this simpler. A container image holds the interpreter, the venv and the code as one artifact with one digest, so "which Python is on the server" stops being a question.

Small scripts

One file that declares what it needs

Not every Jenkins helper deserves a package. For a single script, put the requirements inside the script, in a comment block that tools read (PEP 723), and give it a lock file of its own:

$ uv add --script check_release.py requests # then set requires-python to >=3.11 by hand $ uv lock --script check_release.py # writes check_release.py.lock $ head -6 check_release.py # /// script # requires-python = ">=3.11" # dependencies = [ # "requests", # ] # /// $ uv run --locked check_release.py release.toml 200 camel-spring-boot-bom-4.20.0.pom 404 camel-spring-boot-bom-9.9.9.pom

uv run builds a private, cached venv for the script, from the lock. The Jenkins step becomes one line, and the script can't silently pick up Ubuntu's requests. The audit script that checks these lesson pages, assets/scripts/audit.py, is written this way.

One more thing for scripts other people depend on: a Python crash also exits with 1. In this script, "an artifact is missing" and "the script is broken" look the same to Jenkins. Give real outcomes their own codes, and document them.

Break it on three Pythons, then make it survive

Part 2: why it failed on the server

This block writes two files into labs/p0-5: the Python script from "Why it failed on the server" above, as check_release.py, and its list of artifacts, as release.toml. Paste it whole:

cd ~/IdeaProjects/devops-course/labs/p0-5 cat > check_release.py <<'EOF' """Check that every artifact a release needs exists before the deploy starts.""" import sys import tomllib import requests with open(sys.argv[1], "rb") as f: release = tomllib.load(f) missing = 0 for artifact in release["artifact"]: status = requests.head(artifact["url"], timeout=10).status_code print(status, artifact["url"].rsplit("/", 1)[-1]) missing += status != 200 sys.exit(1 if missing else 0) EOF cat > release.toml <<'EOF' # Artifacts the Interchange release needs. The check fails if any is missing. [[artifact]] url = "https://repo1.maven.org/maven2/org/apache/camel/springboot/camel-spring-boot-bom/4.20.0/camel-spring-boot-bom-4.20.0.pom" [[artifact]] url = "https://repo1.maven.org/maven2/org/apache/camel/springboot/camel-spring-boot-bom/9.9.9/camel-spring-boot-bom-9.9.9.pom" EOF ls

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

Someone ran pip install requests on the Jenkins agent, and the job still fails with No module named 'requests'. Give two ways that happens.

The install and the run used different interpreters. pip belongs to one Python, for example 3.12, and the job runs python3, which is 3.9. Each has its own sys.path, so the package is in a directory the job never searches.

Or it was installed with --user as a different user. User installs go under that user's home directory, and the Jenkins agent runs as jenkins. The fix for both: a venv for the job, installed with .venv/bin/python -m pip and run with .venv/bin/python.

requirements.txt says requests==2.28.1. The same commit is deployed a year apart and installs different code. How?

Only the direct dependency is pinned. requests declares ranges for its own dependencies, and pip picks the newest version in each range on the day. In the lab, three of four transitive packages changed while requests stayed put.

Fix: a lock file that pins every package, transitive ones included, with hashes, such as uv.lock exported with uv export, or pip-compile --generate-hashes. Install it with --require-hashes.

What does source .venv/bin/activate actually do, and does a Jenkins job need it?

It puts .venv/bin first on PATH, sets VIRTUAL_ENV, and changes the prompt. Nothing else: the venv works because of pyvenv.cfg next to the interpreter, not because of activate.

A job doesn't need it. Call .venv/bin/python directly. It is explicit in the log, and it doesn't depend on shell state surviving between steps.

Your team runs pip freeze > requirements.txt and calls it a lock file. What's weak about it?

It records the environment, not the project. Anything someone installed by hand to debug, a linter or ipython, gets frozen in and shipped to production. It has no hashes, so a changed file on the index isn't caught.

And it mixes direct and transitive dependencies with no record of which is which, so nobody can tell which lines are safe to remove or upgrade. Upgrades stop, and the pinned versions slowly collect known vulnerabilities.

You build a wheel in CI and install it on each server with pip install check_release-0.1.0-py3-none-any.whl. Is that build once, deploy many?

Only half of it. Your code is built once, but the wheel's metadata lists ranges (requests>=2.34.2), so each install resolves dependencies on the day. Two servers installed a week apart can run different urllib3.

Fix: ship the hashed lock export with the wheel. On each server, install -r requirements.lock.txt --require-hashes first, then the wheel with --no-deps. Nothing is resolved at deploy time, and both files are promoted through JFrog like a jar.
