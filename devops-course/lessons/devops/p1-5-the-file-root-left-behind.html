The File Root Left Behind

On Friday night someone ran the app by hand with sudo, "just to check it starts", and then stopped it. On Monday the service is restarted the normal way. It answers 200, the health check is green, and the log file hasn't had a line since Friday. Nothing crashed. One file now belongs to root, and the app isn't root. This lesson is the rule the kernel applies every time a program opens a file, from below: the owner, group and mode your Ansible playbooks have been setting for years.

~3 hours week 6 laptop; sudo only for the Build Ubuntu 26.04 · Docker · Ansible 2.21

Review · lesson 1.4

Two questions before you start

These are the two 1.4 questions where the "because" was missing. Answer each one out loud, without notes, before you open it. It's done when you get ¾ or better.

"Connection refused" against "connection timed out": what does each tell you, and where do you look for each?

Refused means the machine answered and nobody was listening. Timed out means nothing answered at all. Refused comes back in a millisecond, as a reset (RST) from the target's kernel, so the network path is fine. Look at the server: is the program running, and is it listening on that port and that address (ss -ltnp)? Timed out takes the full timeout, because the packets were dropped on the way. Look at firewalls, security groups, routing, and whether the IP is right at all.

dig api.internal returns the new IP, but the app keeps connecting to the old one. Give two reasons.

The app doesn't ask DNS the way dig does. First, /etc/hosts. The app's lookups go through nsswitch.conf, which checks files first, so an old entry there wins. dig skips it. getent hosts api.internal shows what the app really gets. Second, caching. The JVM keeps lookups for 30 seconds by default, and longer if networkaddress.cache.ttl is set.

The mechanism

A process carries numbers, a file carries numbers, and the kernel compares them

Every process runs as a user ID (UID) and a group ID (GID), plus a list of supplementary groups. Every file's inode, the record you met in Lesson 1.1, stores an owner UID, a group GID and twelve mode bits. When a process calls open(), the kernel compares the two sets of numbers and picks one row of the mode to apply:

1

Is the process root (UID 0)?Read and write are allowed whatever the bits say. Execute still needs at least one x bit set somewhere.

2

Is the process the file's owner?Use the owner bits, and stop. The group and other bits are never looked at, even if they'd allow more.

3

Is the file's group one of the process's groups?Use the group bits, and stop.

4

Everyone elseUse the other bits.

The first match decides, and nothing falls through to the next rung. If the chosen row says no, the call fails with EACCES, which prints as "Permission denied".

In the library: your UID is the number on your library card, and your groups are the society memberships stamped on the back. Each book has a slip inside the cover with three lines: what its owner may do, what members of one society may do, and what everyone else may do. The librarian reads one line, the first that applies to you, and doesn't read on.

Who the process is

Names are for people; the kernel only sees numbers

$ id uid=1000(al) gid=1000(al) groups=1000(al),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users),114(lpadmin),126(docker),995(input) $ grep -E '^(Uid|Gid|Groups|Umask)' /proc/self/status Umask: 0002 Uid: 1000 1000 1000 1000 # real, effective, saved, filesystem Gid: 1000 1000 1000 1000 Groups: 4 24 27 30 46 100 114 126 995 1000 $ getent passwd al root nobody | cut -d: -f1,3,4,6,7 al:1000:1000:/home/al:/bin/bash # name : UID : GID : home : shell root:0:0:/root:/bin/bash nobody:65534:65534:/nonexistent:/usr/sbin/nologin

/etc/passwd and /etc/group only translate numbers into names for people to read. Inside a container, which has its own /etc/passwd, your UID still works but has no name:

$ docker run --rm -u "$(id -u):$(id -g)" php:8.2-cli id uid=1000 gid=1000 groups=1000 # the same number, no name for it in there

/proc/PID/status works for any process, not only your shell, so it's how you ask what a running service is: grep -E 'Uid|Groups|Umask' /proc/$(pidof -s java)/status. That matters below, because a running process's groups can differ from what id username says now.

What the file carries

Owner, group, and twelve bits

$ stat -c '%A %a %U:%G %n' ~ /etc/passwd /etc/shadow /tmp /usr/bin/passwd /var/log/journal drwxr-x--- 750 al:al /home/al -rw-r--r-- 644 root:root /etc/passwd -rw-r----- 640 root:shadow /etc/shadow drwxrwxrwt 1777 root:root /tmp -rwsr-xr-x 4755 root:root /usr/bin/passwd drwxr-sr-x 2755 root:systemd-journal /var/log/journal

Take the first one, drwxr-x---, apart:

dtype rwxowner al r-xgroup al ---others

Each group of three is a sum: r = 4, w = 2, x = 1. So rwx is 7, r-x is 5, --- is 0, and the mode is 750. The fourth, leading digit holds the three special bits, covered below; it's the 1 in 1777 and the 4 in 4755.

ModeStringTypical use
644-rw-r--r--Config files, jars: the owner writes, everyone reads
640-rw-r-----Logs and secrets: the owner writes, one group reads, others nothing
600-rw-------SSH private keys, credentials files. ssh refuses a key that's more open than this
755-rwxr-xr-xScripts and programs; ordinary directories
750drwxr-x---A directory only its owner and one group may enter

The owner's row wins, even when it's the worst row

$ echo secret > mine; chmod 077 mine $ ls -l mine ----rwxrwx 1 al al 7 Nov 18 17:10 mine # group and others: everything. Owner: nothing $ cat mine cat: mine: Permission denied

You own the file and you're in its group, and everyone else could read it, but you can't. Rung 2 matched, so the group and other bits were never consulted. You can still chmod it back, because changing the mode depends on owning the file, not on the bits.

Directories

A directory is a list of names, and its bits guard the list

Lesson 1.1 showed that a directory is a table of names pointing to inodes. Its three bits mean different things from a file's:

BitOn a directory it allowsWithout it
rReading the list of names (ls)You can't list it, but you can still open a file whose name you already know
wChanging the list: create, delete, rename (needs x too)No new files, and no deleting, even files you own
xPassing through it to anything inside ("search")Nothing inside can be opened, whatever the inside's own bits say
# r without x: you can read the names, nothing else $ chmod 644 ronly; ls -l ronly -????????? ? ? ? ? ? f $ cat ronly/f cat: ronly/f: Permission denied # x without r: no list, but a known name opens $ chmod 311 xonly; ls xonly ls: cannot open directory 'xonly': Permission denied $ cat xonly/known b # deleting is a change to the directory, not to the file $ chmod 444 d/locked; echo more >> d/locked bash: d/locked: Permission denied # the file says no $ rm -f d/locked && echo "rm ok" rm ok # the directory said yes $ chmod 555 d; rm -f d/f2 rm: cannot remove 'd/f2': Permission denied

That's Lesson 1.1's rm again: it removes a name from a directory, so it's the directory's w bit that counts. A read-only file in a directory you can write to can be deleted, and a writable file in a read-only directory can't.

Every directory on the path needs x

To open /a/b/c/file, the kernel walks the path one name at a time, and each directory on the way must give you x. namei -l shows the whole walk in one command:

$ namei -l ~/IdeaProjects/interchange/services/reference/target/reference-0.1.0-SNAPSHOT.jar drwxr-xr-x root root / drwxr-xr-x root root home drwxr-x--- al al al # others: no x. Nobody but al gets past here drwxrwxr-x al al IdeaProjects drwxrwxr-x al al interchange … -rw-rw-r-- al al reference-0.1.0-SNAPSHOT.jar

The jar itself is readable by everyone (r for others), and no other user can read it, because /home/al is 750. Ubuntu has created home directories like this since 21.04 (HOME_MODE 0750 in /etc/login.defs). Java's message when it can't reach the jar doesn't mention permissions at all:

$ chmod 000 h; java -jar h/app.jar Error: Unable to access jarfile h/app.jar

This is the first thing that goes wrong in this lesson's Build, so remember it.

New files

umask: the bits a new file doesn't get

A program creating a file asks for a mode, usually 666 for files and 777 for directories. The kernel removes the bits set in the process's umask. With the same touch and mkdir:

umask 002 -rw-rw-r-- 664 u002 drwxrwxr-x 775 ud002 # Ubuntu's default for a login umask 022 -rw-r--r-- 644 u022 drwxr-xr-x 755 ud022 # systemd's default for system units umask 027 -rw-r----- 640 u027 drwxr-x--- 750 ud027 # services that write logs

It isn't subtraction: a bit that was never requested can't be removed, so a file never gets x from a umask. The umask belongs to the process and is inherited by its children, which is why the same app creates 664 files when you start it from a shell and 644 ones under a system unit. Your reference user unit shows Umask: 0002 in its /proc status, inherited from your login session. A system unit sets it with UMask=.

Groups

Group membership is read once, at login

A process gets its supplementary groups when the login program sets them up (a terminal, SSH, sudo, a systemd service start), and keeps them until it exits. Its children inherit them. Adding a user to a group changes /etc/group, and nothing that's already running notices:

$ sudo usermod -aG docker deploy $ id deploy # reads /etc/group now: docker is there $ grep Groups /proc/$(pidof -s java)/status # the Jenkins agent, started last week: docker isn't

So "I added the user to the group and it still says Permission denied" means the process started before the change. Log in again, or restart the service. For a shell, newgrp docker starts a new one with the group.

The -a in usermod -aG

usermod -G docker deploy, without -a, replaces the user's supplementary groups with just docker, so they drop out of every other group. The Ansible user module does the same unless you set append: true. A one-letter difference that takes someone out of sudo.

The leading digit

setuid, setgid and the sticky bit

BitShown asOn a fileOn a directorySeen at
4 · setuidrws ownerRuns as the file's owner, not as the callerIgnored on Linux/usr/bin/passwd 4755: you run it, it runs as root, so it can write /etc/shadow
2 · setgidrws groupRuns with the file's groupNew files inside get the directory's group, not the creator's/var/log/journal 2755: every journal file is group systemd-journal. Shared team directories
1 · stickyt othersIgnoredOnly a file's owner (or the directory's owner, or root) may delete or rename it/tmp 1777: everyone can write there, and nobody can delete anyone else's files

The sticky bit, with two container UIDs sharing a directory on the laptop:

# mode 777: uid 4242 creates a file, uid 4343 deletes it 777: uid 4343 deleted it # mode 1777: the same again rm: cannot remove '/s/theirs': Operation not permitted

Notice the message changed. "Permission denied" (EACCES) means the rwx bits said no. "Operation not permitted" (EPERM) means a rule beyond the bits said no: the sticky bit, or trying to chown a file without being root. The wording tells you which kind of rule to look for.

root

What root skips, and the files it leaves behind

Root passes rung 1: it reads and writes anything, and needs just one x bit to execute. Docker's default user is root, which makes it an easy way to try this without sudo:

$ chmod 000 zero s.sh # a text file and a script, no bits at all $ docker run --rm -v "$PWD:/w" php:8.2-cli sh -c 'cat /w/zero; /w/s.sh; echo "exit $?"' top # root read it sh: 1: /w/s.sh: Permission denied # root can't run it: no x anywhere exit 126 # 126: found, not executable (137 was killed, Lesson 1.2)

The real danger isn't what root can do. It's what root creates. A file created by a root process is owned by root, with root's umask, and stays that way after the process has gone. Here is this lesson's opening story, in five lines:

$ docker run --rm -v "$PWD/logs:/logs" php:8.2-cli bash -c 'id; echo started > /logs/app.log' uid=0(root) gid=0(root) groups=0(root) $ ls -l logs -rw-r--r-- 1 root root 8 Nov 18 17:10 app.log # in your directory, owned by root $ echo "appended" >> logs/app.log bash: logs/app.log: Permission denied # your app can't write its own log $ rm -f logs/app.log && echo "rm ok" rm ok # and yet you can delete it: your directory $ docker run --rm -u "$(id -u):$(id -g)" -v "$PWD/logs:/logs" php:8.2-cli bash -c 'echo started > /logs/app.log' $ ls -l logs -rw-r--r-- 1 al al 8 Nov 18 17:10 app.log # run as your UID: your file

What does the app do when it can't open its log? Spring Boot's Logback, tested with a log file the app's user can't write:

|-ERROR in ch.qos.logback.core.rolling.RollingFileAppender[FILE] - openFile(…/reference.log,true) call failed. java.io.FileNotFoundException: …/reference.log (Permission denied) |-WARN in ch.qos.logback.core.rolling.RollingFileAppender[FILE] - Attempted to append to non started appender [FILE]. … Tomcat started on port 8099 (http) … Started ReferenceApplication in 1.176 seconds $ curl -s -o /dev/null -w '%{http_code}\n' localhost:8099/customers/C001 200 $ stat -c '%A %s %n' reference.log ---------- 0 reference.log # 0 bytes: the file log is dead, the app isn't

The app keeps serving and only the file log goes dark, just as in Lesson 1.1's postmortem. The one clue is a single ERROR at startup, on the console, which under systemd means the journal.

Ports below 1024 are the other thing root is for: net.ipv4.ip_unprivileged_port_start = 1024 on this laptop. That's why Java apps listen on 8080 or 8081 and a load balancer or nginx takes 443.

Ansible

The mode your playbook really set

The file, copy and template modules all take owner, group and mode. The mode is where a playbook that "worked" sets the wrong bits. Three tasks, run against three empty files:

- ansible.builtin.file: { path: a1, mode: 644 } # unquoted - ansible.builtin.file: { path: a2, mode: "644" } # quoted - ansible.builtin.file: { path: a3, mode: "0644" } # quoted, leading zero $ stat -c '%A %a %n' a1 a2 a3 --w----r-T 1204 a1 -rw-r--r-- 644 a2 -rw-r--r-- 644 a3

YAML reads an unquoted 644 as the decimal number six hundred and forty-four. In octal that's 1204: the sticky bit, write-only for the owner, nothing for the group, read for others. All three tasks reported changed and none failed. An unquoted 0644 happens to work, because YAML 1.1 reads a leading zero as octal, which is the other form the Ansible docs accept. Quoting with the zero, "0644", is the habit that's safe whichever YAML parser reads it.

systemd

Running a service as its own user

A service runs as root unless its unit says otherwise. These lines in the [Service] section put the rules above together:

LineWhat it does
User=, Group=The UID and GID the process runs as. In a user unit, the only allowed value is yourself, so a service with its own user needs a system unit in /etc/systemd/system/
LogsDirectory=nameCreates /var/log/name before start, owned by User=. Also StateDirectory= (/var/lib) and RuntimeDirectory= (/run)
UMask=The umask of the service. The default for system units is 0022; 0027 keeps logs away from other users

A detail from systemd.exec(5) that matters on Monday morning: if the directory is owned by the wrong user, systemd changes the owner of everything inside it. If the directory is already owned by the right user, "files and directories below of them are left as-is, even if they do not match". So a root-owned file inside a correctly owned LogsDirectory is not repaired. You'll see this happen in the Build.

Never link a system unit from your home

In Build 3 you ran systemctl --user link on the unit in the repo, and for a user unit that's fine. A system unit runs as root, so whoever can edit the file can make root run anything. A unit file that you can write, linked into /etc/systemd/system, hands root to your account and to anything running as you. Install a root-owned copy instead: sudo install -m 0644.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence. In 1.4 you had the what every time and missed the because; that's what each of these is scored on.

On Monday the app answers 200 but its log hasn't changed since Friday. ls -l shows -rw-r--r-- root root reference.log in a directory owned by the app's user. What happened, how do you prove it, and how do you fix it?

Someone ran the app as root, and root created the log file. A file belongs to whoever created it, so the new log is root's, 644. The app's user matches rung 4 (other), which has only r, so Logback's open() fails with Permission denied. Logback prints one ERROR at startup and the app carries on serving. Prove it with journalctl -u app (the openFile … (Permission denied) line) and find /var/log/app ! -user app. Fix: chown app:app the file and restart. Prevent it by never starting the app by hand as root: use systemctl start, or sudo -u app.

A file is ----rwxrwx, owned by you, group is one of your groups. Can you read it? Why?

No. The kernel uses the first rung that matches. You're the owner, so it applies the owner bits, ---, and stops. The group and other bits are never consulted, even though they'd allow it. You can chmod it back, because changing the mode depends on being the owner, not on the bits.

You chmod 444 a file so nobody can delete it, and another user deletes it anyway. Why, and what would have stopped them?

Deleting changes the directory, not the file. rm removes a name from the directory's list, so it needs w and x on the directory, and the file's own bits don't matter. To stop it, remove w from the directory, or set the sticky bit (chmod +t, as on /tmp), which lets only the file's owner, the directory's owner or root delete it. The error is then "Operation not permitted".

You run usermod -aG docker jenkins, but builds on the agent still fail with "permission denied" on /var/run/docker.sock. id jenkins shows docker. Why, and what do you do?

Groups are given to a process when it starts, and the agent started before the change. id jenkins reads /etc/group now; the running agent still has its old group list, which you can see in /proc/PID/status under Groups. Restart the agent so it starts with the new groups. And check that it was -aG: plain -G would have removed jenkins from every other group.

A playbook sets mode: 644 on a config file, reports changed, and then the app can't read its config. What mode did the file get, and why?

1204, shown as --w----r-T. Unquoted, YAML reads 644 as a decimal number, and 644 in octal is 1204: the sticky bit, write-only for the owner, nothing for the group, read for others. If the app runs as the owner, rung 2 applies, and -w- has no read. Ansible doesn't fail, because 1204 is a valid mode. Fix: quote it, mode: "0644", everywhere.

Build 5 · Interchange

Run reference as its own user

Today reference runs as you, from your home directory, so any bug in it can do anything you can. After this build it runs as a system user that can read its jar, write its log directory, and nothing else. This build needs sudo, so you run every command yourself. Predict before each step.

  1. Predict: if you only added User=interchange to the existing user unit, what would happen? And if you moved it to a system unit but left ExecStart pointing at the jar in ~/IdeaProjects?
  2. The user. A system account with no home and no login shell: sudo useradd --system --user-group --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin interchange, then getent passwd interchange and id interchange.
  3. The artifact, owned by root. The service may read its code and not change it: ./mvnw -pl services/reference -am package, then sudo install -D -o root -g root -m 0644 services/reference/target/reference-0.1.0-SNAPSHOT.jar /opt/interchange/reference.jar. Check the walk with namei -l /opt/interchange/reference.jar.
  4. The unit. Write infra/systemd/interchange-reference.service, a system unit. Start from Build 3's unit and change: User= and Group= interchange; LogsDirectory=interchange; Environment=LOGGING_FILE_NAME=/var/log/interchange/reference.log (Spring reads it as logging.file.name); UMask=0027; ExecStart on /opt/interchange/reference.jar; no WorkingDirectory under your home; WantedBy=multi-user.target. Keep MemoryMax, MemorySwapMax, Restart and the JVM flags.
  5. Swap over. Port 8081 can only have one listener: systemctl --user disable --now reference, then sudo install -m 0644 infra/systemd/interchange-reference.service /etc/systemd/system/, sudo systemctl daemon-reload, sudo systemctl enable --now interchange-reference.
  6. Verify. ps -o user,group,pid,cmd -C java; curl localhost:8081/customers/C001; sudo ls -l /var/log/interchange/ (predict the owner and mode first); sudo -u interchange touch /opt/interchange/x (predict).
  7. Read the log as yourself. Predict, then try tail /var/log/interchange/reference.log. Add yourself to the group with sudo usermod -aG interchange $USER and try again in the same terminal. Then in a new login. Explain the difference.
  8. Drill: the file root left behind. sudo systemctl stop interchange-reference, sudo rm /var/log/interchange/reference.log, sudo touch /var/log/interchange/reference.log, then start it again. Predict: does it start? Does systemd fix the file's owner? Does a request reach the log? Then find it with the method table, fix it, and prove the fix.
  9. Commit the unit file, with a comment on each line you added.

Done when: ps shows interchange, a request appears in /var/log/interchange/reference.log, the service user can't write to /opt/interchange, and you can explain each failure you hit on the way.

Where this comes back

In Phase 2 every container image runs as root unless its Dockerfile says USER, and a container running as root that writes to a bind mount leaves exactly the files from Part 4 on the host. In Phase 5 Kubernetes asks the same questions in YAML: runAsUser, runAsNonRoot: true, and fsGroup, which is the setgid directory again: a volume whose files all get the pod's group. The UIDs are the same numbers on both sides, and that's why they line up.
