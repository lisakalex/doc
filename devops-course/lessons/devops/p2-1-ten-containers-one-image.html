Ten Containers, One Image

The build agent's disk is full again. docker images lists forty images at about 600 MB each, which adds up to 24 GB. du on /var/lib/docker says 9 GB. Both are right. A Docker image isn't one file: it's a stack of read-only layers, and an image that shares a layer with another one stores that layer once. A running container adds one thin writable layer on top, and the first time it changes a file, the whole file is copied up into that layer. This lesson is that mechanism, from below, on the reference service you built in Phase 1.

"Connection refused" against "connection timed out": what does each tell you, and where do you look for each?

Refused means the machine answered and nobody was listening. Timed out means nothing answered at all. Refused comes back in a millisecond, as a reset (RST) from the target's kernel, so the network path is fine. Look at the server: is the program running, and is it listening on that port and that address (ss -ltnp)? Timed out takes the full timeout, because the packets were dropped on the way. Look at firewalls, security groups, routing, and whether the IP is right at all.

dig api.internal returns the new IP, but the app keeps connecting to the old one. Give two reasons.

The app doesn't ask DNS the way dig does. First, /etc/hosts. The app's lookups go through nsswitch.conf, which checks files first, so an old entry there wins. dig skips it. getent hosts api.internal shows what the app really gets. Second, caching. The JVM keeps lookups for 30 seconds by default, and longer if networkaddress.cache.ttl is set, so a long-running app may not look again until it restarts.

The mechanism

Read-only layers, one writable layer, and a filesystem that merges them

An image is an ordered list of layers. Each layer is a tar archive of the files that one build step added, changed or deleted, and it never changes after it's built. A container is those same layers, read-only, plus one new, empty, writable layer on top that belongs to that container alone.

The kernel joins them with overlayfs, the overlay2 storage driver. It shows the process one merged directory tree. Reading a file finds it in the topmost layer that has it. Writing always goes to the writable layer:

The container…What overlayfs doesWhat it costs
reads a file from the imageReads it straight from the read-only layerNothing; every container shares the same copy
creates a new fileWrites it in the writable layerThe file's size
changes a file from the image, even by one byteCopy-up: copies the whole file into the writable layer first, then changes the copyThe whole file's size
deletes a file from the imageWrites a whiteout in the writable layer that hides itNothing freed: the file is still in the layer below

In the library: the image is a reference book on the shelf, one copy, that nobody may write in. Every reader who sits down with it gets their own sheet of tracing paper laid over the page, and that's the writable layer. Ten readers means ten sheets and still one book. To change a paragraph, you first trace the whole page onto your sheet, then change it there: copy-up. To "remove" a page, you put a "removed" sticker on your sheet. The page is still in the book for anyone who lifts the sheet.

Where layers come from

One layer per build step that changes files

Every RUN, COPY and ADD in a Dockerfile makes a layer holding exactly what that step changed. ENV, WORKDIR, CMD, USER and EXPOSE only change the image's config, so they show as 0B. Here is reference on the Temurin JRE, newest layer first:

$ docker history ref:multi --format '{{.Size}}\t{{.CreatedBy}}' 0B CMD ["java" "-jar" "app.jar"] 23.6MB COPY /src/services/reference/target/referenc… # our one layer 0B WORKDIR /app 0B ENTRYPOINT ["/__cacert_entrypoint.sh"] 5.98kB COPY --chmod=755 entrypoint.sh /__cacert_ent… 0B RUN /bin/sh -c set -eux; echo "Verifying… 166MB RUN /bin/sh -c set -eux; ARCH="$(dpkg --… # unpacks the JRE 0B ENV JAVA_VERSION=jdk-21.0.13.1+2 68.6MB RUN /bin/sh -c set -eux; apt-get update;… … 102MB umoci raw add-layer --image /home/buildd/roc… # Ubuntu 26.04

Three lines from our own Dockerfile, and only one of them adds anything. Everything below WORKDIR /app came with FROM eclipse-temurin:21-jre. Each layer is named by the SHA-256 of its contents, so two images built on the same base point at the same layers, and Docker stores them once.

Ten containers

Why ten containers don't use ten images of disk

Ten copies of reference, all started from one image:

$ for i in $(seq 1 10); do docker run -d --name ten$i ref:multi; done $ docker ps -s --format '{{.Names}}\t{{.Size}}' ten1 34.4kB (virtual 359MB) ten2 34.4kB (virtual 359MB) … ten10 34.4kB (virtual 359MB)

docker ps -s gives two numbers. The first is the container's own writable layer: what it has written since it started (Tomcat's work directory and the JVM's perf data in /tmp). "Virtual" is that plus the image it stands on. Ten containers cost ten times 34 kB, plus one image: about 359 MB in total, not 3.6 GB.

The same sharing works between images. docker system df -v splits each image into what it shares and what is its own:

$ docker system df -v REPOSITORY TAG SIZE SHARED SIZE UNIQUE SIZE CONTAINERS ref multi 359MB 335.8MB 23.61MB 10 ref alpine 238MB 214.1MB 23.61MB 0 eclipse-temurin 21-jre 336MB 335.8MB 0B 0 eclipse-temurin 21-jre-alpine 214MB 214.1MB 0B 0 maven 3.9-eclipse-temurin-21 539MB 539MB 0B 0

The SIZE column is what docker images prints, and adding it up counts every shared layer again for each image that uses it. That's the build agent in the opening: forty images on the same few bases look like 24 GB and take 9 GB. The real figure is the "Images" line of docker system df, or the UNIQUE SIZE column added up, plus the shared layers once.

Memory works the same way. When ten containers read the same app.jar, they read one file in one lower layer, so the kernel keeps one copy of it in the page cache (lesson 1.2), not ten.

Copy-on-write

One byte changed, the whole file copied

A running container appends one byte to the 23.6 MB jar that came from the image:

$ docker ps -s --filter name=cow1 --format '{{.Size}}' 35kB (virtual 359MB) $ docker exec cow1 sh -c 'echo x >> /app/app.jar' $ docker ps -s --filter name=cow1 --format '{{.Size}}' 23.6MB (virtual 383MB) # the whole jar, copied up

overlayfs can't change a file inside a read-only layer, so on the first write it copies the entire file into the writable layer and changes the copy. From then on, the container sees only its copy. A 2 GB file with one line appended costs 2 GB per container.

docker diff lists what the writable layer holds, as A (added), C (changed) and D (deleted):

$ docker diff cow1 C /app C /app/app.jar # copied up, then changed A /app/logs A /app/logs/reference.log # the app's own log file A /tmp/note C /tmp A /tmp/hsperfdata_root/1 …

Look at /app/logs/reference.log. The app wrote its log into the writable layer, because application.properties still says logging.file.name=logs/reference.log, relative to the working directory. The writable layer is deleted with the container. After docker rm, that log is gone. In a container the log goes to stdout, where docker logs collects it, and data that must outlive the container goes on a volume (lesson 2.4).

Deleting

A file deleted in a later layer is still in the image

Two Dockerfiles that both end with no /big file:

# two steps FROM alpine:latest RUN dd if=/dev/zero of=/big bs=1M count=100 RUN rm /big
# one step FROM alpine:latest RUN dd if=/dev/zero of=/big bs=1M count=100 && rm /big
$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' cow:two-steps 113MB cow:one-step 8.43MB alpine:latest 8.43MB $ docker history cow:two-steps --format '{{.Size}}\t{{.CreatedBy}}' 0B RUN /bin/sh -c rm /big # buildkit # only a whiteout 105MB RUN /bin/sh -c dd if=/dev/zero of=/big bs=1M… # still here

A layer never changes once it's built. The rm step can only add a whiteout on top, so the 100 MB stays in the layer below. In one RUN, the file is created and removed before the layer is saved, so it never reaches any layer. That's why Dockerfiles write apt-get update && apt-get install … && rm -rf /var/lib/apt/lists/* as one line.

A deleted secret is still in the image

The same rule applies to a password file. This image copies one in and deletes it in the next step. The container can't see it, but anyone who can pull the image can read it:

$ docker run --rm cow:secret ls /tmp/db.password ls: /tmp/db.password: No such file or directory $ docker save cow:secret -o s.tar && tar -xf s.tar -C x $ for l in x/blobs/sha256/*; do tar -tf $l | grep password; done tmp/.wh.db.password # the whiteout, in the top layer tmp/db.password # the file, in the layer below $ for l in x/blobs/sha256/*; do tar -xOf $l tmp/db.password; done not-a-real-password-123

Pass build-time secrets with RUN --mount=type=secret, which never writes them into a layer, and runtime secrets as environment or mounted files when the container starts.

On disk

Where the layers live

Inside a container, the root filesystem is one overlay mount. Its options name every layer:

$ docker exec ten1 grep ' / ' /proc/mounts overlay / overlay rw,relatime,lowerdir=…,upperdir=/var/lib/docker/overlay2/b718…/diff,workdir=… $ docker exec ten1 sh -c 'grep -o "lowerdir=[^,]*" /proc/mounts | tr ":" "\n" | wc -l' 9
  • lowerdir: the read-only layers, joined with colons. Here that's the image's eight layers plus one small -init layer that Docker adds for each container, with the empty /etc/hosts, /etc/hostname and /etc/resolv.conf it mounts over. Every container from this image shares the same eight.
  • upperdir: this container's writable layer. It's a plain directory under /var/lib/docker/overlay2/, and sudo ls on it shows exactly what docker diff lists.
  • workdir: overlayfs's scratch space for copy-up.

All of it is under /var/lib/docker, on the host's root filesystem unless someone moved it. That's how containers fill the disk of the host they run on, which takes you back to lesson 1.1.

Who runs it

Every image here runs as root, unless the Dockerfile says otherwise

$ docker run --rm eclipse-temurin:21-jre id uid=0(root) gid=0(root) groups=0(root)

Lesson 1.5 again: a process in a container is an ordinary process on the host, with the same UID numbers. Root in the container is UID 0 on the host's files that it can reach, through a bind mount, for example. A USER line in the Dockerfile picks the user; the user must exist in the image (useradd in a RUN). Its UID is the image's own count, not the host's: useradd --system gave interchange UID 999 in the Temurin image and UID 997 on your laptop.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

A build agent's docker images adds up to 24 GB, but /var/lib/docker uses 9 GB. Which number is right, and how do you see the real one?

9 GB is right; the 24 GB counts shared layers many times. Each image's SIZE includes every layer it stands on, and most images on one agent share their base layers, which are stored once, named by their SHA-256. docker system df counts each layer once; docker system df -v splits every image into SHARED SIZE and UNIQUE SIZE.

A Dockerfile downloads a 300 MB tarball in one RUN, unpacks it, and deletes it in the next RUN. The image is still 300 MB bigger. Why, and what's the fix?

Layers never change once they're built, so the second RUN can only hide the file with a whiteout. The tarball is still in the layer below, and it's pulled and stored with the image. Download, unpack and delete in the same RUN, joined with &&, so the tarball never reaches a saved layer. Or unpack it in a build stage and copy only the result into the final image (lesson 2.2).

A Dockerfile copies settings.xml with a repository password in, runs mvn package, and deletes it in the next step. Is the password safe?

No. It's in the layer the COPY made, and anyone who can pull the image can read it. The delete only adds a whiteout. docker save and tar get it back in two commands, and so does anything that reads the registry. Use RUN --mount=type=secret, which makes the file available to that one step without writing it into any layer. Then rotate the password, because it's already in every copy of the old image.

A container appends one line to a 2 GB data file that came with its image. How much does its writable layer grow, and why? What happens with ten such containers?

About 2 GB each, so 20 GB for ten. overlayfs can't change a file in a read-only layer, so the first write copies the whole file up into the container's writable layer and changes the copy. Every container makes its own copy. Data that a container changes belongs on a volume, not in the image.

You run reference in a container, and its log goes to /app/logs/reference.log. You docker rm the container and start a new one. Where is yesterday's log?

Gone. The file was in the container's writable layer, which is deleted with the container. A new container starts with a new, empty writable layer on the same read-only image. In a container, log to stdout so docker logs (and later the platform) collects it; put anything that must outlive the container on a volume.

Interview answer · 60 seconds, spoken

"What's actually in a Docker image, and what happens on disk when you start ten containers from it?"

Mechanism first: read-only layers, one per build step, shared between images by their hash; one thin writable layer per container; overlayfs merges them; copy-up on the first write. Then the consequences: ten containers cost ten small writable layers and one image; RUN rm doesn't shrink an image and doesn't hide a secret; a container's own files, logs included, are deleted with it. End with Build 6, the jar in an image as its own user, in one sentence. Say it with a timer, then type what you said.

Where this comes back

In lesson 2.2 the build cache turns out to be these same layers: a step is reused while everything above it is unchanged, so the order of your Dockerfile decides whether a one-line Java change rebuilds in 3 seconds or 23.
