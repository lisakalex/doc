Project brief · runs weeks 3–24

The Interchange Project

An enterprise integration platform, built on the stack you already know and deployed on the infrastructure you do not. Four services, one queue, one database, and eight failures you cause on purpose — each one a question you got wrong, turned into an incident you fix and write up.

~70 hours 4 services 8 postmortems about $20 of AWS

Why this and not the book's example

You have already read the books. That is the problem this solves

Brikman and Burns are the two best books in print on Terraform and Kubernetes, they are both sitting in your read/ folder, and you scored 1/8 and 0/8 on those subjects. That is not a failure of the books. It is what reading produces: the vocabulary arrives and the mechanisms do not. Working through their examples would run the same experiment a third time.

Their examples are also deliberately trivial — a Hello-World web server on an autoscaling group, a toy frontend and backend — because the tool is meant to be the only thing you think about. Excellent teaching. Worthless as portfolio, and every interviewer in the country has seen them.

What makes this one worth building instead

All the difficulty is in the right layer. Apache Camel is the open-source cousin of MuleSoft — routes, endpoints, transformations, the same enterprise integration patterns. You already know the application. So no weekend disappears into a Java problem, and every hour of confusion lands on Terraform, containers, EKS and observability, which is where the gaps are.

It is the migration your market is paying for. Java integration shops moving off on-prem middleware onto Kubernetes is a live, well-funded, deeply unglamorous pattern — and it is the agency-placed enterprise half where Jenkins sits at 29.5% and your CV already half-fits.

You can be interrogated about it. “Why Camel routes rather than a REST service?” “What happened to in-flight exchanges during a rolling update?” Those are questions you can answer from experience. That is the entire reason to have a project.

The system

Four services, deliberately more than one

Everything you have operated has been one application and its database. Partial failure — one thing down while another is up, a queue filling, a timeout cascading — only exists once services talk to each other, and it is most of what makes this job hard.

Camel / Spring Boot

ingest

Accepts orders over HTTP and from a file drop. Validates, normalises, publishes to the queue. The Camel showcase: routes, endpoints, a transformation, a dead-letter channel.

Two input channels, because one of them will be awkward and that is the point.

Camel / Spring Boot

enrich

Consumes the queue, calls reference to fill in customer and product detail, writes the completed order to Postgres. Retries, backoff, and a dead-letter queue it cannot avoid.

Where idempotency lives. It will process the same message twice and you will have to make that safe.

Spring Boot, plain REST

reference

Holds customer and product reference data. Small, boring, and deliberately the weak dependency — most of the incident drills start by making this slow rather than making it fail.

Slow is harder than down. Down is obvious; slow takes everything with it.

Spring Boot, plain REST

status-api

Read-only API over the Postgres data, fronted by the ALB. The thing a user would actually hit, and the thing that returns 502s when a rollout goes wrong.

Your availability SLO is measured here, not on the internals.

The point of the whole thing

Eight failures you cause on purpose

Not bugs you happen to hit. Scheduled, deliberate breakage at the layer you have just finished learning. Each one is a question from the placement that you got wrong — made to happen to a system you built, so that the next time it happens you recognise it from the symptoms.

Each one gets written up, and the write-up is the deliverable

Interviews ask you to walk through an incident. “I have been in the room” is a visibly weaker answer than “I was paged at 2am, here is what I checked first, and here is what I got wrong before I found it.” Eight written incidents about your own system is the closest honest substitute for a pager you have never carried — and unlike a real one, you get to choose the curriculum.

The template, same every time

What broke one sentence, in user terms, not system terms
Impact how many, how long, what they saw
Timeline detected → diagnosed → mitigated → resolved, with clock times
How I found it which signal, and which three I looked at first that were useless
Root cause the mechanism, not the trigger
What I got wrong the hypothesis you chased for twenty minutes
Fix what changed, and how you know it worked
Prevention the alert, limit or test that catches it next time

“What I got wrong” is not there for humility. It is the line that proves you were actually debugging rather than reciting, and it is the one an interviewer will follow up on.

Build order

What exists at the end of each phase

The system is rebuilt at a higher level in each phase rather than assembled once. Phase 3 is deliberately thrown away by phase 4 — clicking it together by hand first is what makes the Terraform mean something.

0

Nothing yet weeks 1–2

Write the brief and the architecture sketch. Pick the domain, name the four services, draw the boxes. Set up the repository with a sane layout. That is all — no code.

1

It runs on one Linux box weeks 3–6

Build reference and status-api as plain Spring Boot. Postgres on the same box. systemd units rather than cron. Deliberately break it at the filesystem and memory layers. No containers, no cloud. One machine you fully understand.

2

It runs in containers weeks 7–10

Containerise all four services. Multi-stage builds against your Maven stack. Compose for the whole system locally. Camel routes doing real work between them. First encounter with partial failure.

3

It runs on AWS, built by hand weeks 11–14

VPC, subnets, security groups, RDS, SQS, ECR — clicked together in the console on purpose, so that phase 4 has something to replace. Secrets in Secrets Manager. This is the phase you throw away.

4

It is code weeks 15–17

Rebuild all of phase 3 in Terraform. Remote state with locking. Modules, per-environment isolation, and import for the one resource you forgot to delete. Terratest on at least one module.

5

It runs on Kubernetes weeks 18–21

kind first, then EKS from your own Terraform. Deployments, services, ingress, probes, resource limits, ConfigMaps, IRSA so pods get AWS credentials without keys. The rollout drills land here.

6

It is operable weeks 22–24

Prometheus and Grafana, Actuator metrics, RED dashboards. An availability SLO on status-api with a real error budget. Alerts that are actionable and a dead man's switch. The last two drills, and all eight postmortems written up.

Money

Keeping it near $20, not near $400

EKS costs $0.10 per cluster-hour with no free tier. Left running for six months that is about $440 before a single node. This is a real constraint and the way around it is itself the lesson.

Rule 1

kind is the default. Everything that can be learned on a local cluster is learned on a local cluster. EKS is for the things only EKS does: IRSA, the ALB controller, EBS CSI and zone affinity, node groups.

Rule 2

Destroy is a first-class workflow. If terraform destroy and a 20-minute rebuild are routine, you will not leave a cluster running over a weekend. Make the rebuild boring in phase 4 and the cost problem solves itself.

Rule 3

A budget alarm on day one. AWS Budgets, $20 a month, alert at 50%. It costs nothing, it is five minutes, and FinOps appears in 3.6% of adverts because everyone has a story about not having done it.

Rule 4

Small and single-AZ everywhere. db.t4g.micro, two small nodes, one NAT gateway or none. Multi-AZ, autoscaling and cross-zone redundancy are things to explain, not things to run.

Realistic total if you follow those: roughly 40–60 hours of EKS uptime across the course, so about $5 of cluster fee, plus nodes, RDS and a little data transfer. Twenty dollars is achievable. Four hundred is what happens if you forget once.

The sentence this is all for

“I took an enterprise integration workload — the kind of thing I run on MuleSoft at work — and rebuilt it on EKS with Terraform and GitHub Actions. Then I broke it eight times on purpose to find out how it fails. The most interesting one was a rollout that reported success while users got 502s, because readiness passing and endpoints converging are not the same event.”

That is not a course certificate. It is thirty seconds that demonstrates every item on the advert and cannot be bluffed, and it is reachable in twenty-four weeks from where the placement put you.

Scoped against the placement of 9 October 2026 and curriculum v4. The failure ledger maps one to one onto questions answered wrongly in that assessment, which is why it is eight items and not a round ten.

Apache Camel is chosen over Spring Integration because it is the closer analogue to MuleSoft and because Camel in Action is already on your shelf. Brikman and Burns are held as review criteria for the Terraform and Kubernetes work — read the chapter after you hit the wall, not before.
