The Job Nobody Saw Fail

A backup script runs fine when you type it. Put it in cron for 02:00 and it fails every night for three weeks, and nobody finds out until the day someone needs a backup. No error, no email, no log. This lesson is about systemd, the program that starts everything else on a Linux server: how it runs services, restarts them, keeps their logs, runs jobs on a schedule, and tells you when one fails.

~3 hours week 5 laptop only, no AWS Ubuntu 26.04 · systemd 259

The incident

Works in the terminal, fails in cron

There are two separate reasons, and a silent cron failure usually has both.

1. cron runs your script with almost nothing set. cron gives a job PATH=/usr/bin:/bin and SHELL=/bin/sh. It doesn't read your .bashrc or .profile, so anything they add isn't there. On this laptop:

CommandIn my terminalIn cron's PATH
java/usr/bin/javafound
python3/usr/bin/python3found
uv~/.local/bin/uvmissing
aws/snap/bin/awsmissing
terraform/snap/bin/terraformmissing

Checked with env -i PATH=/usr/bin:/bin /bin/sh -c 'command -v uv', which runs a command with cron's environment and nothing else.

2. cron's output goes nowhere. cron mails anything a job prints to the crontab's owner. Most servers have no mail system, so Ubuntu's cron writes (CRON) info (No MTA installed, discarding output) to syslog and throws the error message away. The script said "aws: not found" every night, to nobody.

systemd fixes both, and adds the things cron never had: restarts, limits, a log you can search, and a hook that runs when something fails.

The mechanism

systemd is the parent of every service

1

PID 1systemd is the first process the kernel starts, and every service on the machine is its child. A parent is told the moment its child exits, and with what exit code or signal. That's how systemd knows a service died, without polling.

2

A unit file per serviceEach service is described by a small text file, a unit: what to run, as which user, with which environment and limits, and what to do when it exits.

3

A cgroup per serviceEvery service gets its own cgroup, so MemoryMax= from Lesson 1.2 applies to the service and all its children, and stopping it kills everything it started. Nothing can escape by forking.

4

The journalA service's stdout and stderr go to journald, indexed by unit and time. No log file to rotate, which is Lesson 1.1's problem solved a different way.

A unit file

A Java service, the way it should run

A unit for a Spring Boot or Mule-style service. Each line replaces something you would otherwise do by hand or in a start script:

# /etc/systemd/system/ingest.service [Unit] Description=Interchange ingest After=network-online.target # start after the network is up Wants=network-online.target StartLimitIntervalSec=300 # at most 5 starts in 5 minutes, StartLimitBurst=5 # then give up and stay failed [Service] User=ingest # never root WorkingDirectory=/opt/ingest Environment=JAVA_OPTS=-XX:MaxRAMPercentage=75 ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/ingest/ingest.jar Restart=on-failure # restart if it crashes, not if you stop it RestartSec=5 MemoryMax=2G # Lesson 1.2: a cgroup limit LimitNOFILE=65536 # Lesson 1.1: the descriptor limit [Install] WantedBy=multi-user.target # start at boot
CommandWhat it does
systemctl daemon-reloadRe-reads unit files. Needed after every edit, or systemd keeps using the old version.
systemctl start ingestStarts it now. Doesn't survive a reboot.
systemctl enable ingestStarts it at boot, by linking it into multi-user.target. Doesn't start it now. enable --now does both.
systemctl status ingestState, main PID, memory, the last log lines.
systemctl cat ingestThe unit file systemd is really using, with any overrides.

Restarts

"Start request repeated too quickly"

A service that exits with code 3 one second after it starts. Restart=on-failure restarts it, and the start limit, 3 starts in 30 seconds, stops the loop:

starting, pid 423025 lesson13-crash.service: Scheduled restart job, restart counter is at 1. starting, pid 423048 lesson13-crash.service: Scheduled restart job, restart counter is at 2. starting, pid 423069 lesson13-crash.service: Scheduled restart job, restart counter is at 3. lesson13-crash.service: Start request repeated too quickly. Failed to start lesson13-crash.service - Lesson 1.3: a service that crashes after 1 second. $ systemctl --user show -p NRestarts,Result,ExecMainStatus lesson13-crash.service Result=exit-code NRestarts=3 ExecMainStatus=3

The limit is what protects the machine. Without it, a service that crashes on start restarts forever, filling the journal and burning CPU. Once it trips, the unit stays failed until someone fixes the cause and runs systemctl reset-failed or starts it by hand. "Repeated too quickly" is never the problem itself. The problem is in the log lines above it.

The first version of this demo was wrong in two ways, and systemd carried on

The limit was in the wrong section. StartLimitIntervalSec= belongs in [Unit]. Put in [Service], systemd logged Unknown key 'StartLimitIntervalSec' in section [Service], ignoring. and started the service anyway, with the default limit. systemd-analyze verify file.service prints the same warning before you start anything. Run it after every edit. (On this laptop it also found a misplaced key in a vendor's unit, spice-vdagent.service.)

$$ printed $. systemd expands $NAME in ExecStart= itself, before any shell sees the line, and $$ is its escape for one literal $. To hand the shell $$, write $$$$. Likewise % is systemd's own specifier character, so date +%T must be written date +%%T.

Environment

A service doesn't read .bashrc either

systemd is not a shell, so nothing from your login files reaches a service. The environment a system service gets on this laptop is three variables:

$ systemctl show-environment LANG=en_GB.UTF-8 PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/snap/bin XDG_DATA_DIRS=/var/lib/flatpak/exports/share:/usr/local/share/:/usr/share/

No JAVA_HOME, no ~/.local/bin, no ~/.nvm, and no HOME unless the unit sets User=. The difference from cron is that systemd makes you say what the service needs, in the unit, where the next person can read it:

Environment=JAVA_OPTS=-XX:MaxRAMPercentage=75 Environment=PATH=/opt/ingest/bin:/usr/bin:/bin EnvironmentFile=/etc/ingest/ingest.env # KEY=value lines; keep secrets out of the unit itself
$ systemd-run --user --wait --pipe -p Environment=JAVA_OPTS=-XX:MaxRAMPercentage=75 sh -c 'echo "JAVA_OPTS=$JAVA_OPTS"' JAVA_OPTS=-XX:MaxRAMPercentage=75

Without that -p Environment=, the same command printed JAVA_OPTS=<unset>, even though the variable might be set in your terminal.

Logs

journalctl: every service's output, searchable

CommandShows
journalctl -u ingestOne unit's log, oldest first. Add -e to jump to the end.
journalctl -u ingest -fFollow it live, like tail -f.
journalctl -u ingest --since "02:00" --until "02:10"The window when the job ran.
journalctl -b -1 -u ingestThe previous boot. Needs a persistent journal (/var/log/journal exists).
journalctl -kKernel messages, where Lesson 1.2's OOM kills are.
journalctl -p errOnly messages logged as errors or worse.

-p err doesn't show what a program printed to stderr

When the nightly job below failed, journalctl -p err showed systemd's "Failed to start" line but not the program's own ls: cannot access … message. journald records a service's stdout and stderr at priority info unless the program says otherwise. Filter by unit (-u), not by priority, when you want the reason.

The journal rotates itself: journalctl --disk-usage said 2.4 GB on this laptop, capped by SystemMaxUse= in /etc/systemd/journald.conf.

Timers

Two files instead of one cron line

A timer is a unit that starts another unit at given times. The job itself is an ordinary oneshot service, so it gets everything above: environment, limits, the journal.

nightly.service · what to run

[Unit] Description=The nightly job OnFailure=alert@%n.service [Service] Type=oneshot ExecStart=/opt/jobs/backup.sh

nightly.timer · when

[Unit] Description=Run the nightly job at 02:00 [Timer] OnCalendar=*-*-* 02:00:00 Persistent=true [Install] WantedBy=timers.target

Check a schedule before you trust it. systemd-analyze calendar prints the next times it will fire:

$ systemd-analyze calendar --iterations=3 'Mon..Fri 02:00' Original form: Mon..Fri 02:00 Normalized form: Mon..Fri *-*-* 02:00:00 Next elapse: Wed 2026-11-11 02:00:00 GMT Iteration #2: Thu 2026-11-12 02:00:00 GMT Iteration #3: Fri 2026-11-13 02:00:00 GMT

Persistent=true catches up on runs the machine slept through. The timer records when it last fired. Here it last fired at 23:00 the night before, so today's 02:00 was missed. Started at 14:49, it ran the job at once:

14:49:03 systemd[3474]: Starting lesson13-nightly.service - Lesson 1.3: the nightly job... 14:49:03 sh[423194]: nightly job ran at 14:49:03 14:49:03 systemd[3474]: Finished lesson13-nightly.service - Lesson 1.3: the nightly job. $ systemctl --user list-timers lesson13-nightly.timer NEXT LEFT LAST PASSED UNIT Wed 2026-11-11 02:00:00 GMT 11h Tue 2026-11-10 14:49:03 GMT 2s ago lesson13-nightly.timer

cron has no memory of missed runs. This laptop's own crontab has a line for a daily job with "hourly catch-up for days missed while asleep/off", which is a hand-built Persistent=true.

Failing loudly

OnFailure=: run something when it breaks

The nightly job, made to fail, with OnFailure=lesson13-alert@%n.service. %n is the failing unit's name, passed to a template unit (alert@.service), which reads it back as %i:

14:49:16 sh[423277]: backing up 14:49:16 sh[423278]: ls: cannot access '/nonexistent/backup-dir': No such file or directory 14:49:16 systemd[3474]: lesson13-nightly.service: Main process exited, code=exited, status=2/INVALIDARGUMENT 14:49:16 systemd[3474]: lesson13-nightly.service: Failed with result 'exit-code'. 14:49:16 systemd[3474]: lesson13-nightly.service: Triggering OnFailure= dependencies. 14:49:16 lesson13-alert[423283]: ALERT: lesson13-nightly.service failed, see: journalctl --user -u lesson13-nightly.service

Here the alert only writes to the journal. On a server it would post to Slack, page someone, or push a metric. And systemd keeps a list of what failed, which survives until it's cleared. On this laptop it still held the OOM kills from Lesson 1.2:

$ systemctl --user --failed UNIT LOAD ACTIVE SUB DESCRIPTION run-p270848-i257652.scope loaded failed failed [systemd-run] /usr/bin/python3 -I …/grow.py run-p271037-i283211.scope loaded failed failed [systemd-run] /usr/bin/java -Xmx2g Grow run-p318854-i320657.scope loaded failed failed [systemd-run] /usr/bin/python3 grow.py

OnFailure can't catch a job that never ran

If the timer is disabled, or the server is rebuilt without it, nothing fails, so nothing alerts. Catching "it didn't happen" needs the opposite check, from outside: the job reports success somewhere, and an alarm fires when that report is missing. That's a dead man's switch, and it's Interchange failure 8.

Changing a vendor's unit

Drop-ins: never edit the package's file

Units installed by a package live in /usr/lib/systemd/system/, and the next package upgrade overwrites them. To change one, add a drop-in: a small file that overrides only the lines you name.

$ sudo systemctl edit jenkins # opens /etc/systemd/system/jenkins.service.d/override.conf [Service] LimitNOFILE=65536 Environment=JAVA_OPTS=-Xmx4g $ systemctl cat jenkins # shows the vendor file, then your override below it $ sudo systemctl restart jenkins # systemctl edit already ran daemon-reload $ grep 'open files' /proc/$(systemctl show -p MainPID --value jenkins)/limits

The last line closes the loop from Lesson 1.1: don't trust the unit file, read the limit the running process really has.

Build it

Break a service, schedule a job, make it fail loudly

Everything runs as your own user, with systemctl --user: the same systemd, the same unit files, no sudo. User units live in ~/.config/systemd/user/. Work in devops-course/labs/p1-3/ and name every unit lab13-… so the clean-up at the end is easy.

Part 1: what cron and systemd would see

mkdir -p ~/IdeaProjects/devops-course/labs/p1-3 ~/.config/systemd/user && cd ~/IdeaProjects/devops-course/labs/p1-3 for c in java python3 uv aws terraform; do printf '%-10s shell:%-28s cron:%s\n' $c "$(command -v $c)" "$(env -i PATH=/usr/bin:/bin /bin/sh -c "command -v $c" || echo MISSING)" done systemctl show-environment crontab -l

Which of your tools would a 02:00 cron job not find? Does your crontab use full paths?

Part 2: a service that crashes

cat > ~/.config/systemd/user/lab13-crash.service <<'EOF' [Unit] Description=Lab 1.3: crashes after 1 second StartLimitIntervalSec=30 StartLimitBurst=3 [Service] ExecStart=/bin/sh -c 'echo "starting, pid $$$$"; sleep 1; echo "giving up" >&2; exit 3' Restart=on-failure RestartSec=1 EOF systemd-analyze --user verify ~/.config/systemd/user/lab13-crash.service systemctl --user daemon-reload systemctl --user start lab13-crash.service; sleep 9 journalctl --user -u lab13-crash.service -o cat --since -15s systemctl --user show -p NRestarts,Result,ExecMainStatus lab13-crash.service

Predict before you run it: how many times does it start, and what is its state at the end? Then move StartLimitIntervalSec=30 into [Service], run verify again, and read what it says.

Part 3: a timer that catches up

cat > ~/.config/systemd/user/lab13-nightly.service <<'EOF' [Unit] Description=Lab 1.3: the nightly job [Service] Type=oneshot ExecStart=/bin/sh -c 'echo "nightly job ran at $$(date +%%T)"' EOF cat > ~/.config/systemd/user/lab13-nightly.timer <<'EOF' [Unit] Description=Lab 1.3: run the nightly job at 02:00 [Timer] OnCalendar=*-*-* 02:00:00 Persistent=true [Install] WantedBy=timers.target EOF systemd-analyze calendar --iterations=3 '*-*-* 02:00:00' mkdir -p ~/.local/share/systemd/timers touch -d 'yesterday 23:00' ~/.local/share/systemd/timers/stamp-lab13-nightly.timer systemctl --user daemon-reload systemctl --user start lab13-nightly.timer; sleep 2 journalctl --user -u lab13-nightly.service -o cat --since -10s systemctl --user list-timers lab13-nightly.timer

The touch fakes "last ran yesterday at 23:00", the way a laptop that was asleep at 02:00 would look. Predict: does the job run now, or at 02:00 tomorrow?

Part 4: make it fail loudly

cat > ~/.config/systemd/user/lab13-alert@.service <<'EOF' [Unit] Description=Lab 1.3: alert for %i [Service] Type=oneshot ExecStart=/bin/sh -c 'echo "ALERT: %i failed" | systemd-cat -t lab13-alert -p err' EOF cat > ~/.config/systemd/user/lab13-nightly.service <<'EOF' [Unit] Description=Lab 1.3: the nightly job OnFailure=lab13-alert@%n.service [Service] Type=oneshot ExecStart=/bin/sh -c 'echo "backing up"; ls /nonexistent/backup-dir' EOF systemctl --user daemon-reload systemctl --user start lab13-nightly.service; sleep 1 journalctl --user -p err --since -10s -o cat journalctl --user -u lab13-nightly.service --since -10s -o cat systemctl --user --failed

Which command showed the real reason, the ls error: the -p err one or the -u one? Why?

Part 5: a drop-in and the limit it changes

cat > ~/.config/systemd/user/lab13-sleeper.service <<'EOF' [Service] ExecStart=/bin/sleep 600 EOF systemctl --user daemon-reload; systemctl --user start lab13-sleeper.service P=$(systemctl --user show -p MainPID --value lab13-sleeper.service); sleep 1; grep 'open files' /proc/$P/limits mkdir -p ~/.config/systemd/user/lab13-sleeper.service.d printf '[Service]\nLimitNOFILE=4096\n' > ~/.config/systemd/user/lab13-sleeper.service.d/override.conf systemctl --user daemon-reload; systemctl --user restart lab13-sleeper.service P=$(systemctl --user show -p MainPID --value lab13-sleeper.service); sleep 1; grep 'open files' /proc/$P/limits systemctl --user cat lab13-sleeper.service

The first grep shows systemd's default for a service: a soft limit of 1024 and a hard limit of 524288. Predict: after the override, does the same sleep process have the new limit, or a new one? Look at the PID. The sleep 1 matters: read the limits straight after a start and you may catch the child before it has applied its limits and run sleep. It shows as (sleep) in /proc/$P/comm, still carrying the manager's values.

Clean up when you're done: systemctl --user stop 'lab13-*'; rm -r ~/.config/systemd/user/lab13-*; systemctl --user daemon-reload; systemctl --user reset-failed

Part 6: your servers

On a Jenkins agent or Mule server, and only looking: systemctl list-timers, crontab -l for your own user, and systemctl --failed. How is the Mule runtime started: a systemd unit (systemctl list-units --type=service | grep -i mule), an init script, or nohup from a Jenkins job? If it's a unit, systemctl cat it and look for Restart=, LimitNOFILE= and MemoryMax=. Is there a nightly job that would fail without anyone knowing? That's your interview story. Leave out hostnames, unit names that identify the customer, and anything that looks like a password.

Done when: you can explain, without notes, the two reasons a cron job fails silently, and what Persistent=true and OnFailure= each fix.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

A script runs fine from your terminal. From cron at 02:00 it fails every night, and there is no error anywhere. Give two reasons.

The environment, and where the output goes. cron runs the job with PATH=/usr/bin:/bin and doesn't read .bashrc, so tools in ~/.local/bin, /snap/bin or /opt aren't found, and variables like JAVA_HOME aren't set. And cron mails the job's output to its owner; with no mail system on the server, the error message is discarded. Use full paths and set the environment explicitly, and run it as a systemd timer so the output lands in the journal.

A service is in state failed and the log ends with "Start request repeated too quickly". What does that mean, and what do you do?

The service kept crashing, and the start limit stopped systemd restarting it. Restart=on-failure restarted it until it hit StartLimitBurst starts within StartLimitIntervalSec, and then systemd left it failed so it wouldn't loop forever. That line is never the cause. Read the lines above it with journalctl -u name to find why each start exited, fix that, then systemctl reset-failed name and start it.

A server was switched off for patching from 01:00 to 03:00. A cron job and a systemd timer were both set for 02:00. What happens to each?

The cron job is skipped; the timer runs at boot if it has Persistent=true. cron only checks the clock while it's running and keeps no record of missed runs. A persistent timer records when it last fired, and on start it sees that a scheduled time passed while it was down, so it runs the job straight away. Without Persistent=true the timer behaves like cron.

The vendor's mule.service needs LimitNOFILE=65536. Where do you put it, and why not edit the unit file? How do you prove it worked?

In a drop-in, because the package owns the unit file. sudo systemctl edit mule writes /etc/systemd/system/mule.service.d/override.conf, which overrides only the lines you give and survives package upgrades; an edit to /usr/lib/systemd/system/mule.service is overwritten by the next upgrade. Then restart the service, because limits are set when a process starts, and prove it with grep 'open files' /proc/<MainPID>/limits, not by reading the file.

A Jenkins job starts a service with nohup java -jar app.jar > app.out 2>&1 < /dev/null &. It works. Why move it into a systemd unit anyway? Name three things you gain.

Because then systemd, not a finished build, is the service's parent. It restarts the service if it crashes (Restart=) and starts it at boot (enable). Its output goes to the journal instead of a file nobody rotates. Limits like MemoryMax and LimitNOFILE are set in one readable place, and its cgroup means stop kills every process it started. The Jenkins job then only runs sudo systemctl restart app, which ends immediately and holds no descriptors, so no "leaked file descriptors".

Interchange

Setting up failure 8 of 8

The project's last deliberate failure, in Phase 6, is a nightly job that silently stops. This lesson gives you half of the defence: a timer with Persistent=true and an OnFailure= alert catch a job that runs and fails. The other half, a dead man's switch that alerts when the job doesn't run at all, comes with CloudWatch. When ingest runs on a VM in Phase 3, it will run as a systemd unit like the one above, with MemoryMax and LimitNOFILE set, which is where failures 1 and 2 happen for the first time.
