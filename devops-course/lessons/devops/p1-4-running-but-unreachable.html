Phase 1 · Lesson 1.4 · AWS + DevOps course

Running but Unreachable

The new release is deployed. On the server, curl localhost:8081/health answers 200. The load balancer marks it unhealthy, and the testers get "connection refused". The day after, a different app works but every call it makes takes five seconds, exactly. Both are networking, and neither is the network. This lesson follows one request from a name to a reply: DNS, the route, the TCP connection, TLS, and what each step's failure looks like.

~3 hours week 6 laptop only, no AWS Ubuntu 26.04 · curl · ss · openssl

The mechanism

One request, five steps, five different failures

When a program calls https://api.example.com/orders, five things happen in order, and the sections below follow the same order. Step 3, the connection, has two sections: what happens on the server (3a) and what the client sees (3b). Each has its own error message and its own tool, so the first job when "it can't connect" is to find out which step failed.

1

Name → address · DNSThe name is turned into an IP address. Fails with "Could not resolve host", or is slow. Tool: getent hosts.

2

Address → interface · routingThe kernel picks which network card the packets leave by, using the routing table. Tool: ip route get.

3

Connect · TCPA three-way handshake with a program listening on that address and port. Fails as "connection refused" (fast) or "timed out" (slow). Tools: curl -v, nc -zv; on the server, ss -ltnp.

4

Prove who it is · TLSThe server shows a certificate; the client checks it's valid, in date, and for this name. Fails with "certificate has expired" or "PKIX path building failed". Tool: openssl s_client.

5

Ask · HTTPOnly now does the request reach the application. A 404, 500 or 502 means steps 1 to 4 all worked.

In the library: DNS is the directory that turns a library's name into a street address. The IP address is the building, and the port is the counter number inside it (counter 443, counter 8081). A program listening on a port is a librarian sitting at that counter. Each connection is a loan ticket again: a socket is a file descriptor, and ss shows which process holds it, just as lsof did in Lesson 1.1.

Step 1 · name

DNS, and the five-second timeout

A program asks the C library (getaddrinfo()), and the library follows two files:

$ grep '^hosts' /etc/nsswitch.conf hosts: files mdns4_minimal [NOTFOUND=return] dns # the order to ask in $ grep -v '^#' /etc/resolv.conf nameserver 127.0.0.53 # systemd-resolved, on loopback options edns0 trust-ad search . $ resolvectl status | grep 'DNS Servers' DNS Servers: (the ISP's two resolvers, given by the router's DHCP)
1

files/etc/hosts first. If the name is there, the search stops. Nothing else is asked.

2

mdns4_minimalNames ending in .local, answered by machines on the LAN. Anything else falls through.

3

dnsEach nameserver in /etc/resolv.conf, in order. On Ubuntu that's systemd-resolved's stub at 127.0.0.53, which caches and forwards to the real servers. On most RHEL servers resolv.conf lists the company's DNS servers directly.

/etc/hosts wins, and dig doesn't know

With one line added to /etc/hosts (in a private copy made with unshare; the lab does the same with a container):

10.9.9.9 example.com # the added line $ getent ahostsv4 example.com 10.9.9.9 STREAM example.com # what programs get $ python3 -c 'import socket; print(socket.gethostbyname("example.com"))' 10.9.9.9 $ dig +short example.com A 104.20.23.154 # dig asks the DNS server directly

dig and nslookup are DNS tools: they skip nsswitch.conf and /etc/hosts. Your Java app, curl and Python don't. When "dig says the right IP but the app goes to the old one", use getent hosts, which follows the same path as the app, and look in /etc/hosts. Then check caches: the JVM keeps successful lookups for 30 seconds by default (networkaddress.cache.ttl), and some old setups cache forever.

The five seconds

If the first nameserver doesn't answer, the resolver waits for it, then tries the next. The default wait is 5 seconds. A fake resolv.conf whose first server is an address that never answers:

nameserver 10.255.255.1 # dead nameserver 127.0.0.53 # works $ time getent ahostsv4 example.com 104.20.23.154 STREAM example.com 5.00s # the right answer, five seconds late # the same, with options timeout:1 attempts:1 added 1.00s

Nothing fails. Every lookup is just slow, by a suspiciously round number. So: when every call takes 5.0 seconds, or 10, suspect DNS first. Prove it with curl's timing, which splits a request into its steps:

$ curl -s -o /dev/null -w 'dns %{time_namelookup}\ntcp %{time_connect}\ntls %{time_appconnect}\nfirst-byte %{time_starttransfer}\n' https://example.com/ dns 0.027660 tcp 0.048201 tls 0.077594 first-byte 0.102771
That request, to scale (times are cumulative, so each step is the difference)
DNS 28 TCP 21 TLS 29 server 25
0 ms103 ms

With the dead nameserver, the first segment would be 5,000 ms and the other three unchanged.

Coming in Phase 5: ndots:5

Not run here, because it needs a cluster. A Kubernetes pod's resolv.conf has three search domains and options ndots:5: any name with fewer than five dots is tried with each search domain appended first. So one lookup of api.example.com becomes eight DNS queries (A and AAAA for each of four names) before the real one is asked. That's why cluster DNS gets busy, and why a trailing dot (api.example.com.) or a full name speeds things up. You'll see it with cat /etc/resolv.conf inside a pod.

Step 2 · route

Interfaces and routes

An interface is a network card, real or virtual. Each has one or more IP addresses. On this laptop:

$ ip -br addr lo UNKNOWN 127.0.0.1/8 ::1/128 # loopback: never leaves the machine wlp0s20f3 UP 192.168.0.32/24 # Wi-Fi: the home network docker0 DOWN 172.17.0.1/16 # Docker's default bridge br-69abccb9ce83 UP 172.23.0.1/16 # a Compose project's network vethbcc244e@if2 UP # one end of a cable into a container … # 14 in all, most of them Docker's

The routing table says which interface to use for each destination. The most specific match wins, and default catches everything else:

$ ip route default via 192.168.0.1 dev wlp0s20f3 proto dhcp src 192.168.0.32 # everything else: to the router 172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 # Docker's addresses: the bridge … $ ip route get 8.8.8.8 8.8.8.8 via 192.168.0.1 dev wlp0s20f3 src 192.168.0.32 $ ip route get 127.0.0.1 local 127.0.0.1 dev lo src 127.0.0.1 $ ip route get 172.17.0.5 172.17.0.5 dev docker0 src 172.17.0.1

ip route get answers "if I sent a packet there, which way would it go, and from which of my addresses?" It's the quickest check when a server has two networks (a front-end and a back-end network, or a VPN) and traffic leaves by the wrong one.

/24 and /16 are the network size: the first 24 (or 16) bits of the address name the network, and the rest name the machine on it. So 192.168.0.32/24 shares a network with every 192.168.0.x. VPC design in Phase 3 is mostly choosing these numbers.

Step 3a · connect, on the server

0.0.0.0 against loopback: which door is the librarian at?

A server program calls bind() to choose which of the machine's addresses it listens on, then listen(). The address it picks decides who can reach it:

Bound toReachable fromTypical use
127.0.0.1This machine only, through loAdmin ports, databases on a single box, anything that must not be exposed
0.0.0.0Every interface: loopback, the LAN, every bridgeA service other machines must reach
192.168.0.32Only through that one interfaceServers with a public and a private network

Two copies of Python's built-in web server, one bound each way:

$ python3 -m http.server 8141 --bind 127.0.0.1 & $ python3 -m http.server 8142 --bind 0.0.0.0 & $ ss -ltnp State Recv-Q Send-Q Local Address:Port Peer Address:Port Process LISTEN 0 5 127.0.0.1:8141 0.0.0.0:* users:(("python3",pid=865059,fd=3)) LISTEN 0 5 0.0.0.0:8142 0.0.0.0:* users:(("python3",pid=865060,fd=3))

ss -ltnp: listening sockets, tCP, numeric (no name lookups), with the process. The fd=3 is the loan ticket: the listening socket is file descriptor 3 in that process. Then the same request to each, from the laptop itself:

curl toServer on 127.0.0.1:8141Server on 0.0.0.0:8142
127.0.0.1200200
192.168.0.32 (own LAN address)refused in 0 ms200

That's the incident from the top of the page. curl localhost on the server proves only that the program answers on loopback. The load balancer arrives on the LAN address, where nobody is listening, so the kernel answers for the program: refused. On the server, ss -ltnp shows it in one line: look at the Local Address column. In a Mule app the setting is the HTTP Listener's host (0.0.0.0 or localhost); in Spring Boot it's server.address.

This laptop's own listeners show all three choices on purpose:

$ ss -ltn LISTEN 0 4096 127.0.0.1:631 0.0.0.0:* # CUPS printing: this machine only LISTEN 0 4096 127.0.0.53%lo:53 0.0.0.0:* # systemd-resolved's DNS stub: loopback only LISTEN 0 4096 0.0.0.0:22 0.0.0.0:* # sshd: every interface, so others can log in

In a container, localhost is the container

Every container has its own network namespace, with its own lo. A program bound to 127.0.0.1 inside the container is reachable only from inside that container, and -p forwards to the container's other interface. Two containers from the same image, publishing port 8000 to the laptop:

$ docker run -d -p 8143:8000 php:8.5.12-cli-alpine sh -c '… php -S 127.0.0.1:8000 -t /tmp' $ docker run -d -p 8144:8000 php:8.5.12-cli-alpine sh -c '… php -S 0.0.0.0:8000 -t /tmp' $ curl http://127.0.0.1:8143/ curl: (56) Recv failure: Connection reset by peer $ curl http://127.0.0.1:8144/ hello $ docker exec lab14-lo wget -qO- http://127.0.0.1:8000/ # from inside, it works hello

docker ps showed 0.0.0.0:8143->8000/tcp for both, so the publishing looked fine. The error is "reset", not "refused": Docker's forwarder accepted the connection on 8143, found nothing listening on the container's address, and cut it. This is Phase 2's first trap, and in Kubernetes the same app fails its readiness probe.

Step 3b · connect, on the client

Refused is fast. Timed out is slow. They mean different things.

$ nc -zv -w 3 127.0.0.1 22 Connection to 127.0.0.1 22 port [tcp/ssh] succeeded! $ nc -zv -w 3 127.0.0.1 8149 nc: connect to 127.0.0.1 port 8149 (tcp) failed: Connection refused $ nc -zv -w 3 10.255.255.1 80 nc: connect to 10.255.255.1 port 80 (tcp) timed out: Operation now in progress
ErrorWhat happenedHow longLook at
Connection refused
errno 111, ECONNREFUSED		The packet reached the machine. The kernel found no listener on that address and port and sent back a reset.0 msThe server: is the program running? ss -ltnp: right port, right address?
Connection timed out
curl exit 28		No answer at all. Something dropped the packet: a firewall, a security group, a wrong IP, a route to nowhere.the full timeout (5.00 s here)The path: firewall rules, security groups, ip route get, is the IP right?
Connection reset by peer
curl exit 56		Connected, then cut. Something accepted the connection and then closed it hard: a proxy with no backend, a crashing app, a TLS mismatch.fastWhatever sits in between: proxy, load balancer, Docker's forwarder

Python's socket shows the same two at the system-call level: ConnectionRefusedError: errno=111 Connection refused after 0.00s and TimeoutError: timed out after 5.00s. Newer curl prints both kinds of failure as "Could not connect to server", so nc -zv is the clearer test.

Why a timeout is worse than refused

Refused costs nothing: the caller knows in a millisecond and can fail over. A timeout holds the caller's thread, connection and memory for the whole timeout. If an app has 200 worker threads and every call to a dead dependency waits 30 seconds, 200 requests in 30 seconds fill it, and now the healthy app is down too. That is how a failure moves from where it started to somewhere else, and it's Interchange failure 7. Every outgoing call needs an explicit connect timeout and read timeout, short ones.

The state of every connection on the machine, counted:

$ ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn 74 ESTAB # open connections 32 LISTEN # programs waiting at a counter 8 TIME-WAIT # closed by this side, kept ~60 s so stray packets aren't misread 2 FIN-WAIT-2 # closing, waiting for the other side to finish

Thousands of TIME-WAIT usually means a client opening a new connection for every request instead of reusing a pool. Thousands of CLOSE-WAIT means the opposite and is a bug: the other side closed, and this program never closed its end, so its file descriptors leak until it hits the limit from Lesson 1.1.

Step 4 · TLS

TLS: proving who's at the counter

After the TCP handshake, the server sends its certificate and the chain of certificates that signed it. The client checks three things: the chain ends at a root certificate it already trusts, today is inside the certificate's dates, and the name it asked for is listed in the certificate. Then both sides agree on keys, and everything after is encrypted.

$ echo | openssl s_client -connect example.com:443 -servername example.com 0 s:CN=example.com # the server's own certificate i:C=US, O=SSL Corporation, CN=Cloudflare TLS Issuing ECC CA 3 # signed by… 1 s:C=US, O=SSL Corporation, CN=Cloudflare TLS Issuing ECC CA 3 # an intermediate i:C=US, O=SSL Corporation, CN=SSL.com TLS Transit ECC CA R2 … # 4 certificates in all $ … | openssl x509 -noout -subject -enddate -ext subjectAltName subject=CN=example.com notAfter=Dec 25 22:56:35 2026 GMT # expiry date X509v3 Subject Alternative Name: DNS:example.com, DNS:*.example.com # the names it's valid for

-servername sends the name in the handshake (SNI), so a server hosting many sites knows which certificate to send. Leave it out and you may get the wrong one. Three test sites at badssl.com each break one of the three checks:

Sitecurl saysWhich check failed
expired.badssl.comcertificate has expired (10)The dates. Someone forgot to renew.
wrong.host.badssl.comno alternative certificate subject name matches target hostnameThe name. You connected by IP, an alias, or an old name.
self-signed.badssl.comself-signed certificate (18)The chain. It ends at a root this machine doesn't trust: internal CAs and test servers.

Java has its own list of trusted roots

curl and Python use the operating system's store (/etc/ssl/certs). Java uses a file called cacerts, inside the JDK. On this laptop it's a link to a copy Ubuntu builds from the system store (120 Java entries, 121 system ones), so they agree. A JDK unpacked from a tarball into /opt, which is common with Mule and Jenkins, carries its own cacerts and ignores the system store. That's why "curl works but the Java app says PKIX path building failed" after a company CA or a new intermediate certificate is introduced. The fix is to import the CA into that JDK's cacerts with keytool -importcert, never to switch verification off. curl -k is a diagnosis, not a fix.

Predict: which one returns at once, and which waits? What is each one telling you about where the problem is?

Part 4: the resolver, in a container · step 1, name

A container gets its own /etc/resolv.conf and /etc/hosts, and Docker lets you choose what goes in them, so you can break name resolution without touching your laptop's. php:8.2-cli is Debian-based, so it uses the same C-library resolver as the laptop. (Alpine images use musl, which asks every nameserver at once and never shows the delay.)

time getent ahostsv4 example.com docker run --rm --dns 10.255.255.1 --dns 1.1.1.1 php:8.2-cli \ bash -c 'cat /etc/resolv.conf; time getent ahostsv4 example.com | head -1' docker run --rm --dns 10.255.255.1 --dns 1.1.1.1 --dns-option timeout:1 --dns-option attempts:1 php:8.2-cli \ bash -c 'time getent ahostsv4 example.com | head -1' docker run --rm --add-host example.com:10.9.9.9 php:8.2-cli getent ahostsv4 example.com dig +short example.com A

Predict: with the dead nameserver first, does the lookup fail, or work? How long does it take, and how long with timeout:1? In the last two lines, does the container's getent agree with dig?

The page's own demo used unshare -rm to mount private copies over the real files. Ubuntu blocks that in an ordinary terminal (kernel.apparmor_restrict_unprivileged_userns = 1; the error is write failed /proc/self/uid_map: Operation not permitted), so the lab uses containers instead.

Part 6: your servers · all steps, at work

On a Mule server or Jenkins agent, and only looking: ss -ltnp (you may need sudo to see process names; without it, the addresses are enough). Which address does the Mule HTTP listener bind to: 0.0.0.0, or something narrower? Read /etc/resolv.conf: how many nameservers, any options? Find which JDK Mule runs (readlink -f on its java) and whether its cacerts is a link to the system store or its own file. Leave out hostnames, IP addresses and anything that names the customer.

Done when: you can say, without notes, what "refused" and "timed out" each tell you, why a service answers on localhost and not from outside, and why every lookup taking 5 seconds points at DNS.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

After a release, curl localhost:8081/health on the server returns 200, but the load balancer marks the app unhealthy and testers get "connection refused". What do you check first, and what's the likely cause?

ss -ltnp on the server, and look at the Local Address. If it says 127.0.0.1:8081, the app is listening on loopback only. The load balancer arrives on the server's network address, where nothing is listening, so the kernel refuses the connection. curl on the server works because it goes through loopback. Fix the app's bind address (the Mule HTTP Listener host, or server.address) to 0.0.0.0 or the server's address, restart, and check ss again.

"Connection refused" against "connection timed out": what does each tell you, and where do you look for each?

Refused means the machine answered and nobody was listening; timed out means nothing answered at all. Refused comes back in a millisecond, as a reset from the target's kernel, so the network path is fine: look at the server, whether the program is running and listening on that port and address. Timed out takes the full timeout, because the packets were dropped on the way: look at firewalls, security groups, routing, and whether the IP is right at all.

Every call from the app to a partner API takes just over 5 seconds, then succeeds. What's your first suspect, and how do you prove it?

DNS: the first nameserver isn't answering. The resolver waits 5 seconds for it, then asks the next, which works, so nothing fails and everything is slow by a round number. Prove it with curl -w '%{time_namelookup}' (it will show about 5.0) or time getent hosts partner-api, then read /etc/resolv.conf and test each nameserver with dig @server name. Fix or remove the dead server; options timeout:1 reduces the damage meanwhile.

dig api.internal returns the new IP, but the app keeps connecting to the old one. Give two reasons.

The app doesn't ask DNS the way dig does. First, /etc/hosts: the app's lookups go through nsswitch.conf, which checks files first, and an old entry there wins; dig skips it. getent hosts api.internal shows what the app really gets. Second, caching: the JVM keeps lookups for 30 seconds by default, and longer if networkaddress.cache.ttl is set, so a long-running app may never look again until it restarts.

After a certificate renewal, the Mule app's HTTPS calls fail with "PKIX path building failed", but curl to the same URL from the same server works. Why?

Java checks against its own trusted roots, not the system's. curl uses /etc/ssl/certs; the JVM uses the cacerts file inside its JDK, and a JDK unpacked into /opt has its own copy. The new certificate is signed by a CA (or a new intermediate) that is in the system store but not in that cacerts, so Java can't build a chain to a root it trusts. Import the CA into that JDK's cacerts with keytool -importcert and restart; don't disable verification.

Interchange

Setting up failures 5 and 7

When the four services run in containers in Phase 2, the first thing that breaks is the loopback trap above: a service bound to localhost inside its container, unreachable from the others. The deliberate failures come later. Failure 7, in Phase 6, adds 3 seconds of latency to reference: nothing refuses, nothing times out quickly, and callers' threads and connection pools fill while they wait, until the failure shows up somewhere it didn't start. That's this lesson's "a timeout is worse than refused", at system scale. Failure 5, in Phase 5, is 502s during a rollout that reports success: connections reset by a load balancer whose backend has gone. You now know which step each of those errors comes from.
