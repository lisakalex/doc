Linux and the network underneath everything

df says the filesystem is full. du on the same mount adds up to far less. What is going on, and how do you get the space back without rebooting?

A process still holds an open file descriptor on a file that has been unlinked. The directory entry is gone, so du cannot see it, but the inode and its blocks survive until the last descriptor closes.

lsof +L1 lists files with no remaining links. Truncating through the descriptor — : > /proc/<pid>/fd/<n> — frees the blocks without killing the process. Restarting the process works too and is usually what you do at 3am. The classic cause is a log file rotated by deletion rather than by copytruncate or a signal.

Mark yourself
A container listens on 0.0.0.0:8080. From the host, curl localhost:8080 hangs. Name the layers you would check, in the order you would check them.

Inside out. Is it actually listening — ss -ltnp in the container's namespace; a process bound to 127.0.0.1 inside a container is unreachable from anywhere else, which is the most common version of this. Is the port published — -p 8080:8080, and docker's PublishAllPorts is not the default. Is the host firewall passing it — iptables or nftables, and on a cloud VM the security group too. Is anything else on the port.

The useful habit is bisecting: curl from inside the container first. That one test splits the problem in half.

Mark yourself
A request to an internal hostname takes almost exactly five seconds, every time, and then succeeds. What does that number tell you?

A timeout, not slowness. Five seconds is the default DNS resolver timeout on most Linux systems — the first nameserver in /etc/resolv.conf is not answering, and the resolver falls through to the second after it gives up.

Round numbers in latency are nearly always a timeout somewhere. Real work produces untidy numbers. Three seconds, five seconds, thirty seconds and sixty seconds are worth recognising on sight; so is the IPv6-then-IPv4 fallback that produces the same shape.

Mark yourself
What does the kernel's OOM killer choose, and how would you change its mind?

It scores every process — roughly resident memory, adjusted by oom_score_adj — and kills the highest. It does not kill the process that allocated last, which is why the database dies when a batch job is the real culprit.

/proc/<pid>/oom_score_adj biases it, from −1000 (never) to +1000. In Kubernetes you do not set it directly: the QoS class does, and a pod with equal requests and limits (Guaranteed) is the last to be chosen while a Burstable pod exceeding its request goes first. Worth knowing that cgroup memory limits produce a different kill — the container is killed by its own cgroup, not by the system OOM killer, and the host logs look nothing alike.

AWS, past the service names

When is an IAM role the only option, and not merely the better one?

Whenever the thing that needs credentials cannot safely hold one: an EC2 instance, a Lambda, a container, a CI job, a user from another account or an identity provider. A role is assumed and the credentials it returns expire; a user carries a key that does not.

“Only” matters in cross-account access — a policy in account B can name a principal in account A, but A still assumes a role in B to act there. And for anything federated, there is no user object at all.

Mark yourself
An instance in a private subnet must read from S3 without its traffic leaving through the NAT gateway. What do you create, and what is the failure you should expect?

A gateway VPC endpoint for S3, which installs a prefix-list route in the subnet's route table. It costs nothing, unlike the NAT gateway's per-gigabyte charge, which is usually the real reason.

The failure: it routes only to S3 in that region, and anything relying on the public path breaks quietly. If a bucket policy or endpoint policy restricts by aws:SourceVpce and you get it wrong, access disappears with an AccessDenied that names nothing useful. And an interface endpoint is a different thing — an ENI with an hourly charge — which is what you need for most other services.

Mark yourself
A role has a policy granting s3:GetObject on the bucket. The call still returns AccessDenied. Name several independent causes.

Any of: an explicit Deny in the bucket policy, an SCP at the organisation level, a permissions boundary on the role, a session policy narrower than the role, the object being owned by another account, KMS — the key policy must allow kms:Decrypt separately and the object policy says nothing about it, the resource ARN missing /* so it grants the bucket and not its contents, a VPC endpoint policy, or Block Public Access when the path depended on it.

The structure worth holding: an explicit Deny anywhere beats every Allow, and the request must be allowed by every policy type that applies, not by any one of them.

Mark yourself
An instance profile carrying broad permissions, versus a long-lived access key with the same permissions. Which is worse, and in what way?

The instance profile is better in the ways that usually matter: credentials rotate automatically, never appear in a repository, and are scoped to one instance you can terminate.

It is worse in one specific way, and knowing it is the mark of having thought about it: anything that can make the instance issue an HTTP request can read them. A server-side request forgery bug against 169.254.169.254 hands the whole role to the internet, and there is no password to fail. IMDSv2's session tokens exist precisely for this; requiring it is one of the highest-value settings in an AWS account.

Terraform and the state problem

What is in the state file, and why can Terraform not simply read the cloud each time?

State maps your resource addresses to real resource IDs, and records the attributes as of the last apply. Without it Terraform cannot know that aws_instance.web means that instance rather than a new one — the cloud has no record of your naming.

It also stores what the configuration looked like, which is how a plan can tell “someone changed this outside Terraform” from “you changed the configuration”. And it holds every attribute of every resource, which is why state contains secrets and belongs in an encrypted bucket.

Mark yourself
Two engineers run apply within a minute of each other against an S3 backend with no lock configured. Describe what you end up with.

Both read the same state, both plan against it, both write. The second write wins and the first engineer's resources are now absent from state while existing in the cloud — orphaned, invisible, still billing. A later apply may try to create them again and fail on a name conflict, which is how people find out.

Native S3 state locking is now available through a lock file in the bucket; the DynamoDB table is the older mechanism and still widespread. Versioning on the bucket is what lets you recover, and it is the reason to turn it on before you need it.

Mark yourself
A plan shows a resource being destroyed and recreated when you expected an update. How do you find out why, and what can you do about it?

The plan marks the triggering attribute with # forces replacement. That is the answer — read the plan rather than guess. terraform plan -out then terraform show -json gives it mechanically when the diff is long.

Remedies, in order of preference: change the configuration so the immutable attribute does not change; lifecycle { create_before_destroy = true } when the resource can be doubled briefly; ignore_changes when something outside Terraform legitimately owns that field; moved blocks when it is only the address that changed. prevent_destroy is a guard rail, not a fix.

Mark yourself
Something was created by hand in the console. Bring it under Terraform without an outage.

Write the configuration to match what exists, then import — as an import block in modern Terraform, which makes the import itself reviewable, or terraform import for the older workflow. Then plan, and expect the first plan to be wrong: it shows every attribute where your configuration disagrees with reality. Iterate on the configuration until the plan is empty.

The empty plan is the whole test. Applying before you get there is how you cause the outage you were avoiding.

Containers and Kubernetes

Why does the order of lines in a Dockerfile change how long a build takes?

Each instruction produces a layer, and layers cache by the instruction plus the contents it brings in. The cache is invalidated from the first changed layer downwards — so COPY . . before npm install means every source edit reinstalls every dependency.

Copy the dependency manifest, install, then copy the source. The same reasoning drives multi-stage builds: the toolchain need not be in the image you ship, and a smaller image pulls faster on every node that has never seen it.

Mark yourself
A pod is in CrashLoopBackOff. What are your first commands, and what is each ruling out?

kubectl describe pod — events first, because image pull failures, failed mounts and scheduling problems all surface here and none of them are in the logs. kubectl logs --previous — the crashed container's output, not the one currently restarting. kubectl get events --sort-by=.lastTimestamp for the surrounding context.

Then the split that matters: did it start and exit, or never start? Exit code 0 means it ran to completion and the restart policy brought it back — the command is wrong for a long-running process. 137 is SIGKILL, usually the memory limit. 1 is the application's own failure, and the logs will say.

Mark yourself
A rollout completes, readiness probes pass, and users see 502s for about half a minute. Why?

Endpoint propagation lags pod deletion. When a pod is terminated, the kubelet sends SIGTERM and the endpoint controller removes it from Service endpoints, and those happen in parallel — kube-proxy or the ingress controller may keep sending traffic for a second or two after the process has begun shutting down.

The fixes are unglamorous: a preStop sleep of a few seconds so the pod stays up while endpoints converge, a terminationGracePeriodSeconds longer than the longest request, and an application that actually handles SIGTERM by draining rather than exiting immediately. A readiness probe that fails fast on shutdown helps; an ingress that balances to pod IPs directly makes the window shorter and more obvious.

Mark yourself
You set limits.cpu and no request. What have you done? And what is the difference between a pod being throttled and being OOMKilled?

Kubernetes defaults the request to the limit, so you have reserved the whole limit on the node — usually not what was intended, and it makes the pod Guaranteed rather than Burstable.

CPU is compressible: exceeding the limit throttles the process, which shows as latency and never as an error. Memory is not: exceeding the limit kills the container, exit 137, no grace. That asymmetry is the whole reason CPU limits are argued about and memory limits are not — a CPU limit can make a healthy service slow for no benefit, while a memory limit stops one pod taking down a node.

Delivery pipelines

Beyond the obvious security objection, what is wrong with a deploy that runs from an engineer's laptop credentials?

It is not reproducible and it is not attributable. Nobody else can run it, the environment that produced the artefact is unique to one machine, and when it goes wrong there is no record of what ran with which inputs. The security problem is real, but the reason it blocks a team is that the deploy cannot be reviewed, repeated, or rolled back by anyone else.

The answer is a short-lived identity issued to the pipeline — OIDC federation from the CI provider into an IAM role, with no stored key at all.

Mark yourself
Rolling, blue/green and canary. What does each cost, and which asks most of your monitoring?

Rolling is cheapest and slowest to undo: both versions serve at once, and rollback means another rolling update. Blue/green doubles the infrastructure for the duration and buys an instant switch back; it needs the database to be compatible with both versions, which is the part that bites. Canary sends a small share of real traffic to the new version and needs the most from monitoring, because the entire mechanism is a decision made from metrics — if you cannot measure error rate and latency for the canary separately, you have a slow rolling deploy with extra steps.

Mark yourself
The pipeline was green and the deploy still broke production. Name the gaps that allow that.

Tests that do not exercise the changed path. A test environment unlike production in a way that matters — data volume, concurrency, network policy, IAM. Configuration and secrets that differ per environment and are not themselves tested. A migration that is fine on an empty table and locks a large one. Something outside the artefact that changed: a base image tag, a dependency resolved at build time, an upstream API. And load, which almost no pipeline tests.

The honest summary is that green means “the things we thought to check still pass”, and production is the first place the code meets reality.

Mark yourself
What properties make a deploy safe to run on a Friday afternoon?

It can be undone quickly without a human deciding how. Its blast radius is bounded — a canary, a feature flag, one cell. It is observable within minutes, not hours, so the alert comes while someone is still there. The database change is backward-compatible, so rolling back the code does not require rolling back data. And it is small, because small changes have small failure modes.

Teams that cannot deploy on Friday do not have a Friday problem. They have a rollback problem.

Observability and being on call

Metric, log, trace. Which one tells you why a single request was slow, and why?

The trace. A metric is an aggregate and has already thrown away the individual request; a log line tells you what one component did but not where the time went across components. A trace carries a span per hop with timings, so the slow segment is visible rather than inferred.

In practice: the metric tells you something is wrong, the trace tells you where, the log tells you what. Skipping straight to logs is the common failure, and it is why people grep for an hour.

Mark yourself
A 99.9% availability objective. How much downtime is that a month, and what is the error budget for?

0.1% of about 43,200 minutes — roughly 43 minutes a month. 99.99% is about four minutes, which is why the extra nine is expensive.

The budget is a decision-making device, not a target. Budget remaining means you can take risks — ship faster, run an experiment. Budget spent means the next work is reliability work. Its real function is to end the argument between the people who want to ship and the people who want stability, by making it arithmetic.

Mark yourself
An alert fires every night at 02:00 and has never once been real. What do you do?

Fix it or delete it, today. An alert nobody acts on trains everyone to ignore alerts, including the one that matters — the cost is not the interruption, it is the next real page being dismissed.

What you do not do is silence it indefinitely and leave it in place, or add a filter that hides the symptom while the condition still occurs. If it represents something real but not urgent, it is a ticket, not a page. The discipline: every page should be actionable, and if you cannot say what the responder should do, it is not a page.

Mark yourself
P50 latency is unchanged. P99 has tripled. What produces that shape?

Something that affects a minority of requests, so the median never sees it. Garbage collection pauses. A cold cache for rare keys. One slow replica or one bad node taking a share of traffic. Lock contention that only matters above a concurrency threshold. A retry storm on a small fraction. Connection-pool exhaustion, where most requests get a connection instantly and the unlucky ones wait.

A uniform cause — more load everywhere, a slower dependency on every call — moves the median too. The median staying flat is the information.

Scripting, and knowing when to stop

set -euo pipefail. What does each part do, and which one surprises people?

-e exits on an unchecked non-zero status. -u errors on an unset variable. -o pipefail makes a pipeline fail if any stage fails rather than only the last.

-e is the surprise, because its exceptions are not obvious: it does not trigger inside a condition, in a && chain, or for any command whose status you test — so cmd || true is fine but if cmd; then silently continues on failure. People assume it means “stop on any error” and it does not.

Mark yourself
Fifty thousand records to pull from a rate-limited API that intermittently returns 500s. Describe the shape of the program, not the code.

Bounded concurrency rather than one at a time or all at once. Retry with exponential backoff and jitter, on a defined set of statuses — 429 and 5xx, never 4xx. Respect Retry-After when it is sent. Checkpoint progress so a crash at record 40,000 does not start again. Make each unit idempotent so a retry cannot duplicate. Log enough to resume. And a hard ceiling on total attempts so a broken endpoint does not loop forever.

Jitter is the part most people omit, and it is what stops every client retrying in lockstep.

Mark yourself
Why is parsing kubectl get pods output with awk fragile, and what do you do instead?

Column positions and widths are presentation, not an interface. They change between versions, shift when a name is long, and differ when a field is empty. Any tool that prints for humans will eventually print something your script did not expect.

-o json with jq, or -o jsonpath, or --template. The general rule applies well beyond kubectl: if a command offers structured output, the human-readable output is not an API.

Mark yourself
When do you stop writing bash?

Honest markers: when you need a data structure beyond a flat list; when you are parsing anything with quoting or nesting; when error handling has to do more than exit; when it needs tests; when it has outlived the problem it was written for, or has two people editing it. Arrays and arithmetic in bash are possible and they are a signal.

Bash is excellent at gluing commands together and bad at everything else. The failure mode is not writing bash — it is a 600-line bash script that nobody will touch and nobody can test.

State, and the ways it fails

Why is retrying a failed write dangerous, and what makes it safe?

Because a failure can mean the write did not happen, or that it happened and the acknowledgement was lost. The client cannot tell those apart, so a retry may apply the operation twice.

Idempotency makes it safe: a client-supplied key the server deduplicates on, a conditional write that fails if the state is not what you expected, or an operation that is naturally idempotent — setting a value rather than incrementing one. Payment APIs put an idempotency key in the request header for exactly this reason, and it is the pattern worth stealing.

Mark yourself
A read replica is forty seconds behind. Which user-visible bugs does that produce?

Read-your-own-writes failures, and they are maddening to report: a user saves a change, the page reloads from a replica, and the change is gone. They save again and now there are two. Pagination that shifts underneath a cursor. A job that reads a row it just wrote and finds nothing. Checks that pass on a stale replica and should have failed.

The mitigations are routing reads after a write to the primary for a window, a session-consistency token, or simply not reading from a replica for anything that drives a decision.

Mark yourself
A backup and a disaster recovery plan are not the same thing. What is the difference, and what do RPO and RTO mean?

A backup is a copy. A recovery plan is a tested sequence that gets a working system back, including the things that are not in the database — DNS, certificates, secrets, the order services must start in, and who has the authority to decide.

RPO is how much data you can afford to lose, which sets backup frequency. RTO is how long you can afford to be down, which sets the mechanism. The question that separates a plan from a wish is when did you last restore from it — an untested backup is a belief, not a capability.

Mark yourself
You put a cache in front of the database. Name failure modes that are worse than having no cache.

The stampede: the cache expires a hot key, every request misses at once, and the database takes a load it has never seen — mitigated by request coalescing or a probabilistic early refresh. The silent dependency: the system has been running on cache hits for months and nobody knows the database can no longer serve the full load, so a cache restart is now an outage. Stale data outliving its usefulness because invalidation was never built. And the cache becoming a second source of truth, where the two disagree and the cache wins.

Caching trades a correctness problem for a capacity problem. That is often the right trade, but it is a trade.
