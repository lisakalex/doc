Before anything else

What is here, and the one thing that is not

The repository is a complete small production system: a Python API that stores users in DynamoDB and avatars in S3, the AWS infrastructure for it, a Helm chart to run it on Kubernetes, and a CI pipeline that tests, scans, builds and pushes the image.

Three Terraform layers, not one

The repository splits its infrastructure into three root modules, each with its own state file, applied in order. That split is the first thing to understand, because it is a decision almost every real project makes and almost no tutorial explains.

LayerStateHoldsChanges
state-backend/localThe S3 bucket and lock table the other two store state inonce
cluster/cluster/terraform.tfstateVPC, EKS, nodes, add-ons, load balancer controller IAM — 43 resourcesa few times a year
terraform/terraform.tfstateS3, DynamoDB, KMS, ECR, CI identity, the app's IRSA role — 16 resourcesweekly

Why split at all. Different lifecycles, and different blast radius. terraform destroy in cluster/ removes a cluster; in the root module it removes a bucket. Those should not be the same command. One state file would also mean every routine application change plans against a VPC and a control plane it has no business touching, and a ten-minute cluster apply holding the lock an application deploy needs.

And they meet through outputs, not copied values. The root module reads the cluster layer's state with a terraform_remote_state data source to get the OIDC provider ARN its IRSA trust policy names. An issuer typed into a tfvars file by hand cannot notice that the cluster it names has been replaced — the role keeps trusting a provider that no longer exists, pods stop getting credentials, and nothing in the configuration changed to explain it.

What it would cost to run, which is why you should not

The EKS control plane is $0.10/hour with no free tier — about $73 a month. Two t3.large nodes are roughly $120, a NAT gateway about $32 plus data. Call it $230 a month standing still.

Everything on this page can be read, validated and rendered for nothing: terraform validate, terraform plan, helm template. The Kubernetes half also runs on kind for free, which is what the CI pipeline does.

Terraform

Four ideas, and that is most of it

1 · DESIRED STATE

You describe what should exist, not the steps to create it. There is no “create bucket” command anywhere — there is a description of a bucket, and Terraform works out whether to create, change or leave it. Run it twice and the second run does nothing.

2 · PROVIDER

A plugin that translates that description into API calls. hashicorp/aws here, pinned to ~> 6.60 in providers.tf. Terraform itself knows nothing about AWS; every resource type comes from the provider.

3 · STATE

A file mapping your names to real IDs: aws_s3_bucket.avatars → the actual bucket. Without it Terraform cannot tell “this already exists” from “make a new one”, because the cloud has no record of your naming. It also contains every attribute of every resource, which is why it holds secrets and belongs in an encrypted, versioned bucket.

4 · PLAN THEN APPLY

terraform plan compares three things — your code, the state, and what is really in AWS — and prints the difference. apply performs it. The plan is the safety feature: it is the only infrastructure tool-chain step where you see the change before it happens.

Everything else — modules, workspaces, for_each, providers for thirty other clouds — is built on those four. If they are solid, the rest is syntax.

The two things that surprise everyone, both visible in main.tf

One bucket is six resources. The bucket, its encryption, its ownership controls, its public-access block, its lifecycle rules, and the KMS key. Terraform resources map to AWS API calls, not to how you think about the object. When you read Terraform, count concepts rather than resource blocks — 175 lines here is about four ideas.

Nothing declares an order, and the order is still correct. The KMS key must exist before the encryption rule that points at it. Terraform knows because aws_kms_key.avatars.arn appears inside that rule, and every such reference is an edge in a graph it builds and then walks — in parallel wherever there is no edge. You write depends_on only for the rare dependency no reference expresses.

The four most important lines in the cluster layer

In cluster/eks-nodes.tf:

http_tokens = "required"
http_put_response_hop_limit = 1

The first forces IMDSv2. A caller must PUT for a session token before it can read anything. A server-side request forgery bug — an application that fetches a URL an attacker chose — can issue a GET but not a PUT. IMDSv1 hands the node's role to the internet; IMDSv2 does not. That difference is the Capital One breach, roughly 100 million records.

The second is counter-intuitive and just as important. The response gets an IP TTL of 1, so it reaches a process on the host and dies before it can cross the extra hop into a container. Pods therefore cannot read the node's credentials at all — which is exactly right when every pod that needs AWS has its own IRSA role. Raising it to 2 to “fix” a pod that cannot reach AWS gives every pod on that node the node's identity.

Kubernetes

Three ideas, and they are not the ones people expect

1 · AN API, NOT A TOOL

Kubernetes is a database of objects with an API in front of it. kubectl apply writes an object. That is the whole interaction. Nothing you type runs a container.

2 · CONTROLLERS RECONCILE

Separate processes watch for objects they care about and work continuously to make reality match them. You wrote replicas: 2; a controller notices there is one and starts another. It never finishes — it is a loop, not a command, which is why a deleted pod comes back and a drained node refills.

3 · LABELS JOIN EVERYTHING

There are no foreign keys. A Service finds pods by matching labels, and so do the HPA, the PodDisruptionBudget and the NetworkPolicy. Get a label wrong and nothing errors — the Service simply has no endpoints and every request fails. That is the most common Kubernetes bug there is.

Once those three are in place the object catalogue is just vocabulary. Here is the chart's:

Helm sits on top of all of this and is simpler than it looks: it is templating plus release tracking. values.yaml is the interface, the files in helm/templates/ are the implementation, and helm template renders them to plain YAML you can read. Run that first, before ever installing — it is Helm's terraform plan.

The part worth the whole page

Three wires join Terraform to Kubernetes

Terraform creates cloud resources. Kubernetes runs containers. The interesting question is how a container gets to use those resources, and the answer is three specific handoffs — all of them visible in this repository.

1 · Identity, with no key

The pod reads S3 and DynamoDB and holds no credentials. Terraform makes a role that trusts the cluster's OIDC provider for one exact ServiceAccount; the annotation puts that role on the ServiceAccount; the SDK exchanges a mounted token for credentials that expire hourly.

main.tf → aws_iam_role.app_role
outputs.tf → app_iam_role_arn
values.yaml → serviceAccount.annotations
→ eks.amazonaws.com/role-arn

2 · The image

Terraform creates the registry and the CI role that may push to it. CI builds, scans and pushes, then prints the digest. The chart runs that image — by digest when one is supplied, which no tag can later redirect.

ecr.tf → aws_ecr_repository.app
outputs.tf → ecr_repository_url
cicd.yml → push-to-ecr
values.yaml → image.repository / image.digest

3 · The names

The app needs to know which bucket and which table. Terraform decides those names; they arrive as environment variables through a ConfigMap. Changing the ConfigMap restarts the pods, because of the checksum annotation.

main.tf → bucket, table
outputs.tf → names
values.yaml → env:
configmap.yaml → envFrom

The handoff is manual, and that is the honest state of the art

Nothing automatically carries terraform output app_iam_role_arn into --set serviceAccount.annotations. A person reads one and types the other, or a pipeline does. Terraform can provision Kubernetes objects and Helm can be driven by Terraform, and both couplings bring their own problems.

So when a job advert asks for “Terraform and Kubernetes”, this seam is what it means. Being able to describe these three wires is most of what a mid-level interview is checking.

End to end

One request, through every object

A user uploads an avatar. Follow it, and each object earns its place.

  1. Ingress terminates TLS and routes the path to a Service.
  2. Service holds a stable virtual IP and picks one of the pods behind it — found by label, not by address.
  3. kube-proxy rewrites the destination to that pod's IP. The pod has been running since the Deployment created it and the readiness probe said it could take traffic.
  4. The app needs AWS. The SDK finds the token Kubernetes mounted because of the ServiceAccount, calls AssumeRoleWithWebIdentity, and gets temporary credentials.
  5. That call leaves the pod on port 443 — which the NetworkPolicy permits, and almost nothing else.
  6. It writes the object to S3, which encrypts it with the KMS key. The role's policy grants kms:GenerateDataKey for exactly this reason, and without that one statement the upload fails with an error that mentions neither KMS nor the key.
  7. It writes the user record to DynamoDB, keyed by email.
  8. Load rises; the HPA sees CPU above 60% of requests and raises the replica count. New pods land on other nodes because of the anti-affinity rule.
  9. A node is drained for an upgrade. The PodDisruptionBudget makes the drain wait rather than take the last pod.

Step 6 is the one to remember. Permissions that look complete fail because of a second policy on a different service, and the error names neither. You met this in the placement: there are about nine independent causes of AccessDenied and the KMS key policy is the one nobody guesses.

The part tutorials skip

Three environments, one configuration

Every tutorial shows you one environment. Every real job has at least three, and the difference between them is where most operational pain lives. Here each layer is applied once per Terraform workspace, with its inputs in a file beside it:

terraform workspace select prod
terraform init -reconfigure -backend-config=env/backend-prod.hcl
terraform plan -var-file=env/prod.tfvars

The obvious alternative — copy the directory three times — is what most teams do first and then regret, because three copies drift. A fix lands in production and never reaches staging, so staging stops being a rehearsal for anything.

Staging differs from production only in size

Look at which rows change and which do not. The AZ count, the NAT topology, the rollout strategy, the probe timings and the PodDisruptionBudget are identical between staging and production. Only size, retention and where the alerts go differ.

That is the entire point of staging. A rehearsal on a different stage tells you nothing: a staging environment with one replica and no disruption budget does not exercise a rolling update, so the rollout behaviour is first tested in production, by users.

The guard rails are in the code, not in a document

Two different severities, chosen deliberately. check blocks in env.tf warn on every plan — a single NAT gateway in production, unpinned add-on versions, running in the default workspace. A precondition in eks.tf fails the plan outright if production would expose the Kubernetes API to 0.0.0.0/0.

A warning is loud and still lets an emergency change through. A precondition is for the thing that must never ship. Getting that distinction wrong in either direction is how guard rails end up commented out.

And note what is not guarded: prevent_destroy is on the state bucket and not on the cluster. It takes a literal, so it cannot read “only in production” — setting it on the cluster would block dev teardown too, somebody would comment it out to get work done, and a guard rail people routinely disable teaches people to disable guard rails. Production deletion protection belongs in an IAM policy or an Organizations SCP, outside Terraform entirely. Terraform state describes intent; it is not an authorisation boundary.

How a change reaches production

One artefact, three environments, one human

push to main
  ↓
cicd.yml  test → build → scan → kind smoke test → sign → ECR
  ↓
cd.yml   resolve the digest, verify its signature
  ↓
  ↳ dev      commit digest → values-dev.yaml       (no gate)
    verify   poll /health until 200, or fail
  ↳ staging  commit digest → values-staging.yaml   (no gate)
    verify   poll /health until 200, or fail
  ↳ prod     commit digest → values-production.yaml  HUMAN APPROVAL

One digest travels the whole way. Nothing is rebuilt between environments. This is the same discipline as a Jenkins pipeline that builds a jar once and promotes it to test, UAT and production rather than rebuilding per stage — and for the same reason: two builds of the same commit genuinely can differ, because a base image tag moved, a transitive dependency resolved differently, or a timestamp got baked in.

The commit is the deploy

No workflow in this repository runs helm upgrade, and none holds cluster credentials. Each promotion writes one digest into gitops/values-<env>.yaml and pushes. Argo CD notices and reconciles the cluster to match.

Which means rolling back is the same mechanism as rolling forward: run the workflow with a previous digest. There is no separate rollback path to get wrong at 3am, which is the only time anyone uses it.

Terraform now gets the same treatment the application always had

The gap this closed is worth naming: the application had test, build, scan, smoke test, sign and push. The infrastructure was applied from somebody's laptop. The code deciding who can reach the Kubernetes API got less review than the code formatting a timestamp.

Now terraform.yml posts a plan as a pull-request comment per layer per environment, and — the part that matters — the apply uses the saved plan file, downloaded as an artifact, not a fresh plan. A fresh plan at apply time can differ from the one that was reviewed, so “approved” would mean approved-something-else. Terraform refuses a stale saved plan, and that refusal is the feature.

Two IAM roles, not one: the plan role is read-only, so a pull request cannot change anything. And drift.yml runs the same plan nightly, opening a GitHub issue when reality stops matching the code — because otherwise drift surfaces during an unrelated apply, under pressure, which is the worst possible moment to find it.

Sync-wave order is not a preference

A chart that installs CRDs must be in an earlier wave than anything whose manifests use them. Get it wrong and the error is no matches for kind "ServiceMonitor" — which reads exactly like a typo in your YAML and is in fact an ordering bug three files away.

The autoscaler failure worth memorising

Cluster Autoscaler finds the node groups it may manage by reading two tags on the Auto Scaling group. Tags set on the EKS node group object are not the same thing and are not reliably propagated down.

So a node group that looks correctly tagged in the EKS console is invisible to the autoscaler, which logs “no node groups configured” and does nothing. That is why eks-nodes.tf uses a separate aws_autoscaling_group_tag resource to reach the ASG that the managed node group created. It is the single most common reason a correctly-installed autoscaler does nothing at all.

When it breaks

An alert with no destination is a comment

The chart creates five alerts. Before the Alertmanager configuration existed, each one transitioned to firing on a dashboard nobody was looking at. That is the most common state of monitoring in the wild: the rules are written, nothing routes them, and everybody believes they are covered.

A ROUTE TREE

severity: critical pages PagerDuty and posts to Slack, so the channel has a record without the page depending on Slack being up. warning is Slack only. A catch-all matches anything with a severity nobody defined — a catch-all that goes nowhere is how an alert silently disappears.

GROUPING

By alertname, namespace and severity. Twenty failing pods become one page listing twenty pods, rather than twenty pages. The shape of an incident is in the grouping.

INHIBITION

KubeNodeNotReady suppresses the warnings from everything on that node. This is the rule that turns a node failure from twenty pages into one — the difference between alerting that helps and alerting that people mute.

A DEAD-MAN’S SWITCH

The Watchdog alert always fires, on purpose, into an external service that pages if it stops arriving. Without it, monitoring that has itself died looks exactly like a healthy cluster: both are silent.

A RUNBOOK LINK

Every alert carries a runbook_url annotation that Alertmanager passes into the PagerDuty payload and the Slack message. The point of a page at 3am is that it arrives with the first diagnostic step attached.

The fifth alert, and why four were not enough

The four original alerts covered error rate, latency, replicas not ready, and restart rate. There is a failure none of them can see.

When the HPA asks for a replica the cluster cannot place, the pod sits Pending indefinitely. The pods that are running are perfectly healthy — so error rate is fine, latency is fine, the ready count matches what the ReplicaSet managed to create. The service is under-provisioned and every alert is green.

UsersApiPodsPending is the one that catches it. Five minutes, because a Pending pod during a normal scale-up is expected: a node takes two to three minutes to boot and join.

Two numbers, often confused

RPO is how much data you can lose, in time. RTO is how long you can be down. They are bought separately and by different mechanisms: point-in-time recovery buys RPO, a rehearsed procedure buys RTO. A five-second RPO with a two-day RTO is perfectly coherent and perfectly useless.

And the sharp edge in docs/DISASTER_RECOVERY.md worth knowing before you need it: DynamoDB point-in-time recovery restores to a new table. It does not roll the existing one back. So the recovery involves a cutover, and therefore a decision, and therefore an outage — which is the part people discover during the incident rather than before it.

No account, no cluster, no risk. terraform init -backend=false then terraform validate; helm template helm/ to render every manifest to plain YAML. Start here, today.

Two things to know before the fourth route

terraform apply against real credentials creates real, billable resources, and variables.tf has a bucket name that must be globally unique. Read the plan. The plan exists for this.

The bucket is declared force_destroy = true, which means terraform destroy deletes it and everything in it without asking. Convenient for a throwaway stack, and exactly the setting you would never ship on something holding real user data.

Check

Six questions

Answer each one before opening it. If the answer is the first time it makes sense, that is a zero, and a zero is useful.

The S3 bucket in main.tf is one logical thing. How many Terraform resources describe it, and why is it not just one?

Six. aws_s3_bucket, plus aws_s3_bucket_server_side_encryption_configuration, aws_s3_bucket_ownership_controls, aws_s3_bucket_public_access_block, aws_s3_bucket_lifecycle_configuration, and the KMS key it encrypts with.

Because the AWS API is shaped that way — each of those is a separate API call against an existing bucket, not a field you set when creating one. Terraform resources map to API calls, not to how a human thinks about the object.

The practical consequence: when you read Terraform, count concepts, not resource blocks. 175 lines here is roughly four things.

Nothing in main.tf says what order to create things in. The KMS key must exist before the bucket encryption that references it. How does Terraform know?

It reads the references. kms_master_key_id = aws_kms_key.avatars.arn is not just a value — it is an edge in a dependency graph. Terraform builds that graph from every expression that mentions another resource, then walks it, creating things in dependency order and in parallel wherever there is no edge.

This is why you almost never write ordering by hand. When you genuinely need an edge that no reference creates, depends_on exists — and needing it often means the configuration could be expressed better.

There are two Terraform projects here: terraform/ and terraform/state-backend/. Why not one?

Chicken and egg. The main project stores its state in an S3 bucket with a DynamoDB lock table. Something has to create that bucket and table — and it cannot be the project that needs them to exist before it can run.

So state-backend/ is applied first, with ordinary local state, and creates the bucket, the lock table and a KMS key. After that the main project runs terraform init -backend-config=backend.hcl and keeps its state there.

Every team doing this hits the same problem and most solve it the same way. The bucket is versioned, which is what lets you recover when state goes wrong.

The pod talks to S3 and DynamoDB. Find the AWS access key it uses.

There isn't one. That is the point of the design, and tracing it is the single most useful thing in this repository.

Terraform creates an IAM role whose trust policy accepts tokens from the EKS cluster's OIDC provider, but only when sub is system:serviceaccount:default:prima-app-sa and aud is sts.amazonaws.com. The role ARN comes out as the app_iam_role_arn output. It goes onto the ServiceAccount as an annotation. Kubernetes mounts a signed token into the pod. The AWS SDK finds that token, calls AssumeRoleWithWebIdentity, and gets credentials that expire in about an hour.

No key is stored, committed, rotated or leaked, because none exists. The comment in main.tf about why aud must also be pinned is worth reading twice — without it, a token the same pod requested for a different audience would be accepted here.

The chart sets readOnlyRootFilesystem: true, and also mounts an emptyDir at /tmp. Why both?

Because the application genuinely needs to write somewhere, and the right answer is to allow exactly that one place rather than to give up on the control.

FastAPI spools large multipart uploads to disk once they pass a size threshold. With a read-only root and no writable mount the upload fails. With a writable root, anything that compromises the process can drop a binary anywhere in the image.

This is what defence in depth looks like in practice: not a switch you turn on, but a control plus the one deliberate exception that makes it survivable. emptyDir lives and dies with the pod, so nothing written there outlasts a restart.

The NetworkPolicy allows egress only to DNS and port 443. CI proves the chart installs cleanly on kind. Does that prove the policy works?

No, and the chart says so itself. NetworkPolicy is enforced by the CNI plugin, not by Kubernetes. kind's default CNI accepts the object and ignores it entirely.

So the test proves the manifest is valid. It proves nothing about whether a packet is actually blocked. On EKS you would need the VPC CNI with network policy support, or Calico or Cilium, before that policy does anything at all.

This is a good habit to copy: the chart's comments state what its tests do not prove. Most projects quietly let a green pipeline imply more than it checked.

What to take, and what not to

This is a specimen to read, not a project to claim. When phases 4 and 5 build the real thing, these are the patterns worth carrying over:

  • The state-backend bootstrap, almost verbatim. Every project needs it and it is always the same shape.
  • Outputs as a deliberate interface. Decide what the next tool needs, and output exactly that.
  • IRSA, with both sub and aud pinned. Not optional, and the reason is in the comment.
  • The security context — non-root, read-only root filesystem, all capabilities dropped — plus the one writable mount the app actually needs.
  • Comments that say what a test does not prove. The NetworkPolicy note is the best thing in the repository.

Also worth carrying over, from the second pass that finished the repository:

  • One configuration, many environments, with the differences in a reviewable file rather than in three copies of a directory.
  • Plan on the pull request, apply the saved plan. The second half is the part most teams miss, and it is what makes “approved” mean something.
  • The Alertmanager route tree with inhibition. Rules are easy; routing and suppression are what make alerting usable.
  • A runbook per alert, linked from the alert itself.
  • The honest “what is still missing” section at the end of docs/PRODUCTION_READINESS.md. A readiness document without one is marketing.

What not to take: the belief that this is finished. Everything here validates, lints and renders, and none of it has ever been applied — no cluster has ever existed, nothing has run under load, nothing has an SLO with an error budget, and nobody has been paged by it. The chart and add-on versions are pinned placeholders that have not been checked against upstream. The first real apply will find something; it always does. That gap is what phase 6 and the eight deliberate failures exist to close, and it is the gap the job adverts care most about.
