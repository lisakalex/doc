Build Once, Deploy Many

You already do this. It was the only full-marks answer in the placement, and you gave it without hesitating. This lesson is not here to teach you the practice — it is here to give you its name, the precise failure it prevents, and the three places your current setup probably leaks.

~3 hours no new tools applies at work on Monday

The thing you said

“We build and test in dev, then deploy the same artifact to test, UAT or prod”

That is artifact promotion, and the principle is build once, deploy many. Both names are standard and both will be recognised in an interview. Artifactory calls the operation promotion directly — moving a build from a staging repository to a release one without rebuilding it.

Having the name matters more than it sounds. A practice you follow is something you do because that is how the pipeline was set up. A practice you can name, justify and defend is a position you hold, and the difference is audible in about ten seconds of conversation.

The failure it prevents, stated precisely

If each environment rebuilds from source, then the thing you tested and the thing you shipped are different artifacts. Not different code — the commit is identical. Different bytes: a dependency resolved differently, a build agent with a different JDK patch, a plugin that pulled a newer version, a generated file with a different timestamp.

So when production breaks in a way UAT did not, nobody investigates the build, because “it is the same code”. That sentence is the bug. The investigation goes to infrastructure, to data, to load — everywhere except the one artifact that never passed through a test environment.

Leak one

Build once is worthless if the build is not reproducible

The promise is that app-1.4.0.jar is one specific set of bytes. Several ordinary things in a Maven project quietly break that promise, and the most common one is probably in your pom.xml right now.

The snapshot problem is worth checking this week

A -SNAPSHOT dependency resolves to the newest snapshot published at the moment of resolution. Build the same commit on Tuesday and Thursday and you can get different jars, with nothing in git to explain it.

The check is one command: mvn dependency:tree | grep SNAPSHOT against a release build. If anything comes back, your promoted artifact is less immutable than it looks. The enforcement is a rule in Artifactory that refuses a release whose dependency tree contains one.

Leak two

If the bytes are identical, every difference lives outside them

This follows logically and it is worth saying out loud, because it is where most of the design consequences come from. The jar in UAT and the jar in production are the same object. Therefore every difference between UAT and production — database host, credentials, queue name, log level, feature toggles, thread pool sizes — is supplied from outside at runtime.

GOOD

Values from the environment: environment variables, a mounted secret, Parameter Store or Secrets Manager read at startup. You already do the Parameter Store version of this, which means you already have the pattern.

ACCEPTABLE

Profile files inside the artifact (application-uat.yml) holding structure, with values injected. The bytes stay identical so promotion survives, and you keep somewhere sensible to see the shape of the config.

BROKEN

Environment-specific values baked into the artifact. Now a configuration change needs a rebuild, the rebuild needs re-promotion through every environment, and a secret is in source control forever.

The test for which one you have: can you change the production database password without producing a new artifact? If not, the configuration is inside the build, whatever the directory structure suggests.

Leak three, and the one that will bite you in phase 2

A container tag is not an artifact version

Your jar in Artifactory cannot change. Someone would have to delete and re-upload it, and most repositories forbid that outright. An image tag has no such guarantee. acme/ingest:1.4.0 is a mutable pointer: push different content to the same tag and it moves, silently, and every environment that pulls after that gets something else.

So the discipline you already have for jars has to be re-established at the image layer, and the thing that carries it is the digest — a content hash that cannot point anywhere else:

acme/ingest@sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08

Promote the digest. Keep tags as human-readable labels for finding things. Then turn on tag immutability in the registry — ECR and Artifactory both support it — so a push to an existing tag is rejected rather than accepted quietly.

latest is not a version

It is a tag with no meaning, applied by convention, pointing wherever it was last pushed. A cluster running latest cannot answer “what is in production?”, cannot roll back, and will pull something different on every pod restart depending on imagePullPolicy and what each node happens to have cached. Different pods of the same deployment can be running different code. You will meet this in phase 5; it is better met here.

The part that does not promote

Your artifact rolls back. Your database does not

Promotion gives you a rollback that is trivially available: 1.3.9 is still in the repository, deploy it. That works right up until 1.4.0 changed the schema — because now the old jar is running against a database it was never built for, and the rollback is a second outage with an unfamiliar stack trace.

The fix is expand and contract, also called parallel change: never make a schema change and a code change that depend on each other in the same release. Split it so that every pair of adjacent versions is compatible in both directions.

1 · EXPAND

Add the new column, nullable. Deploy. The running code ignores it entirely, so this release is a no-op that cannot break.

2 · DUAL WRITE

New code writes both old and new columns, reads the old. Deploy. Backfill existing rows. Rolling back here is safe — the old column is still correct.

3 · SWITCH

Read from the new column. Deploy. The old column is still being written, so a rollback still works.

4 · CONTRACT

Stop writing the old column, then drop it — a separate release, often weeks later, once you are confident nothing needs it.

Four deploys where an unconstrained change would be one, and each is individually reversible. That cost is the entire answer to “why can we not deploy on a Friday”. Teams that cannot deploy on a Friday usually do not have a deployment problem. They have a migration problem.

In the project

How Interchange does it, from week three

Phase 1

Each service builds one jar with a real version. Nothing environment-specific inside it. Configuration arrives as environment variables read by a systemd unit, so the pattern exists before containers complicate it.

Phase 2

Images are built once and referenced by digest. Base images pinned by digest for release builds. No latest anywhere, including in Compose.

Phase 4

The deployed digest is a Terraform or manifest input, not something the pipeline discovers. The commit that deployed a given version is therefore recoverable from git alone.

Phase 5

Failure drill 5 — the rollout that reports success while users get 502s — is run against a pinned digest, so you know the change in behaviour came from the rollout and not from the image moving underneath you.

And failure drill 4, two applies against one unlocked state file, has a cousin here: re-running a build job that pushes a mutable tag is the same class of mistake, one layer up. Both are “two writers, one name, last one wins”.

Check

Five questions

Answer each one out loud before you open it. Reading the answer first is how the last six months of reading turned into 7/64.

Your pom.xml depends on com.acme:common:1.4.0-SNAPSHOT. You build the same git commit on Tuesday and again on Thursday. Are the two jars identical?

No, and nothing about the commit tells you that. A -SNAPSHOT dependency resolves to the most recent snapshot build in the repository at the moment you resolve it. If the common team published on Wednesday, Thursday's jar contains different code than Tuesday's, built from an identical commit of your project.

This is the quiet version of the failure the whole practice exists to prevent. You promoted the Tuesday artifact through test and UAT, it passed, and then someone rebuilt for the production deploy — and shipped something nobody tested. The git history shows no change at all, which is why the investigation goes everywhere except the build.

The rule: nothing a release depends on may be a moving target. Release builds resolve only released versions. Many shops enforce it by making the release repository in Artifactory refuse to accept a build whose dependency tree contains a snapshot.

Your deploy pipeline pulls app-1.4.0.jar from JFrog and deploys it to test, then UAT, then production. Same bytes every time. Where does the database connection string come from, and why does that question follow from the first sentence?

It has to come from outside the artifact — environment variables, a Spring profile resolved at runtime, Parameter Store, a mounted secret. That is not a style preference. It is forced by the bytes being identical: if the artifact is the same in UAT and production, then every difference between UAT and production lives somewhere else by definition.

The common half-measure is bundling application-uat.yml and application-prod.yml inside the jar and selecting one with a profile flag. The bytes stay identical, so build-once survives — but now a production configuration change requires a rebuild and a re-promotion, and a secret has been committed to source control. The compromise worth making is structure in the jar, values from the environment.

You containerise the service. The pipeline builds acme/ingest:1.4.0, pushes it, and the deploy pulls acme/ingest:1.4.0 in each environment. Have you preserved build-once-deploy-many?

Not yet, because a tag is a mutable pointer. Nothing stops anyone — a person, or a re-run of the same pipeline job — pushing different content to 1.4.0 tomorrow. The tag moves and every environment that pulls afterwards gets something else. The jar in Artifactory could not do this to you; an image tag can.

What is immutable is the digest: acme/ingest@sha256:9f86d081…, which is a content hash and cannot point at anything else. Promote the digest, not the tag. Tags stay as human-readable labels for finding things.

Two supporting measures: turn on tag immutability in the registry (ECR and Artifactory both offer it) so a push to an existing tag is rejected, and never use latest, which is a tag with no meaning and the default answer to “which version is in production?” being “nobody knows”.

app-1.4.0.jar has been promoted to production and something is wrong. You roll back to 1.3.9, which is sitting in Artifactory, untouched. Under what circumstances does that not work?

When 1.4.0 changed the database. The artifact promotes; the schema does not. If 1.4.0's migration dropped a column, renamed one, or changed a type, then 1.3.9 is now running against a database it was never built for — and your rollback is an outage with a different stack trace.

The discipline that fixes it is expand and contract, sometimes called parallel change. Release the schema change and the code change separately, in an order where every adjacent pair of versions is compatible:

1. Add the new column, nullable, deploy. Old code ignores it.
2. Write to both old and new, deploy. Backfill the existing rows.
3. Read from the new column, deploy.
4. Only once nothing reads the old one, drop it — a separate release, often weeks later.

Four deploys instead of one, and each is individually reversible. That is the price of a rollback that actually works, and it is why “can we deploy on a Friday” is really a question about migrations.

Make the case in one paragraph, the way you would to a team lead who wants the deploy pipeline to just rebuild from the tag because “it is the same code”.

Something close to: “Same code is not the same artifact. A rebuild re-resolves dependencies, runs on whatever the agent has installed that week, and produces bytes nobody has tested. We would be shipping to production the one build that skipped test and UAT. Promoting the artifact costs us a repository and gives us a deployment that is identical to the one we verified.”

The phrase to have ready is build once, deploy many — or artifact promotion, which is what Artifactory calls it. Both are standard, both will be recognised, and having the name turns a practice you follow into a position you hold.
