Where the Memory Went

A Jenkins agent alerts: "free memory 3%". Someone asks for more RAM. Nothing was wrong. On another box, a Java service vanishes overnight: no stack trace, no error in its log, just exit code 137. That one was wrong. This lesson is about telling the two apart: what free actually counts, why a process can ask for memory it never gets, and who decides which process dies when memory really runs out.

~3 hours week 4 laptop only, no AWS Ubuntu 26.04 · kernel 7.0 · OpenJDK 21 · Python 3.14

Reading free

2 GB free on a 31 GB machine, and nothing is wrong

$ free -m total used free shared buff/cache available Mem: 31085 20972 3334 1814 9045 10112 Swap: 8191 21 8170

Read the columns as three kinds of memory, not as "used" against "free":

The same 31,085 MB, drawn to scale
programs 18,706 buff/cache 9,045 free 3,334
used = total − available = 20,972 available 10,112
1

freeMemory holding nothing at all. On a healthy Linux machine this is small, on purpose. Empty RAM does no work, so the kernel fills it.

2

buff/cacheCopies of files the kernel has read or written recently: the page cache. Jars, logs, the Maven repository. If a program needs the memory, the kernel drops clean cached pages and hands them over. They cost a disk read later, nothing now.

3

availableThe kernel's estimate of how much a program could get without swapping: free memory plus the part of the cache it can drop. This is the number to alert on.

The bracket under the bar doesn't line up with the coloured blocks, and that's the point. Not all of the cache can be dropped, so available covers the free block and only most of the cache. On this version of free (procps-ng 4.0.4), used is simply total − available. Older versions computed it differently, so don't compare the used column across distributions. Compare available.

The page cache

Reading a file takes 1 GB from "free" and nothing from "available"

A 1 GB file on disk, evicted from the cache first, then read twice. fincore shows how much of a file is sitting in RAM:

$ fincore big.bin RES PAGES SIZE FILE 0B 0 1G big.bin # not cached $ dd if=big.bin of=/dev/null bs=1M 1073741824 bytes (1.1 GB, 1.0 GiB) copied, 0.621026 s, 1.7 GB/s # from disk $ fincore big.bin RES PAGES SIZE FILE 1G 262144 1G big.bin # all of it is cached now $ dd if=big.bin of=/dev/null bs=1M 1073741824 bytes (1.1 GB, 1.0 GiB) copied, 0.0577978 s, 19 GB/s # from RAM

Before the read3,3349,04510,112
After the read2,30710,06910,108
Change−1,027+1,024−4

A monitor watching free sees a gigabyte disappear. A monitor watching available sees nothing happen, which is correct: the second read was ten times faster, and the kernel will give that gigabyte back the moment someone asks. A build agent that reads a lot of jars always looks "full" by the first measure.

The exception: tmpfs is cache that can't be dropped

The first attempt at this demo ran in /tmp, which on Ubuntu 26.04 is a tmpfs: a filesystem that lives in RAM. The 1 GB file went into shared (1,811 → 2,836 MB) and couldn't be evicted, because RAM is the only place it exists. tmpfs files and shared memory are counted in buff/cache but not in available. A build that fills /tmp or /dev/shm is really using memory.

Process memory

Asking for memory is not getting it

Two numbers describe a process's memory. VSZ (virtual size) is everything it has asked for. RSS (resident set size) is the part actually sitting in RAM right now. A Python process asks for 2 GB, then writes one byte into each 4 KB page of the first 512 MB:

$ python3 lazy.py start VSZ 21 MB RSS 9 MB after asking for 2 GB VSZ 2069 MB RSS 10 MB after touching 512 MB VSZ 2069 MB RSS 522 MB

Asking for 2 GB cost nothing. The kernel only wrote down a promise. RAM is handed over one page at a time, the first time each page is touched (a page fault). That's why VSZ is almost useless for capacity planning, and why a JVM with -Xmx4g can show a 4 GB VSZ and a 600 MB RSS.

Overcommit: the bill arrives later

Because promises are cheap, Linux lets processes ask for more than the machine has (vm.overcommit_memory = 0, the default, refuses only absurd requests). So malloc() almost never fails. The failure comes later, when the pages are touched and there is nothing left to give. At that point no function can return an error, so the kernel has to take memory back from somebody.

Running out

Drop cache, then swap, then kill

When a page is needed and nothing is free, the kernel works down a list:

1

Reclaim cacheDrop clean page-cache pages. Cheap. This is why available exists.

2

Write back and swapWrite dirty cache to disk, and move rarely used program pages to swap. Slow. The machine stays up but everything stalls on disk. A Java heap partly in swap makes garbage collection crawl.

3

The OOM killerNothing left to reclaim. The kernel picks one process and sends it SIGKILL. No warning, no cleanup, no shutdown hook.

Step 2 shows up before step 3, in the pressure gauge. /proc/pressure/memory reports the share of time processes spent waiting for memory. some means at least one task was stalled; full means all of them were:

$ cat /proc/pressure/memory some avg10=0.00 avg60=0.00 avg300=0.00 total=316455 full avg10=0.00 avg60=0.00 avg300=0.00 total=304477

All zeros here: 10 GB available, nothing waiting. A some avg60 that sits above a few percent means the machine really is short, whatever free says.

The choice

Who the OOM killer picks

Every process has an oom_score. It is mostly the process's share of memory, shifted by oom_score_adj, a setting from −1000 to +1000. The highest score is killed. On this laptop:

$ for p in /proc/[0-9]*; do …; done | sort -rn | head -5 score adj RSS_MB name 880 300 852 claude-desktop 872 300 339 chrome 872 300 336 chrome 870 300 202 cef_server 869 300 195 cef_server sshd score=0 adj=-1000 # never killed systemd-journal score=501 adj=-250

The browser-style apps raised their own oom_score_adj to 300, volunteering to die first. sshd set −1000, so you can always log in to a machine that is out of memory. On a Mule server the biggest process is almost always the JVM, so it is almost always the victim. That is usually the right choice, and it is also why the service you care about is the one that disappears.

cgroups

A limit smaller than the machine, and exit code 137

A cgroup is a group of processes the kernel accounts for together. Give it a memory limit, and the group runs out of memory long before the machine does. Every Docker container and every Kubernetes pod is a cgroup. systemd-run makes one on a laptop, no container needed:

$ systemd-run --user --scope -p MemoryMax=300M -p MemorySwapMax=0 python3 grow.py holding 50 MB holding 100 MB holding 150 MB holding 200 MB holding 250 MB Killed $ echo $? 137

137 = 128 + 9. The shell reports "killed by signal N" as exit code 128 + N, and signal 9 is SIGKILL. Python never printed an error: a process can't catch SIGKILL, so it had no chance to. The only witness is the kernel log:

$ journalctl -k | grep -i oom oom-kill:constraint=CONSTRAINT_MEMCG,…,oom_memcg=/user.slice/…/run-p270848-i257652.scope,task=python3,pid=270848 Memory cgroup out of memory: Killed process 270848 (python3) total-vm:328644kB, anon-rss:306476kB, …

CONSTRAINT_MEMCG means the limit hit was the cgroup's, not the machine's. The laptop had 10 GB available the whole time. In Kubernetes the same event shows as Reason: OOMKilled, Exit Code: 137 on the pod, and the limit is resources.limits.memory.

Java

Two ways a JVM dies, and only one leaves a stack trace

A JVM started without -Xmx sizes its heap from the memory it can see, and it reads the cgroup limit, not the machine's RAM:

no limit (31 GB laptop): MaxHeapSize 7772 MB # 25% of RAM cgroup MemoryMax=1G: MaxHeapSize 256 MB # 25% of the limit 1G, -XX:MaxRAMPercentage=75: MaxHeapSize 768 MB

The default is 25%, which wastes three quarters of a container. Now a Java program that keeps allocating 50 MB arrays, under a 1 GB limit, twice:

A · default heap (256 MB)

heap holds 200 MB Exception in thread "main" java.lang.OutOfMemoryError: Java heap space at Grow.main(Grow.java:6) exit=1

B · -Xmx2g, above the limit

heap holds 800 MB heap holds 850 MB heap holds 900 MB exit=137

In A the JVM hit its own ceiling first. It threw an error you can log, catch, and see in the console. In B the heap was allowed to grow past the cgroup, so the kernel got there first and sent SIGKILL. No exception, no heap dump, no last log line. The log just stops.

The heap is not the whole JVM

Setting -Xmx equal to the container limit still ends in 137. The JVM also uses memory outside the heap: metaspace for classes, a stack per thread, the JIT's code cache, direct buffers for network I/O, and the garbage collector's own tables. A Mule or Camel app with many routes and threads can spend several hundred MB there. Leave room: start with -XX:MaxRAMPercentage=75 and measure RSS under load.

Part 2: watch the page cache

cat > evict.py <<'EOF' import os, sys fd = os.open(sys.argv[1], os.O_RDONLY); os.fsync(fd) os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED); os.close(fd) EOF head -c 1G /dev/urandom > big.bin python3 evict.py big.bin; fincore big.bin; free -m dd if=big.bin of=/dev/null bs=1M fincore big.bin; free -m dd if=big.bin of=/dev/null bs=1M rm big.bin; free -m

Predict before you run it: after the first dd, which of free, buff/cache and available will move, and by how much? What happens to buff/cache after rm?

Part 3: ask for memory, then use it

cat > lazy.py <<'EOF' import mmap def show(label): st = {l.split(':')[0]: l.split()[1] for l in open('/proc/self/status') if l.startswith(('VmSize','VmRSS'))} print(f"{label:<28} VSZ {int(st['VmSize'])//1024:>5} MB RSS {int(st['VmRSS'])//1024:>5} MB") show("start") m = mmap.mmap(-1, 2 * 1024**3) # ask for 2 GB show("after asking for 2 GB") for i in range(0, 512 * 1024**2, 4096): # touch the first 512 MB, one byte per page m[i] = 1 show("after touching 512 MB") EOF python3 lazy.py

Predict the RSS on each of the three lines.

Part 4: the OOM killer in a cgroup

cat > grow.py <<'EOF' hold = [] for i in range(1, 100): hold.append(bytearray(50 * 1024**2)) # 50 MB, zero-filled, so really touched print(f"holding {i*50} MB", flush=True) EOF systemd-run --user --scope -p MemoryMax=300M -p MemorySwapMax=0 python3 grow.py echo "exit=$?" journalctl -k --since -2min | grep -iE 'oom-kill|Killed process'

Predict the last "holding" line and the exit code. Then find the word in the kernel log that proves it was the cgroup's limit, not the machine's.

Part 5: two ways for Java to die

cat > Grow.java <<'EOF' import java.util.*; public class Grow { public static void main(String[] a) { List<byte[]> hold = new ArrayList<>(); for (int i = 1; ; i++) { byte[] b = new byte[50 * 1024 * 1024]; Arrays.fill(b, (byte) 1); hold.add(b); System.out.println("heap holds " + i * 50 + " MB"); } } } EOF javac Grow.java java -XX:+PrintFlagsFinal -version 2>/dev/null | grep ' MaxHeapSize ' systemd-run --user --scope -p MemoryMax=1G -p MemorySwapMax=0 java Grow; echo "exit=$?" systemd-run --user --scope -p MemoryMax=1G -p MemorySwapMax=0 java -Xmx2g Grow; echo "exit=$?"

Predict both exit codes, and which run prints a Java exception.

Part 6: your servers

On a Mule server or Jenkins agent, and only looking: run free -m and read available, not free. Run ps -o pid,rss,args -C java and find each JVM's -Xmx. Add the -Xmx values up and compare them with total RAM. Has a Mule app ever "just stopped" with nothing in its log? That is your interview story for this lesson. Leave out hostnames and anything that looks like a password.

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

Monitoring on a Jenkins agent says "free memory 3%". free -m shows 40% available. Do you need more RAM?

No, the monitor is reading the wrong column. Free memory is RAM holding nothing, and Linux keeps it small on purpose by filling it with page cache: the jars, artifacts and workspaces the agent has read. The kernel drops clean cache the moment a program needs the memory, so available (40%) is the real headroom. Change the alert to MemAvailable, and add memory pressure (/proc/pressure/memory) if you want to know when the box really is short.

A Java container restarts with exit code 137. Its log stops mid-line, with no exception. What killed it, and where do you look?

The kernel's OOM killer, because the container hit its cgroup memory limit. 137 is 128 + 9, killed by SIGKILL, which a process can't catch, so Java never had the chance to log anything. Look in the kernel log (journalctl -k or dmesg) for Memory cgroup out of memory, or in Kubernetes for Reason: OOMKilled in kubectl describe pod. The cause is a JVM whose total memory, heap plus everything else, grew past the limit.

A JVM in a container with a 1 GiB limit and no -Xmx throws OutOfMemoryError: Java heap space at about 256 MB. Why 256, and what do you change?

Because the JVM defaults to a heap of 25% of the memory it sees, and it sees the cgroup limit. 25% of 1 GiB is 256 MiB, so the heap hits its own ceiling while three quarters of the container sits unused. Raise it with -XX:MaxRAMPercentage=75 (better than a fixed -Xmx, because it follows the limit if someone changes it), then check RSS under real load.

Someone sets -Xmx1g in a 1 GiB container to "use all of it". The container is now killed with 137 under load. Why?

Because the heap is only part of the JVM's memory. Metaspace, one stack per thread, the JIT code cache, direct buffers and GC structures all live outside the heap, and the cgroup counts all of it. With the heap allowed to reach the full limit, the extra pushes the process past it, and the kernel kills it before Java ever reaches its own heap limit. Leave headroom: heap around 75% of the limit, then measure.

A program allocates 2 GB on a machine with 1 GB available. The allocation succeeds. An hour later the program is killed. Why didn't the allocation fail?

Because asking for memory only reserves address space. Linux overcommits: malloc or mmap returns at once, VSZ goes up, and RAM is handed over page by page only when each page is first touched. The program filled its 2 GB slowly; when the touched pages exceeded what the kernel could reclaim, there was no function call left to fail, so the OOM killer picked the biggest process, which was this one.
