Ansible Idempotency, Named

You have run Ansible for two years and you know it is "idempotent". This lesson makes that word precise: what Ansible checks before it acts, why shell and command skip that check, and the four tools that put it back. You prove it on your own laptop by running a playbook twice and reading one number.

~3 hours week 2 laptop only, no AWS ansible-core 2.21.5

The definition

Idempotent means two things, and the second gets forgotten

An operation is idempotent when doing it twice leaves the system the same as doing it once. For an Ansible playbook that splits into two separate promises:

  1. Safe to re-run. The second run does no harm. It does not append a line again, create a second user, or fail because the directory already exists.
  2. Honest about it. The second run reports that nothing changed. Every task says ok, not changed, and the recap ends in changed=0.

Most people stop at the first. The second matters as much, for two reasons. Handlers fire on changed, so a task that always reports changed restarts your service on every run. And the recap is your only signal that a server had drifted. If every run says changed=12, the day a server really was wrong looks exactly like every other day.

The one test that matters

Run the playbook twice against the same machine. The second run must end in changed=0. That is the whole definition in one line, and it is the answer to give in an interview.

The mechanism

What a module does that a shell line does not

A module such as lineinfile is a small Python program that Ansible copies to the host and runs. It describes a state, not an action: "this line is in this file", not "append this line". Every well-written module follows the same four steps:

1

ReadLook at the current state. Is the line in the file? What is the file's checksum? Does the user exist?

2

CompareCompare it with the state the task asked for.

3

Act on the difference onlyIf they match, do nothing. If they differ, make the smallest change that closes the gap.

4

ReportReturn changed: true only if step 3 actually did something.

command and shell cannot do steps 1 to 3. They receive a string and run it. Ansible has no idea whether echo "-Xmx512m" >> jvm.options changes anything, so it does the only safe thing for step 4: it assumes the command changed something and reports changed, every time.

command runs the program directly, with no shell, so pipes, >> and $VAR do not work in it. shell runs it through /bin/sh, so they do. Neither one knows what the command does.

Seen on a real run

The quick way, run twice

This playbook is the kind you write when a deadline is close. It configures a directory on your own laptop, standing in for an app server. Every task works:

- name: Set up the app box, the quick way hosts: localhost connection: local gather_facts: false vars: ansible_python_interpreter: "{{ ansible_playbook_python }}" box: "{{ playbook_dir }}/box" tasks: - name: Make the app directory ansible.builtin.shell: mkdir -p {{ box }}/app - name: Set the heap size ansible.builtin.shell: echo "-Xmx512m" >> {{ box }}/app/jvm.options - name: Unpack the release ansible.builtin.command: tar xzf {{ playbook_dir }}/app-1.0.tgz -C {{ box }}/app - name: Show the JVM options ansible.builtin.command: cat {{ box }}/app/jvm.options notify: Restart app handlers: - name: Restart app ansible.builtin.shell: date >> {{ box }}/restarts.log

Run it twice. These are the real recaps from ansible-core 2.21.5:

# first run localhost : ok=5 changed=5 unreachable=0 failed=0 skipped=0 # second run, nothing new to do localhost : ok=5 changed=5 unreachable=0 failed=0 skipped=0 $ cat box/app/jvm.options -Xmx512m -Xmx512m $ wc -l < box/restarts.log 2

A restart on every deploy

Scale the second row up to work. A playbook that runs against a cluster of Mule runtimes, with a shell task notifying a restart handler, restarts every node on every run, even when nothing changed. That is an outage window you scheduled by accident, and the recap gives you no way to tell it apart from a real change.

The fixes, in order of preference

Four ways to put the check back

Reach for them in this order. Each step down gives Ansible less information, so you write more of the check yourself.

1. Use a module

Most shell lines in real playbooks have a module that does the same job with the check built in. Use it whenever one exists:

Instead of this in shellUse this module
mkdir -p, chmod, chown, ln -sansible.builtin.file
echo … >>, sed -i on one lineansible.builtin.lineinfile, replace, blockinfile
cp, writing a config with cat <<EOFansible.builtin.copy, template
curl -o, wgetansible.builtin.get_url
tar xzf, unzipansible.builtin.unarchive
useradd, groupaddansible.builtin.user, group
apt-get install, yum installansible.builtin.package, apt, dnf
systemctl restart, enableansible.builtin.systemd_service, in a handler

A module is not automatically idempotent: it is only as good as its step 1. unarchive, for example, compares files inside the archive with files on disk, which is a real check. get_url without a checksum only checks that the file exists.

2. creates and removes

When you really must run a command, tell Ansible which file the command leaves behind. creates: /path means "skip this task if that path exists". removes is the opposite: run only if it exists.

- name: Unpack the release ansible.builtin.command: tar xzf /tmp/app-1.0.tgz -C /opt/app args: creates: /opt/app/README

It checks that a file exists, nothing more

Change the archive to app-1.1.tgz and the task is skipped, because /opt/app/README is still there from 1.0. The recap says ok, the server still runs 1.0, and nobody notices. Point creates at something that only exists for the version you want, such as /opt/app/releases/1.1/, and unpack each version into its own directory. That is the same layout a current symlink deploy uses.

3. changed_when and failed_when

These do not stop the command from running. They tell Ansible how to judge the result, from the return code or the output, which you capture with register:

Read-only: it never changes anything

- name: Show the JVM options ansible.builtin.command: cat /opt/app/jvm.options register: opts changed_when: false

The command says what it did

- name: Apply database migrations ansible.builtin.command: /opt/app/bin/migrate register: migrate changed_when: "'Applied' in migrate.stdout"

failed_when is the same idea for failure. grep exits with 1 when it finds nothing, which Ansible treats as an error. If "not found" is a normal answer, say so: failed_when: result.rc not in [0, 1].

changed_when: false on a command that does change something is a lie in the other direction. The handler never fires and the recap hides a real change. Use it only on commands that read.

4. Check, then act

When the only way to know the state is to ask, ask in one task and act in the next:

- name: Is the schema there? ansible.builtin.command: test -f /opt/app/schema.done register: schema changed_when: false failed_when: schema.rc not in [0, 1] check_mode: false # a read: safe to run even in a dry run - name: Create the schema ansible.builtin.shell: /opt/app/bin/init-schema && touch /opt/app/schema.done when: schema.rc == 1

This is steps 1 to 3 of the module ladder, written by hand. It is also the most code to get wrong, which is why it comes last.

Dry runs

--check is only as honest as your modules

ansible-playbook --check --diff asks every task what it would do without doing it. Modules answer from step 1 and step 2. A command or shell task cannot answer, so in check mode it is skipped, unless it has creates or removes, which give Ansible something to check.

The result, on a real run against an empty directory, with the check-then-act pair above:

$ ansible-playbook -i localhost, schema.yml --check # output trimmed TASK [Is the schema there?] ok: [localhost] TASK [Create the schema] skipping: [localhost] localhost : ok=1 changed=0 skipped=1

The dry run says nothing would change. A real run would create the schema. A playbook built mostly from shell gives you a dry run that reports "nothing to do" while the real run is about to do a lot. Without check_mode: false on the read, it is worse: the read is skipped too, and the next task's when tests a result that never existed.

Remember this in Phase 4. terraform plan is check mode built into the tool from the start, and it works because every Terraform resource has to implement step 1. There is no shell resource to hide behind, only provisioners, and the Terraform documentation calls those a last resort for exactly this reason.

Proving it

Test idempotency like any other behaviour

The two-run test can run in CI. Molecule, the standard testing tool for Ansible roles, has an idempotence step that does exactly this: converge once, converge again, fail if the second run reports any change. Without Molecule, the same check is a few lines of shell after the second run:

ansible-playbook -i inventory site.yml # converge ansible-playbook -i inventory site.yml | tee second.log # any host with a non-zero count in its recap line fails the job if grep -Eq '(changed|unreachable|failed)=[1-9]' second.log; then echo "not idempotent"; exit 1 fi

Build it

Make the quick playbook honest

Everything runs on your laptop against a directory, so nothing on your system is touched. Work in devops-course/labs/p0-4/ so the files are committed and I can review them.

Part 1: set up

uv tool install ansible-core==2.21.5 ansible-playbook --version # expect: core 2.21.5 mkdir -p ~/IdeaProjects/devops-course/labs/p0-4 && cd $_ mkdir -p src && echo "release 1.0" > src/README tar czf app-1.0.tgz -C src README

-i localhost, in the commands below is an inventory written inline. The trailing comma is what makes Ansible read it as a list of hosts and not as a file name. connection: local in the play runs the tasks directly, without SSH. Lesson 0.5 is about why the version is pinned.

Part 2: watch it fail

  1. Save the quick playbook from above as naive.yml.
  2. Run ansible-playbook -i localhost, naive.yml twice.
  3. Confirm the second recap says changed=5, the heap line is in box/app/jvm.options twice, and box/restarts.log has two lines.
  4. rm -rf box to start clean.

Part 3: fix it

Write fixed.yml, doing the same four jobs. Pick the fix for each task from the four above, highest on the list that fits:

  1. The directory.
  2. The heap size, and move the notify: Restart app here, to the task whose change really should restart the app.
  3. Unpacking the release. Try it two ways: unarchive, then command with creates. unarchive needs its dest directory to exist already, so task order matters. By default its src is a file on the machine running Ansible, which it copies to the host first. Here both are your laptop, so that works as it is.
  4. Showing the options, which must still run and print every time.

Done when: the first run reports changes and one restart, and the second run ends changed=0 with no new line in restarts.log.

Then break it on purpose

  1. Make app-1.1.tgz with release 1.1 in its README, and point the creates version of the unpack task at it. Run it. Does box/app/README say 1.1? What did the recap say?
  2. Fix it with a versioned directory: unpack into box/app/releases/1.1/ and make creates point inside it.
  3. Run --check --diff on a clean box and compare its recap with a real run. Which tasks did the dry run skip?

Check

Five questions

Out loud first, and end each one with "because…" and the consequence.

A playbook's second run reports changed=7, yet nothing on the server is different. Nothing broke, so why does it matter?

Handlers fire on changed, so any of those seven tasks that notifies a restart restarts the service on every run: an outage window nobody planned.

And the recap stops meaning anything. If every run says changed=7, a run where a server had really drifted looks exactly the same, so you lose the one signal Ansible gives you for free.

A task unpacks app-1.1.tgz with command and creates: /opt/app/README. You bump it to 1.2 and run. What happens?

The task is skipped and the server stays on 1.1. creates only checks that the path exists, and the 1.1 README is still there. The recap says ok, so the failed upgrade is silent.

Fix: unpack each version into its own directory and point creates inside it, for example /opt/app/releases/1.2/README, or use unarchive, which compares the archive's contents with the files on disk.

What is the difference between creates and changed_when: false?

creates decides whether the command runs. If the path exists, the command does not run at all. changed_when only decides what the report says. The command runs every time.

So changed_when: false is right for a command that only reads, and wrong for one that changes something: the change still happens, but the recap hides it and the handler never fires.

You run --check on a playbook made mostly of shell tasks and it reports changed=0. Can you trust it?

No. In check mode, command and shell tasks without creates or removes are skipped, because Ansible cannot predict what a command will do. A skipped task counts as no change.

So the dry run is quiet about exactly the tasks most likely to do something. A dry run is only as honest as the modules in the playbook.

A task runs grep -q ERROR /var/log/app.log to decide whether to alert. When the log is clean, the whole play fails. Why, and what is the fix?

grep exits with 1 when it finds nothing, and Ansible treats any non-zero exit as a failure. Here "nothing found" is the good answer, not an error.

Fix: register the result, add failed_when: result.rc not in [0, 1] so only a real error (exit 2, such as a missing file) fails, and changed_when: false because reading a log changes nothing. Then act on it with when: result.rc == 0.
