Jenkins to GitHub Actions

You maintain two Jenkins pipelines in production. GitHub Actions has the same concepts under different names, and the renaming takes an afternoon. What catches Jenkins people out is four places where the mechanism is different, and every one of them can quietly break build-once-deploy-many.

~4 hours week 1 builds Interchange's first workflow

Worked example

A pipeline shaped like yours, translated

Not your employer's pipeline, but the same shape: build and test, publish the jar to JFrog, deploy it to UAT with Ansible, wait for a human, deploy the same version to production.

Jenkinsfile

pipeline { agent { label 'maven-jdk21' } options { disableConcurrentBuilds() } environment { JFROG = credentials('jfrog-deployer') } stages { stage('Build') { steps { sh 'mvn -B verify' script { env.VERSION = sh(returnStdout: true, script: 'mvn -q help:evaluate ' + '-Dexpression=project.version ' + '-DforceStdout').trim() } } } stage('Publish') { when { branch 'main' } steps { sh 'mvn -B deploy -DskipTests' } } stage('Deploy UAT') { when { branch 'main' } steps { sh "ansible-playbook deploy.yml " + "-e env=uat -e version=${VERSION}" } } stage('Approve') { when { branch 'main' } steps { input 'Deploy to production?' } } stage('Deploy prod') { when { branch 'main' } steps { sh "ansible-playbook deploy.yml " + "-e env=prod -e version=${VERSION}" } } } }

.github/workflows/release.yml

name: release on: push: branches: [main] pull_request: permissions: contents: read concurrency: group: release-${{ github.ref }} jobs: build: runs-on: ubuntu-24.04 outputs: version: ${{ steps.v.outputs.version }} steps: - uses: actions/checkout@v7 - uses: actions/setup-java@v6 with: distribution: temurin java-version: '21' cache: maven - id: v run: | v=$(./mvnw -q help:evaluate \ -Dexpression=project.version -DforceStdout) echo "version=$v" >> "$GITHUB_OUTPUT" - name: Build, test, and publish on main run: | goal=verify [ "$GITHUB_REF" = refs/heads/main ] && goal=deploy ./mvnw -B -ntp "$goal" env: JFROG_USER: ${{ secrets.JFROG_USER }} JFROG_TOKEN: ${{ secrets.JFROG_TOKEN }} deploy-uat: needs: build if: github.ref == 'refs/heads/main' runs-on: [self-hosted, uat] environment: uat steps: - uses: actions/checkout@v7 - run: > ansible-playbook deploy.yml -e env=uat -e version=${{ needs.build.outputs.version }} deploy-prod: needs: [build, deploy-uat] runs-on: [self-hosted, prod] environment: production # reviewers = input steps: - uses: actions/checkout@v7 - run: > ansible-playbook deploy.yml -e env=prod -e version=${{ needs.build.outputs.version }}

Tags like @v7 are shown for readability. The fourth difference below is why Interchange pins every action to a commit SHA instead. The JFrog secrets are stored credentials, exactly like Jenkins's; Lesson 0.3 removes them.

Line by line it is a translation. Three choices in it are not obvious, and each one is answering one of the differences below: build and publish happen in one job, the deploy jobs run on self-hosted runners, and the deploy jobs pass a version number, never a jar they built.

Where the mechanism differs

Four things that are not just renaming

1

Every job is a fresh machine

A Jenkins agent is a long-lived server. The workspace from the last build is still on disk, and ~/.m2 has two years of downloads in it. A GitHub-hosted runner is a new VM for every job, thrown away when the job ends.

  • Nothing carries between jobs. A file built in job build does not exist in job deploy unless you pass it with upload-artifact and download-artifact, or through a registry.
  • The Maven cache starts empty. Without cache: maven on setup-java, every job downloads Spring and Camel from scratch.
  • Jobs run in parallel unless you say otherwise. Three jobs with no needs: all start at once, on three machines. Jenkins stages run in order by default; Actions jobs do not.

Becausethe unit of isolation is the job, not the pipeline. Steps share a machine; jobs never do.

Upsideno drift. Cause 2 from Lesson 0.1a, two agents with different JDK patches, mostly disappears when every build starts from the same image.

2

Splitting a stage into a job can rebuild your artifact

In the Jenkinsfile, Publish runs mvn deploy after Build ran mvn verify. That re-runs the whole lifecycle, but in the same workspace, so it mostly reuses target/. Translate those two stages into two jobs and the second one is a fresh machine: it re-resolves dependencies, recompiles and repackages. The jar in JFrog is no longer the jar that was tested.

The same trap, bigger: a deploy job that runs mvn package so it has something to deploy. That is rebuilding per environment, the exact failure Lesson 0.1 exists to prevent, and in YAML it looks perfectly reasonable.

Because"same pipeline" stopped meaning "same machine". Anything a job produces from source, it produces again.

Fixbuild, test and publish in one job, as the example does with goal=deploy. Later jobs receive a version (or, from Phase 2, an image digest) and fetch that exact artifact. No job after build ever runs a compiler.

3

A GitHub-hosted runner is outside your network

Your Jenkins agents sit inside the company network, next to the Mule servers. GitHub's runners are on the public internet. A deploy job on ubuntu-24.04 cannot reach 10.20.0.15, and should not be able to.

  • Self-hosted runner. You install the runner agent on a machine inside the network; it dials out to GitHub and asks for work, so no inbound firewall hole is needed. That is what runs-on: [self-hosted, uat] selects. Same idea as an inbound Jenkins agent.
  • Cloud targets. For AWS this mostly goes away: the deploy calls AWS's public APIs, and the question becomes how the job proves who it is. That is OIDC, next lesson.

Becausethe controller and the runners are GitHub's machines, not yours. Where the work runs decides what it can reach.

4

An action is someone else's code, run with your token

A Jenkins plugin is installed once by an administrator. An action is fetched from another GitHub repository on every run, at whatever @v7 points to today, and it runs with your GITHUB_TOKEN and any secrets the job can see.

@v7 is a git tag, and a git tag can be moved. In March 2025 an attacker who got write access to tj-actions/changed-files, used by tens of thousands of repositories, repointed its version tags at a commit that printed the runner's secrets into the build logs (CVE-2025-30066). Every workflow using a tag picked it up on its next run. Workflows pinned to a commit SHA did not.

Becausea tag is a mutable pointer and a SHA is a content hash. This is Lesson 0.1's image tag versus digest, one layer up.

Fixpin every action to a full 40-character commit SHA, with the version as a comment: uses: actions/checkout@3d3c42e… # v7.0.1. Set permissions: contents: read at the top so the token can do almost nothing by default. Let Dependabot (package-ecosystem: github-actions) raise PRs that bump the SHAs.

The approval gate, and a catch on private repos

A Jenkins input inside an agent block holds an executor the whole time it waits. A job waiting on a GitHub environment's required reviewers holds no runner at all. But on GitHub's Free, Pro and Team plans, required reviewers only work on public repositories. Interchange is private for now, so it cannot have that gate yet. Making it public, which a portfolio eventually needs anyway, turns it on.

The third dialect

The same pipeline in GitLab CI

Two structural differences. Stages are an explicit ordered list, and jobs in the same stage run in parallel. And artifacts flow to later stages automatically; here a dotenv report passes the version along.

stages: [build, uat, prod] build: stage: build image: eclipse-temurin:21-jdk # pin by digest for real script: - echo "VERSION=$(./mvnw -q help:evaluate -Dexpression=project.version -DforceStdout)" > build.env - goal=verify; [ "$CI_COMMIT_BRANCH" = main ] && goal=deploy - ./mvnw -B -ntp "$goal" artifacts: reports: dotenv: build.env # later jobs get $VERSION deploy-uat: stage: uat tags: [uat-network] # a runner inside the network environment: uat rules: - if: $CI_COMMIT_BRANCH == "main" script: - ansible-playbook deploy.yml -e env=uat -e version=$VERSION deploy-prod: stage: prod tags: [prod-network] environment: production rules: - if: $CI_COMMIT_BRANCH == "main" when: manual # the input step script: - ansible-playbook deploy.yml -e env=prod -e version=$VERSION

GitLab's approval rules on protected environments are a paid-tier feature; when: manual is the free version: anyone with permission to run the job can press the button.

Build it

Interchange's first workflow

You write this one; I review it. Create .github/workflows/ci.yml in Interchange. The directory is already there with a .gitkeep in it. It is done when:

  1. It runs on every push to main and on every pull request.
  2. One job on ubuntu-24.04, Temurin 21 from actions/setup-java, with the Maven cache on.
  3. It runs ./mvnw -B -ntp verify, then ./mvnw -B -ntp -P release validate, so the SNAPSHOT rule from Lesson 0.1 is enforced by CI, not by memory.
  4. permissions: contents: read at the top.
  5. A concurrency: group per branch with cancel-in-progress: true, so pushing twice quickly does not run two builds of a stale commit.
  6. Every uses: pinned to a full commit SHA with the version as a comment. Look the SHA up yourself: gh api repos/actions/checkout/commits/v7.0.1 --jq .sha
  7. It goes green on a push. Watch it with gh run watch.

Then break it on purpose

On a branch, add any -SNAPSHOT dependency to one service's POM and open a pull request. The release check should go red. Read why with gh run view --log-failed, find the enforcer's message, then close the PR and delete the branch. A check you have never seen fail is a check you are only hoping works.

The exercise from the plan

Your own pipeline, translated

From memory, sketch your work's build and deploy pipelines as a Jenkinsfile: stages, agent labels, credentials, approvals. Use made-up names and no real hosts or secrets. Then translate it to an Actions workflow and answer three questions in writing:

  1. Which stages became separate jobs, and does any later job now rebuild something? (Difference 2.)
  2. Which jobs need a self-hosted runner, and why? (Difference 3.)
  3. Which Jenkins plugins did you rely on, and what replaces each one? Is the replacement a third-party action you would have to pin? (Difference 4.)

This is also the interview answer to "have you used GitHub Actions?": "Not in production. I run Jenkins in production, and here is what changes when you move it."

Check

Five questions

Out loud first, and end each answer with "because…".

You translate a Jenkinsfile into three jobs, build, test and deploy, with no needs: anywhere. What happens on the next push?

All three start at the same moment, on three different machines. deploy runs before anything is built and has nothing to deploy. test has no build output either, so it either fails or quietly compiles its own copy.

Because Actions jobs are parallel by default and isolated from each other: no shared workspace, no ordering. Order comes only from needs:, and files move between jobs only through artifacts or a registry.

Your Jenkins pipeline runs mvn verify in Build and mvn deploy -DskipTests in Publish. In Actions you make Publish its own job. What changed, and why does it matter?

Publish now rebuilds from scratch on a different machine. It re-resolves every dependency into an empty cache, recompiles and repackages. Every cause from Lesson 0.1a is back in play, and the jar that reaches JFrog is not the one whose tests passed.

Because in Jenkins both stages shared one workspace on one agent, and in Actions a job shares nothing. Fix: build, test and publish in one job, and give later jobs a version or digest, never source code to compile.

Your deploy job on ubuntu-24.04 times out connecting to the UAT server. The same playbook works from Jenkins. Why?

GitHub-hosted runners are on the public internet; your Jenkins agents are inside the company network. The UAT server is not reachable from outside, which is correct.

Fix: a self-hosted runner inside the network, selected with runs-on: [self-hosted, uat]. It connects out to GitHub to pick up jobs, so no inbound firewall rule is needed. Because where the job runs decides what it can reach.

A workflow uses some-org/notify-slack@v2. What is the risk, and what are the three fixes?

v2 is a movable git tag on someone else's repository, and the code it points to runs inside your job with your token and your secrets. If that repository is compromised and the tag repointed, your next run executes the attacker's code. That is what happened with tj-actions/changed-files in March 2025.

Fixes: pin to a full commit SHA with the version as a comment; set permissions: contents: read so the token is nearly powerless by default; let Dependabot propose SHA bumps you review. Because a SHA is a content hash and cannot be repointed, the same reason you promote an image by digest.

In GitLab CI, what decides which machine runs a job, and what replaces Jenkins's input step?

tags: picks the runner (the label equivalent) and, on Docker-based runners, image: picks the container the job runs in. when: manual replaces input: the job waits until someone presses play. Protected environments with approval rules are the stricter, paid-tier version.

Because GitLab, like Actions, separates "where" (runner tags) from "what" (the job), and approval is a property of the job or environment rather than a step that blocks a running agent.
