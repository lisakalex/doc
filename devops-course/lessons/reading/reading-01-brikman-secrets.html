The Example Is Not the Advice

Brikman's Terraform: Up & Running has the only real KMS section on your shelf, and it is good. It is also a teaching example, simplified in three places — and every simplification is somewhere Module 2 or Module 4 told you the security actually lives. Read it with this page beside it.

Terraform: Up & Running, 3e ch. 6 · Managing Secrets PDF pages 328–334

What you are reading

Where the section sits

Chapter 6 is organised around three axes — what kind of secret, where it is stored, how you get at it — and then walks three techniques. KMS appears in the second one.

Chapter 6 — Managing Secrets with Terraform Secret Management Basics The Types of Secrets You Store personal / customer / infrastructure The Way You Store Secrets KMS first named here The Interface You Use to Access Secrets A Comparison of Secret Management Tools Secret Management Tools with Terraform Environment variables Encrypted files ← the KMS section, p328–334 Secret stores AWS Secrets Manager, p334+ State Files and Plan Files p340 — read this too, see below

The technique: encrypt a secrets file with a CMK, commit the ciphertext, and decrypt it back inside Terraform. The worked example runs aws_iam_policy_document → aws_kms_key → aws_kms_alias → an encrypt.sh wrapper around aws kms encrypt → aws_kms_secrets + yamldecode → straight into aws_db_instance. Then sops as the humane version, and honest advantages and drawbacks.

Read it. It is the right shape.

Nothing below says the technique is wrong. The point of this page is that the example is not the advice — three details are simplified for the page, and all three are load-bearing in production.

First, the agreements

What he says that you already know

Worth noticing, because independent agreement is how you tell a real rule from something a tutor made up:

His pricing — $1 per key per month, $0.03 per 10,000 calls, $1–$10/month for a small estate — is still right for 2026, and the ranges are useful sanity checks. What it omits is that rotation is separately billed for the first and second rotation of each key, capped thereafter. Lesson 4.1. On a handful of keys it rounds to nothing; on four hundred it does not.

Gap one · the big one

That key policy locks you out

Here is the example, complete, as printed:

data "aws_caller_identity" "self" {} data "aws_iam_policy_document" "cmk_admin_policy" { statement { effect = "Allow" resources = ["*"] actions = ["kms:*"] principals { type = "AWS" identifiers = [data.aws_caller_identity.self.arn] } } }

He flags it himself — “to keep this example simple” — but look at what it actually produces. One statement, naming one principal, and no delegation to IAM at all. There is no :root statement. Which is precisely the key from revision question 3: if that one principal stops resolving, nobody on earth can use or edit this key, because editing the policy is itself an action the policy must allow.

Two ways it stops resolving, and which one you get depends on how you authenticate:

1

If you run Terraform as an IAM user

The ARN is arn:aws:iam::111122223333:user/al. AWS stores it as the user's unique principal ID, not as text. Delete that user and the policy is broken — and recreating a user with the same name does not fix it, because the new user has a new principal ID. The key becomes a support case.

2

If you run Terraform the way this course taught you

You assume a role, so aws_caller_identity returns a session ARN: arn:aws:sts::111122223333:assumed-role/admin/botocore-session-1758…. That is a legal principal — but it names one session. Tomorrow's session has a different name, so it is a different principal, and it has no access to the key you created today.

The irony worth keeping

The example works cleanly only if you are a long-lived IAM user with static keys — which is exactly the posture Lesson 2.5 had you dismantle. Do the Module 2 thing and the Module 6 example quietly produces a key nobody can use next week.

What to write instead

Resolve the session back to the role that issued it, and keep the IAM delegation AWS puts in the default policy:

data "aws_caller_identity" "self" {} # turns an assumed-role session ARN into the underlying role ARN data "aws_iam_session_context" "self" { arn = data.aws_caller_identity.self.arn } data "aws_iam_policy_document" "cmk" { statement { sid = "Delegate to IAM in this account" effect = "Allow" actions = ["kms:*"] resources = ["*"] principals { type = "AWS" identifiers = ["arn:aws:iam::${data.aws_caller_identity.self.account_id}:root"] } } statement { sid = "The pipeline may use the key, through KMS only" effect = "Allow" actions = ["kms:Encrypt", "kms:Decrypt", "kms:DescribeKey"] resources = ["*"] principals { type = "AWS" identifiers = [data.aws_iam_session_context.self.issuer_arn] } } }

Two statements, and the first is the one the book drops. :root names the account, not the root user — Lesson 4.2 — so it delegates to IAM rather than granting anything, and it is what makes the key survivable when people come and go. The second names the role, not the session, so it still works tomorrow.

Gap two

That is not envelope encryption, and it has a ceiling

The script calls aws kms encrypt on the whole file. That is direct encryption — the plaintext travels to KMS, KMS encrypts it with the CMK's own material and hands back the ciphertext. It works here because two lines of YAML are tiny.

The limit nobody mentions until it fires

Encrypt takes at most 4 KB of plaintext on a symmetric key. A credentials file grows, somebody adds a certificate or a private key, and the pipeline fails with ValidationException on a line that worked for two years. There is no setting to raise it; it is what the API is for.

Everything above 4 KB is why GenerateDataKey exists, which is Lesson 4.1 in one sentence: ask KMS for a fresh data key, get it back twice — once in plaintext, once wrapped — encrypt the payload locally with the plaintext copy, throw that copy away, and store the wrapped copy beside the ciphertext. Unlimited size, one KMS call.

Which is exactly what sops does internally, and a better reason to reach for it than the one the book gives. Brikman recommends sops for ergonomics — no more long aws kms commands, less chance of committing plaintext — and that is true. But it also silently fixes the ceiling, because sops generates its own data key, encrypts the values with it, and stores the KMS-wrapped key in the file's metadata. Same envelope pattern, done for you.

Gap three · the one that is not his fault

The decrypted secret lands in state

Follow the example to its end and the database password is passed to aws_db_instance. Which means it is written, in plain text, into terraform.tfstate. Every carefully encrypted byte in version control, and then the cleartext sits in the state file.

He does cover this — thoroughly — but in a different section, six pages later: State Files and Plan Files, p340. “Any secrets you pass into your Terraform resources and data sources will end up in plain text in your Terraform state file.” The encrypted-files section does not cross-reference it, so somebody reading only the KMS pages, which is what you were doing, would miss it entirely.

What it means for the ranking

This technique does not remove the secret; it moves the secret. The thing you must now protect is the state bucket and the key that encrypts it — which is why your repo encrypts state with KMS, and why Lesson 2.6 ranks “no secret at all” above every one of these three techniques. An IRSA role has nothing to leak into state.

Using it

Where this technique belongs

Reach for it

Bootstrap secrets that must exist before anything else does, small config that genuinely belongs beside the code, and teams who want secrets reviewed in pull requests. Anywhere the audit question is “who changed it” rather than “who read it”.

Do not

Anything that must be rotated on a schedule, anything read at runtime by an application, and anything whose exposure you need to detect. Encrypted-in-git cannot be revoked — the old commit still decrypts with the same key forever.

Check yourself

Two questions

A colleague copies the book's CMK example into your repo and applies it from their laptop, which assumes the admin role. It works. A week later nobody can touch the key. What happened, and what is the one line that would have prevented it?

The key policy named their session — an assumed-role/admin/<session-name> ARN — because that is what aws_caller_identity returns when you assume a role. It is a valid principal, so nothing failed at apply time. The next session had a different name, so it was a different principal, and the key's only statement now grants access to somebody who no longer exists.

No IAM delegation exists in that policy either, so no administrator can override it and no amount of IAM policy helps. It is the permanent lock-out from Lesson 4.2, produced by a published example.

The one line: the :root statement from the AWS default key policy, delegating to IAM in the account. The better second line is data.aws_iam_session_context.self.issuer_arn, which names the role rather than the session.

You adopt the encrypted-files technique. Six months later a leaver's laptop is found to have had a copy of the repo and their AWS access. Which of your secrets must be rotated?

All of them, and every version of them. The repository holds the ciphertext of every secret that was ever committed, and the key that decrypts all of it is the same CMK. If they could call Decrypt, they could read the current secrets and every historical one, and you cannot tell from CloudTrail which ones they actually read — the audit log shows key use, not purpose. Brikman lists both of these as drawbacks; this is what they look like on a Tuesday.

Which means the remediation is the expensive one: rotate every credential the files contain, re-encrypt, and accept that the old commits stay readable to anyone who kept a copy of both the repo and the key material. Rotating the CMK does nothing for that — Lesson 4.1 — because the old ciphertext is still decryptable by the old material, which KMS keeps.
