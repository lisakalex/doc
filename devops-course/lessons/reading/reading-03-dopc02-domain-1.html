The Toolchain That Shrank

Domain 1 is the best section of the DOP-C02 course — 2.5 hours on the CI/CD chain, and the CodeDeploy lectures are as good as anything in it. It is also the section that decayed most, because the Code* family is precisely what AWS has spent two years retiring. Four of its claims have expired, three of its services have moved on without it, and the part that is still exactly right is worth your eleven minutes.

Where it is wrong

Four claims that have expired

None of these were wrong when recorded. All four are wrong now, and three of them are wrong in the same direction: AWS withdrew the service.

1 · "CodeStar regroups CodeCommit, CodePipeline, CodeBuild and CodeDeploy in one tool"

Lecture 001. AWS CodeStar reached end of support on 25 July 2024 and is listed by AWS among services in full shutdown. This is not a rename or a repositioning — the service is gone. Do not spend time on it. The exam guide still lists CodeStar among in-scope Developer Tools, which tells you something about how closely the guide tracks the console.

2 · "A CodeStar Source Connection — a GitHub application that connects GitHub into AWS"

Lecture 008. Renamed to AWS CodeConnections on 29 March 2024. From 1 July 2024 the console creates connections with codeconnections in the ARN; resources created under the old codestar-connections namespace are still supported.

What did not change

The mechanism. A connection is still the right answer for an event-driven third-party source, and it is still the thing that replaces polling. Only the name moved — so an exam question may use either, and the ARN namespace is the tell for which era the question was written in.

3 · "CodeGuru Reviewer does automated code reviews… it supports Java and Python"

Lectures 023 and 024. Since 7 November 2025 you cannot create new repository associations in CodeGuru Reviewer. It is in maintenance mode: existing associations keep working, and AWS will not add functionality. Automated code review moved to Amazon Q Developer, which covers static analysis for security and best practice, secrets exposure, dependency vulnerabilities and code quality. The Secrets Detector demo in lecture 024 is the clearest casualty.

Maarek hedges inside the lecture — "don't quote me on this, maybe things will evolve over time" — which turned out to be the most durable sentence in it. Worth noting which claims an author chooses to hedge; it is usually the ones they know are thin.

4 · "Why would you want to use CodeCommit? Git repositories can be quite expensive"

Lecture 002. This one is more interesting, because the obvious conclusion is wrong. AWS closed CodeCommit to new customers on 25 July 2024 — and then returned it to general availability. So the service works, new accounts can use it, and the lecture is not factually wrong.

The real problem

CodeCommit does not appear in the Developer Tools section of exam guide v1.6. The in-scope list there runs CodeArtifact, CodeBuild, CodeDeploy, CodeGuru, CodePipeline, CodeStar, Fault Injection Simulator, X-Ray. The course spends 22 minutes and five lectures on a service the current guide omits — and zero on Fault Injection Simulator, which the guide includes.

The branch-security content in lecture 005 survives the cut and is worth keeping, because the shape of it recurs: CodeCommit has no resource policy, so restricting who may push to main is done with an IAM Deny on the user or group, conditioned on the branch reference. That is the same reasoning as Module 2's explicit-deny lesson, in a service you will probably never use.

Where it is incomplete

Three things that arrived after the recording

Not errors. Features that did not exist, whose absence makes a correct answer in the course an incomplete answer now.

ServiceWhat the course knowsWhat exists now
CodePipelineThree ways to start a pipeline: events (preferred), webhooks, polling (discouraged)Still true, now underspecified. V2-type pipelines add triggers that filter: on git tags, branches and file paths for pushes, and on branches and file paths for pull requests — which is what makes branch-based development and monorepos work. Plus Parallel and Queued execution modes, and stage-level rollback, either to a named previous successful execution or automatically on failure.
CodeBuildBuilds run in a container on managed compute, from an AWS-provided image or your ownTwo compute modes: EC2 and AWS Lambda, the latter for lower start-up latency and no queueing. EC2 mode runs on either on-demand fleets (BUILD_GENERAL1_SMALL and friends) or reserved capacity fleets, where you choose vCPU, memory and disk and CodeBuild picks a matching type.
CodeDeployEverythingNothing to add. The hooks, the lifecycle, the traffic-shifting strategies and the troubleshooting list are all current.

The CodePipeline gap is the one that costs you marks. "How do I start a pipeline only when files under services/api/ change on a pull request into main?" had no good answer in 2023 — you started on every change and burned a build step deciding not to build. It is now one trigger filter, and a question written against the current console will assume you know that.

Where it is right

The lifecycle, which has not moved at all

Lecture 016 teaches the CodeDeploy EC2 hook sequence, and the thing that makes it a good lecture is the distinction it draws: some events are yours to script, and four belong to the agent. Checked against the appspec hooks reference, every claim holds.

Two facts the documentation carries and the lecture does not, both of which are exactly the sort of thing a professional-level question turns on:

ApplicationStop runs the old revision's script

It fires before the new bundle is downloaded, so "the AppSpec file and scripts used for this deployment lifecycle event are from the previous successfully deployed application revision". Two consequences. A fix you make to ApplicationStop does not take effect until the deployment after the one you ship it in. And the hook does not run at all on the first deployment to an instance, because no AppSpec file is there yet.

The ECS hook is called AfterAllowTestTraffic

Lecture 017 describes the test-listener step correctly but never names it. The five scriptable ECS hooks are BeforeInstall, AfterInstall, AfterAllowTestTraffic, BeforeAllowTraffic and AfterAllowTraffic; Start, Install, TestTraffic, AllowTraffic and End are reserved. There is no ApplicationStop, ApplicationStart or ValidateService on ECS — and every hook is a Lambda function, not a script, which must call putLifecycleEventHookExecutionStatus within the hour or the deployment is failed.

Lambda deployments have exactly two hooks, BeforeAllowTraffic and AfterAllowTraffic, which the course gets right. And a detail worth stealing for any deployment system: each hook script has a timeout whose default is 3600 seconds, which is also the ceiling for all scripts in one lifecycle event combined, and a runas for the user to impersonate. Hooks receive APPLICATION_NAME, DEPLOYMENT_ID, DEPLOYMENT_GROUP_NAME, DEPLOYMENT_GROUP_ID and LIFECYCLE_EVENT as environment variables — the course names only the deployment group.

For this repo

What this maps onto in your own code

Why CodePipeline needs an artifact store and GitHub Actions does not

The course's best architectural point, in lecture 006: stages do not talk to each other. CodePipeline extracts the source into an S3 artifact store and hands that artifact to CodeBuild — which is why CodeBuild needs no access to the source repository at all. CodePipeline pushes the code to it, through S3.

Your .github/workflows/cicd.yml never needs that, because steps in a job share a filesystem and jobs pass artifacts through the Actions artifact API. The difference is not cosmetic — it is why a cross-region CodePipeline needs one artifact bucket per region in which it has actions, and why the pipeline's service role needs read and write on every one of them. Create the pipeline in the console and AWS makes those buckets for you; create it with the CLI or SDK and you make them yourself, which is the failure mode worth remembering.

The hooks you already have

Your repo deploys with Helm, so there is no CodeDeploy. The concept transfers exactly: Helm's pre-install, post-install and pre-upgrade hooks are BeforeInstall, AfterInstall and ApplicationStop wearing different names, and ValidateService is what your /ready probe is for. The Module 13 split between /health and /ready is the same decision as putting a check in ValidateService rather than AfterInstall: one asks whether the process is alive, the other whether it should receive traffic.

The third appearance of one rule

Cross-account access to a CodeArtifact repository needs a resource policy on the repository; an identity policy in the other account cannot reach it, and access is all-packages or nothing — you cannot grant a subset. That is Module 3's bucket policy and Module 4's key policy for the third time. The rule to carry out of the course is the general one: crossing an account boundary requires the resource to opt in, and the service-specific detail is only which document does the opting.

And one you will use before the exam

buildspec.yml resolves environment variables from SSM Parameter Store and Secrets Manager at build time, which is the correct place to put a CI secret. Putting it in the variables block puts it in your git history instead — Lesson 2.6's trap, in a file you have not written yet.

Check yourself

Four questions

A pull request into main should start your pipeline, but only when files under services/api/ have changed. What do you configure — and what did this require before 2023?

A V2-type pipeline with a trigger on pull-request events, filtered on branch main and on the file path services/api/. Push and pull-request events take different filter sets: pushes can filter on git tags, branches and file paths, pull requests on branches and file paths.

Before trigger filters existed you started the pipeline on every change and decided inside it — a first CodeBuild action that inspected the diff and exited early. You paid for a build in order to learn that you did not need a build. The course's events-versus-webhooks-versus-polling lecture is still correct about how a pipeline starts and has nothing at all about which changes should start one.

A blue/green CodeDeploy deployment to EC2 installs cleanly and then fails at AllowTraffic. There is nothing in the deployment logs. Where do you look?

The load balancer's health checks. The deployment logs are empty because nothing in the deployment failed — the application installed, and the ELB simply never considered the replacement instances healthy, so traffic could not be allowed. Check the target group's health check path, port, protocol and thresholds.

The sharper half of the answer: a BeforeAllowTraffic hook is where you would have caught this yourself, with the same health check the ELB is about to run. A deployment that can only fail at a reserved event is a deployment missing a validation hook.

One CodePipeline deploys a Lambda function to eu-west-1 and us-east-2. It works for eu-west-1 and fails for us-east-2. Name the likely causes.

No artifact store in us-east-2. A pipeline needs an S3 artifact bucket in every region where it has actions. If the pipeline was created in the console those buckets were created for you; if it was created with the CLI, SDK or CloudFormation, they are yours to create.

The pipeline's service role lacks read and write on that bucket. CodePipeline copies input artifacts into the remote region itself, so it needs both.

And a third, less obvious: a cross-region CloudFormation action needs its own template. One build step producing one template.yaml is not enough — the course's example emits template-us-east-2.yaml as a separate artifact for exactly this reason.

Your CI needs a database password. Where can CodeBuild get it, and what must you not do?

The env section of buildspec.yml resolves values from the SSM Parameter Store and from Secrets Manager at build time. Neither value is stored in the file.

What you must not do is put it in the variables block, which is plaintext in the buildspec and therefore in git, forever, on every branch and in every fork.

The permission detail that catches people: the CodeBuild service role needs read access on whichever store you chose, and kms:Decrypt on the key if the parameter is a SecureString — because a wildcard in one service namespace never crosses into another. That is Lesson 2.5 and Lesson 4.2, arriving in a build file.
