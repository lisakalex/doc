The Table Nobody Designed

Three books on your shelf create the same DynamoDB table, in the same chapter, for the same reason. It is the best-designed table in any of them — eight lines, one access pattern, no index — and not one author presents it as a design. It is also, as of Terraform 1.11, deprecated.

Brikman, ch. 3 Wojslaw, ch. 11 Terraform in Action, ch. 6 LockID

What you are reading

The same eight lines, three times

Search ~/Documents/books/devops for DynamoDB and the hits cluster in a place that has nothing to do with databases — the chapter on Terraform remote state:

None of the four discusses partition keys, access patterns or capacity. DynamoDB appears as plumbing — a thing you create so that something else works. Which is exactly why it is worth reading against Lesson 5.1, because the table they hand you is the one your own users table should have been.

The artefact

Two tables, one correct

Here is Brikman's, from page 152:

resource "aws_dynamodb_table" "terraform_locks" { name = "terraform-up-and-running-locks" billing_mode = "PAY_PER_REQUEST" hash_key = "LockID" attribute { name = "LockID" type = "S" } }

And here is yours, from terraform/main.tf:

resource "aws_dynamodb_table" "users" { name = local.dynamodb_table billing_mode = "PAY_PER_REQUEST" hash_key = "email" attribute { name = "email" type = "S" } }

Character for character, the same table. Same billing mode, same single partition key, no sort key, no index, eight lines each. One of them is exactly right and the other is the subject of a whole lesson — and nothing in the Terraform tells you which is which.

The difference is not in the configuration

It is in how many questions the application asks. The lock table is asked exactly one: “does a lock exist for this state file?” The users table is asked six, and was designed for one of them.

Why it is the best table in the book

One question, answered by existence

Brikman gives the rationale in a single sentence, and it is the most precise thing any of the four books says about DynamoDB (page 152):

Quoted

“It supports strongly consistent reads and conditional writes, which are all the ingredients you need for a distributed lock system.”

That is the whole design, and it is worth unpacking because the mechanism is not what most people assume. The lock is not a flag that is set to true. The item's existence is the lock.

1

Acquire

Terraform issues a PutItem with ConditionExpression: attribute_not_exists(LockID). The write succeeds only if no item with that key is there. One network call, atomic, no read first.

2

Lose the race

If somebody already holds it, DynamoDB rejects the write with ConditionalCheckFailedException — which is the error behind the “Error acquiring the state lock” message everyone has seen. The item holds an Info attribute naming who, when and which operation, which is why the message can tell you who to go and ask.

3

Release

DeleteItem. The lock is gone because the item is gone.

4

The one item that is not a lock

The table also holds a row keyed <bucket>/<key>-md5 carrying a digest of the state file, so Terraform can detect a truncated or mismatched upload. Two item shapes, one table, told apart by a suffix on the key — the trick from Lesson 5.1, used in the wild.

Count what this table never does: no Query, no Scan, no secondary index, no filter expression, no sort key, no pagination. Every access is GetItem-shaped, by a key the caller already has. That is the ideal case, and it is why nobody ever writes a blog post about their Terraform lock table being expensive.

The LockID value is the state file's own address — my-bucket/global/s3/terraform.tfstate — so the key is the question. One state file, one lock, by construction. Note also that Terraform requires the attribute to be named LockID exactly, capitalisation included; it is not a convention you may rename.

Where the books are wrong

Three corrections, in increasing order of consequence

1. It is not a flag

Wojslaw, page 324, describing the same table:

Quoted, and wrong

“In AWS environments, it's simply a DynamoDB table with a lock entry with a state of 0 or 1.”

There is no 0 or 1. There is an item or there is no item, and the distinction is the entire reason the thing works. A boolean flag would have to be read, inspected, and then written — three steps with a gap in the middle, and two machines running terraform apply at the same moment would both read 0 and both write 1. That is a textbook race, and it is precisely what a lock is supposed to prevent.

The conditional write collapses the read and the write into one atomic operation that the storage engine adjudicates. Getting this wrong in prose is harmless; getting it wrong in your own code — “I'll just check if the row exists, then insert it” — is a bug you will not reproduce in testing.

2. The pattern is deprecated

All three Terraform books teach dynamodb_table in the backend block. Since then:

TerraformWhat changed
1.10use_lockfile = true introduced — the S3 backend locks by writing a .tflock object beside the state, using S3 conditional writes
1.11dynamodb_table deprecated; configuring it emits a warning
futureremoval announced
# what the books teach terraform { backend "s3" { bucket = "state-files" key = "terraform.tfstate" region = "eu-central-1" dynamodb_table = "terraform" # deprecated in 1.11 encrypt = true } } # what to write today terraform { backend "s3" { bucket = "state-files" key = "terraform.tfstate" region = "eu-central-1" use_lockfile = true # no table, no second resource encrypt = true } }

Both can be set at once during a migration, and Terraform then requires both locks before proceeding — which is the correct way to cut over without a window where two machines use different mechanisms and neither sees the other.

3. The CDK example grants everything

Kapoor, page 152, assembling permissions for a Lambda:

dynamodbPermissionsForLambda.addActions("dynamodb:*"); dynamodbPermissionsForLambda.addResources(dynamodbTable.tableArn); kmsPermissionsForLambda.addActions("kms:*"); kmsPermissionsForLambda.addResources("*");

The DynamoDB statement is at least scoped to one table, though dynamodb:* includes DeleteTable. The KMS statement is kms:* on * — every key in the account, every operation, including ScheduleKeyDeletion and PutKeyPolicy. Lesson 4.2 spent a section on exactly this, and Lesson 5.1 closes by removing a single verb from a policy so that an expensive mistake becomes impossible. Here a book does the opposite, in a chapter about a different subject, where a reader copying the CDK is not thinking about IAM at all.

This is the same shape as Reading Note 1: the simplification is in the part the chapter is not about, which is exactly where a reader will not be looking.

What survives

The mechanism was never DynamoDB

It would be easy to read the deprecation as “DynamoDB was the wrong choice”. It was not. For a decade it was the only AWS store that offered the two primitives Brikman named — strongly consistent reads and conditional writes. S3 could not do it: writes were eventually consistent, and there was no way to say “create this object only if it does not exist”.

What changed is S3, not Terraform. S3 gained strong read-after-write consistency in 2020 and conditional writes in late 2024 — If-None-Match on a PUT, which is byte-for-byte the same idea as attribute_not_exists(LockID). The moment the state store itself could do compare-and-set, the second service became an extra moving part with its own IAM policy, its own bill and its own bootstrap problem.

The transferable idea

A distributed lock is compare-and-set on a store everybody can see. DynamoDB, S3 with If-None-Match, Redis with SET NX, etcd with a compare-and-swap, a unique index in Postgres — all the same primitive wearing different vendor names. Learn the primitive and the migration above is a configuration change rather than a new topic.

For this repo

You already have this table

Not hypothetically. terraform/state-backend/main.tf contains it, created by whoever followed this chapter — which was you:

resource "aws_dynamodb_table" "state_lock" { name = "${var.namespace}-tfstate-lock" billing_mode = "PAY_PER_REQUEST" hash_key = "LockID" attribute { name = "LockID" type = "S" } }

So this repo holds both tables from the comparison above: the ideal one in state-backend/ and the over-asked one in main.tf, eight lines each, written months apart, and only one of them is a problem. And your backend.hcl passes the deprecated argument:

# terraform/backend.hcl.example bucket = "prima-tech-challenge-lisakalex-tfstate" key = "senior-sre-tech-challenge/terraform.tfstate" dynamodb_table = "prima-tech-challenge-lisakalex-tfstate-lock" kms_key_id = "arn:aws:kms:..." encrypt = true

Nothing is broken — it still works, and the AWS stack is torn down anyway. But when you rebuild it, this is a free simplification:

1

Swap dynamodb_table for use_lockfile = true

Set both at once first, run an apply so each machine holds both locks, then remove dynamodb_table and delete aws_dynamodb_table.state_lock. You lose one resource, one IAM statement and one thing to forget when you tear the stack down — which, given how often you destroy this stack, matters more here than in most repos.

2

Keep versioning on the state bucket

This is the part none of the books oversell: the lock protects you from concurrent writes, and versioning protects you from the bad write that succeeded. Different failures, both needed.

3

If you inherit a lock table, learn the stuck-lock drill before you need it

A crashed apply leaves the item behind and every later run fails. The supported fix is terraform force-unlock <LOCK_ID>, taking the ID from the error message — not deleting rows in the console. And if somebody has already deleted rows: the -md5 row is not a lock and does not need restoring; Terraform rewrites it on the next apply.

Check yourself

Two questions

A colleague proposes adding a sort key to the lock table “so we can keep lock history and see who locked what, when”. What do you tell them?

Three separate noes. First, you cannot: the key schema is fixed at creation, so this is a destroy-and-create of the table, and Terraform will show it as forces replacement. Second, it would not work: Terraform requires a table whose primary key is exactly LockID, and it writes and deletes by that key alone — a composite key would break the backend, because the code does not supply a sort key value.

Third, and most importantly, it is the wrong tool for the question. Lock history is not an access pattern of the locking system; the lock item is deleted the moment the operation finishes, by design. If you want an audit trail of who ran apply and when, that is CloudTrail on the state bucket, or your CI logs — a system that is supposed to retain history, rather than one whose correctness depends on forgetting.

Which means the right response is to ask what they are actually trying to find out, because “who is running Terraform” is a reasonable question with a good answer that is not this table.

You are reviewing a pull request that adds a DynamoDB table for a new feature. It looks exactly like the lock table: one partition key, no sort key, no index, PAY_PER_REQUEST. What do you ask?

Not “is this table right?”, because you cannot tell from the Terraform — it is the same eight lines either way. Ask about the questions: what will the application look up, and by what, over the life of this feature? List them. If the answer is one question and the caller always holds the key, this is the ideal table and you approve it. If any answer begins “we'll also need to find all the…”, the design is wrong now and will be expensive to change later, because the key schema is the one thing that cannot be altered.

The follow-up question is about the key's values: how many distinct ones, and will traffic land evenly? A partition key with one value is a single partition with a hard ceiling, however much capacity the table is allowed.

Which means a DynamoDB review is never a review of the resource block — it is a review of a list of sentences that does not appear in the diff.
